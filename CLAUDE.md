# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Qué es esto

PRISMA: plataforma para odontólogos de Córdoba que combina gestión de clínica (turnero, agenda, pacientes) con una página pública propia deployable donde los pacientes piden turno, más un buscador público de clínicas. La especificación completa vive en `docs/Arquitectura y base/dental-mirage-spec.md`; el plan de implementación fase por fase en `docs/Arquitectura y base/implementation-plan.md`; las decisiones de arquitectura/alcance con sus alternativas descartadas en `docs/Arquitectura y base/tradeoffs.md`. Leé esos tres antes de planificar o tocar un módulo nuevo — son la fuente de verdad, este archivo es solo el mapa rápido. El sistema de auth/onboarding (Google OAuth, verificación de mail por código de 6 dígitos, clínicas individuales/organización) queda documentado como cierre de feature en `docs/Login/feature-sumarte-login-resumen.md` (qué se implementó, variables de entorno, repaso de seguridad) y como decisiones puntuales en `docs/Arquitectura y base/tradeoffs.md` TR-036 a TR-047 — el flujo post-TR-047 cambió: `/sumarse` es solo crear cuenta + confirmar código (2 pasos), perfil profesional y clínica se completan después en un modal de "bienvenida" sobre `/seleccionar-servicio` (TR-057 a TR-059) — `docs/Login/feature-sumarte-login.md` fue el prompt original de esa feature, no un documento vivo, y puede quedar desactualizado. `README.md` (raíz) tiene la puerta de entrada para levantar el proyecto de cero (setup, comandos, CI, deploy).

**Proyecto de referencia:** `../Marcuzzi_Madryn` — mismo stack y modo de trabajo, reutilizado sin cambios (spec §9). Ante cualquier duda de patrón (BFF, interfaces dev/prod, testing, flujo de ramas), ese repo es el ejemplo ya validado en producción de cómo aplicarlo.

## Stack (decidido, no "a evaluar" — spec §9.1)

El **porqué técnico** de cada pieza —contra qué alternativa se comparó, qué se sacrifica y qué condición la haría cambiar— está en `docs/Arquitectura y base/por-que-cada-decision-tecnica.md`. Leerlo antes de proponer cambiar cualquier elemento del stack: varias decisiones que parecen arbitrarias sostienen mecanismos centrales (el exclusion constraint de no-solapamiento y el rollback de las migraciones dependen de features que solo tiene PostgreSQL).

- **Backend:** Go + [chi](https://github.com/go-chi/chi) + GORM, en `apps/api`.
- **Frontend:** Next.js + TypeScript + Tailwind, en `apps/web` — leer el `AGENTS.md` que genera cada versión de Next antes de escribir código, por posibles breaking changes.
- **DB:** PostgreSQL + extensión `btree_gist`.
- **Package manager JS:** `pnpm` (no `npm`).
- Requiere Docker corriendo (`docker compose up -d`) para Postgres local.

## Comandos

Desde la raíz del repo (`package.json` tiene los atajos; detalle completo en `README.md`):

- `pnpm run dev:web` / `pnpm run build:web` / `pnpm run lint:web` / `pnpm run typecheck:web`
- `pnpm run typecheck:shared-types`
- `pnpm run dev:api` (`go run ./cmd/api`) / `pnpm run build:api` (`go build ./...`) / `pnpm run vet:api`
- `pnpm run migrate:api` — aplica el esquema (AutoMigrate de GORM). Idempotente, se puede correr de nuevo sin romper nada.
- Lint de Go: `golangci-lint run ./...` dentro de `apps/api` (no tiene atajo en `package.json`). En Windows con `git config core.autocrlf=true` (y sin `.gitattributes` en el repo), el working tree queda en CRLF mientras los blobs de git son LF — `gofmt`/`golangci-lint` corridos en el lugar dan resultados inestables (archivos distintos marcados "mal formateados" de una corrida a otra, puro ruido CRLF-vs-LF). Antes de confiar en un resultado ahí: extraer una copia sin CRLF primero (`cp -r apps/api <tmpdir> && find <tmpdir> -name '*.go' -exec sed -i 's/\r$//' {} \;`) y correr el lint dentro de esa copia.
- `pnpm run test:web` (Vitest) / `pnpm run test:api` (`go test ./internal/...`) — ver "Testing" abajo.
- `pnpm run test:coverage:web` / `pnpm run test:coverage:api` — mismo run + reporte de cobertura.
- Un test puntual: frontend `pnpm --filter @dental-mirage/web test <patrón del archivo o nombre>`; backend `cd apps/api && go test ./internal/<paquete>/... -run TestNombre`.
- `-race` (detector de condiciones de carrera en Go) no está en `test:api` porque alarga la corrida — para correrlo local: `cd apps/api && go test ./internal/... -race`.

Flujo de ramas activo desde antes de Sprint 4 — ver "Flujo de ramas" más abajo; no asumir que hay que crear una rama ni mergear a `main` sin que lo pidan explícitamente.

## El requisito no negociable: turnos sin solapamiento (spec §4.3)

Dos turnos de un mismo profesional no pueden solaparse en horario. Se garantiza con `EXCLUDE USING gist` sobre **`(atendido_por_user_id, rango_horario)`** en la tabla `turnos`, **a nivel de base de datos**, no solo validación de app — mismo mecanismo que las reservas de alojamiento/vehículos en Marcuzzi_Madryn. El constraint solo aplica a turnos en estado `agendado` (un `cancelada` nunca conflictúa, libera el horario). Hasta Extra 2.3.3 también excluía a los `pendiente` (recién llegados de la página pública, sin hora fija todavía — TR-006 en `docs/Arquitectura y base/tradeoffs.md`) — ese estado se eliminó del todo (TR-104): hoy `Turno.Estado` solo puede ser `agendado`/`cancelada`. Cualquier intento de solapamiento debe fallar de forma controlada (error de validación en el modal), nunca como 500 crudo.

**La columna cambió en la Fase 3.2.1 (TR-137), y el texto de esta regla no.** Siempre dijo "del mismo profesional", pero la constraint estaba sobre `profesional_id` — que guardaba un `clinics.id`. Mientras cada clínica tuvo un solo profesional las dos cosas coincidían; con N profesionales, sobre la clínica pasaba de garantía a **bloqueo falso** (rechazaba que dos odontólogos atendieran a la misma hora en sillones distintos). Sobre `atendido_por_user_id` gana además algo que el modelo viejo no podía expresar: impide que un profesional tenga turnos solapados en **dos clínicas distintas**.

Dos cosas que hay que saber al tocar turnos: **todo turno `agendado` debe tener `atendido_por_user_id`** (`chk_turno_agendado_profesional`) — sin esa columna el constraint no aplica, porque compara `WITH =` y dos NULL nunca son iguales; y ese usuario **tiene que ser miembro de esa clínica**, garantizado por la FK compuesta contra `clinic_members`. Para resolver el profesional cuando todavía no hay elección explícita, `db.OwnerDeLaClinica(tx, clinicID)`.

## Arquitectura del frontend: BFF con Server Actions — el navegador nunca llama a la API Go directo

Mismo patrón que Marcuzzi_Madryn: `apps/web/src/lib/api.ts` es `server-only`, sin prefijo `NEXT_PUBLIC_`. Todo el tráfico hacia `apps/api` pasa por Server Actions (`apps/web/src/app/actions/*.ts`, `"use server"`) o Route Handlers. La sesión (token opaco validado server-side contra `internal/auth.Session` en Go — ya no JWT stateless, ver TR-037 en `docs/Arquitectura y base/tradeoffs.md`) va en cookie `httpOnly` (`lib/session.ts`), nunca en `localStorage`. Una pantalla nueva extiende `lib/api.ts` y se llama desde Server Component/Action — nunca un `fetch` nuevo desde Client Component.

La sesión y el rate-limiting de auth (`internal/ratelimit`) viven en Postgres, no en memoria del proceso — cualquier instancia del backend valida/cuenta contra la misma tabla, así que escalar a varias instancias no requiere sticky sessions ni un secret compartido entre ellas. Dato aparte para no confundirse: la env var `JWT_SECRET` es un nombre heredado de antes de TR-037 — hoy solo firma el `state` de OAuth de Google (`internal/http/oauthstate.go`), no queda ningún JWT de sesión real; no se renombró para no romper deploys ya configurados con ese nombre (ver el comentario en `apps/api/.env.example`).

## Interfaces con implementación dev/prod (spec §9.4)

Mismo patrón que Marcuzzi_Madryn para cada dependencia externa: interfaz en Go, implementación dev (no-op/log) e implementación prod activada por env var, inyectada desde `main.go`. El envío inicial del formulario público de turno **no** usa este patrón — es un link `wa.me` generado client-side (TR-003), no una integración de backend; el patrón dev/prod queda reservado para recordatorios automatizados futuros (Fase 2) y para las dependencias del auth nuevo, ya implementadas: `internal/mail` (Resend/`LogSender`), `internal/googleauth` (Google OAuth), `internal/turnstile` (CAPTCHA), `internal/security` (HaveIBeenPwned) — todas nil-safe/no-op sin la env var correspondiente configurada, ver `buildAuthDeps` en `cmd/api/main.go`. `internal/storage` (foto de perfil) solo tiene la implementación dev (disco local) hecha — R2/S3 prod queda pendiente, ver TR-046 en `docs/Arquitectura y base/tradeoffs.md`.

## Timezone

Cualquier regla de fecha/hora "vigente" pasa por `internal/clock.Today()` fijado a `America/Argentina/Cordoba` (UTC-3), nunca `time.Now()` directo.

## Testing (gate real desde el día 1)

- Backend: tests contra Postgres real (no mocks), cada uno en su propia transacción revertida, `TEST_DATABASE_URL` debe terminar en `_test`.
- `go test ./internal/...` corre los paquetes en paralelo contra esa misma base de test, y cada paquete llama a `testdb.New(t)` → `db.RunMigrations` por su cuenta — por eso `RunMigrations` toma un `pg_advisory_xact_lock` antes de correr (serializa las llamadas concurrentes; ver el comentario grande en `apps/api/internal/db/migrate.go`). Sin ese lock, dos llamadas entrelazando los pasos de una migración cruda no atómica (`DROP CONSTRAINT` + `ADD CONSTRAINT`) pueden fallar con "ya existe" — bug real de CI, no hipotético. Cualquier SQL crudo nuevo que se agregue a esa función queda protegido por el mismo lock automáticamente.
- Frontend: Vitest + Testing Library + jsdom, todo mockeado a nivel `fetch`/Server Actions. El gate de cobertura excluye `src/app/**/page.tsx` (Server Components async, no testeables vía Testing Library/jsdom — quedan cubiertos por QA end-to-end manual, no por esta suite).
- **Gate: 80% de cobertura mínimo en ambos lados, activo desde Sprint 0** (a diferencia de Marcuzzi_Madryn, donde se agregó después — ver TR-007 en `docs/Arquitectura y base/tradeoffs.md`), CI falla si no se cumple.

## Auditoría de seguridad y optimización (línea de trabajo recurrente)

Desde el 2026-09-08, después de cerrar la Fase 2, el sistema entra en rondas periódicas de revisión técnica. **Antes de tocar `internal/http`, `internal/db` o `apps/web/src/lib/api.ts`, leer `docs/Seguridad y optimizacion/radiografia-tecnica_1.md`** — es el diagnóstico vigente y explica por qué varias cosas están como están.

- `docs/Seguridad y optimizacion/radiografia-tecnica_1.md` — el diagnóstico (primera radiografía, de ahí el `_1`), el plan de acción en Fases A/B/C, y el registro de cada ronda de arreglos.
- `docs/Seguridad y optimizacion/como-se-arreglo-cada-cosa.md` — el porqué de cada decisión y las alternativas descartadas.
- Decisiones de arquitectura: `docs/Arquitectura y base/tradeoffs.md` TR-121 a TR-132. Plan por fases: `implementation-plan.md` §12. Resumen: `dental-mirage-spec.md` §12.

**Fases A y B cerradas (2026-09-09).** Lo que hay que tener presente al escribir código nuevo:

- **`clientIP()` prefiere `CF-Connecting-IP`, y si no está, la última IP PÚBLICA de `X-Forwarded-For`** (TR-136, corrige TR-121). El "último valor" de TR-121 asumía un solo proxy delante y **nunca fue cierto**: Render pone Cloudflare delante de todos sus servicios y además tiene un router interno — medido, un request quedaba logueado con `ip=10.29.215.4`, una dirección privada. El logger escribe `ip_fuente` (`cf`/`xff`/`xff-interna`/`remote`) en cada request: si alguna vez hay que revisar la topología de proxies, **mirá ese campo en un deploy real, no deduzcas**.
- **Las comodidades que exponen datos van detrás de `Config.HerramientasDeDesarrolloHabilitadas()`** (TR-135): exige `DEV_TOOLS=true` **y** que `AppBaseURL` apunte a localhost. Si agregás una comodidad de desarrollo nueva (exponer un dato, saltear un control, sembrar datos), va detrás de esa puerta — **no** de `APP_ENV`, que vale `development` en Render a propósito, ni de "¿está configurado X proveedor?", que fue el error que dejó `ExponerCodigoVerificacion` prendido dependiendo de una variable no relacionada. `AutoVerifyEmail` es la excepción y sigue atada a Resend: no expone nada, es una decisión de producto (TR-051).
- **La IP que ve `clientIP()` la pone el BFF** (TR-134, Fase 3.1.1). El navegador nunca llama a la API directo, así que sin esto llegaría siempre la IP del proceso web — la misma para todos los visitantes, que dejaba al rate-limiting por IP y a los detectores de abuso del wizard contando a todo el mundo como una sola persona (borró turnos reales en QA). `apps/web/src/lib/api.ts` manda `X-Prisma-Client-IP` + `X-Prisma-Bff-Auth`, y el middleware `confiarEnIPDelBFF` (`internal/http/ip_del_visitante.go`) reescribe con eso el `X-Forwarded-For` **solo si el secreto coincide** — la API es pública, sin esa prueba cualquiera elegiría su IP. Requiere `BFF_SHARED_SECRET` con el MISMO valor en los dos servicios; vacío, todo se comporta como antes. **Para leer la IP usar siempre `clientIP(r)`** — no leer esas cabeceras a mano, el middleware las borra a propósito.
- **`decodeJSON(w, r, v)` acota el body a 1 MiB.** No leer `r.Body` por fuera de esa función.
- **Paginación opt-in en `/turnos` y `/pacientes`** (TR-122): `?limit=&offset=`, total en `X-Total-Count`. Sin `limit` el endpoint responde como siempre — el calendario depende de eso, necesita el rango de fechas completo. Del lado del panel, "Cargar más" (`components/panel/cargar-mas.tsx`, tamaños en `lib/paginacion.ts`).
- **Nunca loguear la query string** (TR-124): "Mis turnos" lleva DNI y mail del paciente ahí. Se loguea el patrón de ruta de chi, no la URL concreta.
- **Las migraciones de DATOS van en `aplicarUnaVez`** (`internal/db/migrate_una_vez.go`, TR-123), no en el bloque idempotente de `migrate.go`. `RunMigrations` reintenta ante deadlock (SQLSTATE 40P01).
- **`JWT_SECRET` no tiene nada que ver con JWT** (TR-125): acá no hay ningún JWT ni la librería. Es el nombre heredado de la env var que firma con HMAC el `state` de OAuth de Google; del lado de Go se llama `Config.OAuthStateSecret`. El proceso no arranca fuera de `development` si su valor resuelto es el de ejemplo del repo.

**Fase C — lo que ya está aplicado (2026-09-09):**

- **El esquema tiene foreign keys reales** (TR-131): 33 constraints. Dos cosas que hay que saber antes de tocar el modelo de datos:
  - **La columna que apunta a la clínica se llama `clinic_id`** en todo el esquema desde la Fase 3.2.1 (TR-137). Se llamaba `profesional_id` en 9 tablas y guardaba un `clinics.id` desde TR-037 — el renombre se hizo antes de agregar `turnos.atendido_por_user_id`, para que no convivieran dos columnas de nombre parecido y significado opuesto. Si ves `profesional_id` en un documento viejo, es el nombre anterior de `clinic_id`. **Las tablas legacy `profesionales` y `profesional_especialidades` ya no existen** (13 filas huérfanas borradas el 2026-09-13; este archivo afirmaba que estaban vacías y era falso), y con ellas se fue `cmd/migrate-usuarios`.
  - **`conflictos_paciente` no lleva foreign key a propósito** — es historial, sus referencias quedan colgadas cuando se resuelve un conflicto. Hay un test que lo protege; no "arreglarlo".
  - **Una ficha de paciente se borra SOLO con `borrarFichaPacienteConSusHijas`** (`paciente_verificado_publico.go`), nunca con un `Delete(&db.Paciente{})` suelto. `pacientes` tiene tres tablas hijas (`paciente_tutores`, `paciente_emails_alternativos`, `paciente_telefonos_alternativos`) con FK `NO ACTION`: cualquier fila viva rebota el DELETE con 23503 y tumba la transacción. Regresión real de QA (2026-09-12), ver el addendum de TR-131.
- **Una migración que borra datos va en `migracionesDestructivasPrevias/Posteriores`** (`internal/db/migrate_destructiva.go`, TR-132), nunca suelta en el loop de `statements`. Declara cómo contar su impacto; fuera de `development` no corre sin `DB_ALLOW_DESTRUCTIVE=true`. Si el AutoMigrate falla cuando ella no corrió antes (un check constraint del tag de GORM, por ejemplo), va en el grupo PREVIO.

**Fase C — lo que sigue pendiente,** y no tiene fecha: cada ítem tiene una condición de activación escrita (`implementation-plan.md` §12.3). La refactorización de `turno_publico.go`/`turnos.go`/`pedir-turno-form.tsx` quedó postergada a la próxima radiografía — no refactorizar eso "de paso" sin pedido explícito.

## Fase 3 — Multi-tenant (N profesionales / N clínicas)

Brief del cliente en `docs/Fases post MVP/Fase 3/Fase2-fix-Fase3-Multi-tenant.docx`; mockups en `docs/Fases post MVP/Fase 3/Mockups/`; plan en `docs/Arquitectura y base/implementation-plan.md` §13.

**Fase 3.1 — cambios al wizard público, cerrada el 2026-09-12 (TR-133).** Explicación larga en `docs/Fases post MVP/Fase 3/fase3.1-wizard-sacar-turno.md`; mecanismo en `docs/Fases post MVP/Fase 2/turnero_pagina/ArquitecturaPeticionesTurno.md` §1.4quater. Lo que cambia respecto a lo que dicen las secciones de Fase 2 más arriba:

- **La regla vigente es 1 turno activo por DNI Y TIPO DE CONSULTA**, no 1 por DNI en toda la clínica. TR-109 queda revertido: `turnoActivoPorDNI`/`turnoActivoDeOtroTipo` siguen en el código sin call sites (`//nolint:unused`), vale `turnoActivoDelMismoTipo`. Cualquier texto anterior que diga "tope universal de 1 turno activo por DNI" describe el estado viejo.
- **Relajar el tope no quitó protección:** la identidad la protege la detección de conflictos (mismo DNI + mail distinto → dos fichas + conflicto a resolver a mano), que el tope tapaba. No "reforzar" esto con un tope nuevo sin pedido explícito.
- **La prueba de mail se reemite heredando su vencimiento** (`consumirYReemitirVerificacionTurnoPublico`). Sigue siendo de un solo uso; lo que no hace es reiniciar los 30 minutos. Si tocás esto, la herencia del `ExpiresAt` es la parte que no se puede perder.
- **`pacienteReconocibleEnElWizard` ≠ `pacienteEstaVerificado`.** El primero (verificado **o** con turno activo) decide si aparece la tarjeta de "ya he venido antes". El segundo, más estricto, sigue rigiendo todo lo demás. No unificarlos.
- **`GET /clinicas/{slug}/mis-turnos` devuelve una LISTA**, y sigue dando 404 —no 200 con lista vacía— cuando ninguno matchea.
- **En "para otro / primera vez" el código de verificación sale al terminar los datos del TUTOR**, no después de los del paciente. No es cosmético: con el mail probado, el wizard decide si ofrecerle sus pacientes ya conocidos (`otro-tarjeta-paciente`) o pedirle los datos de uno nuevo (`otro-paciente`). **Esa lista nunca puede mostrarse antes del código** — diría qué pacientes tiene un tutor a cualquiera que tipee su mail.
- **La búsqueda de pacientes de un tutor es por MAIL, nunca por teléfono.** El código se manda al mail: es lo único que la persona demuestra tener. Sumar el teléfono al criterio dejaría ver los pacientes de un tutor ajeno verificando la propia dirección. Requiere verificación por SMS, hoy fuera de alcance.

**Fase 3.2 — multi-tenant, en curso desde 2026-09-13.** Documento vivo: `docs/Fases post MVP/Fase 3/fase3.2-multi-tenant.md`. Modelo de datos con los diagramas ER pre y post: `docs/Arquitectura y base/modelo de datos/`. Plan por subfases (3.2.1 a 3.2.8) en `implementation-plan.md` §13.2. Lo que hay que saber antes de tocar el modelo:

- **El historial de un paciente se ve ENTERO, con su dueño** (Fase 3.2.5): la ficha trae todos los turnos —el paciente es de la clínica— y cada uno informa `atendidoPorNombre` y `esMio`. Los ajenos van en solo lectura y sin link (el destino está acotado: no encontraría nada). No confundir con el aislamiento: una cosa es que un dato sea ajeno, y otra que una operación legítima —resolver un conflicto de identidad— tenga consecuencias sobre lo ajeno. Lo primero se corta; lo segundo se declara (el modal avisa cuántos turnos de otros alcanza).
- **El aislamiento lo verifica un test, no la memoria**: `TestAislamiento_NingunaConsultaDelPanelSinAcotar` lee los 14 archivos del panel y falla si una consulta filtra por clínica sin acotar por profesional. Si agregás una, acotala con un scope de `visibilidad.go` **o** sumala a `clinicaWide` en ese test con el motivo. Se rompió cuatro veces buscando por patrón en vez de por ruta; el estado medido hoy es 39 acotadas y 18 clínica-wide a propósito.
- **TODO lo de gestión de clínica es individual** (Fase 3.2.5, barrido del 2026-09-14): además de turnos y pacientes, van por scope los **conflictos de identidad** (`soloMisConflictos`, derivado del turno que los originó), los **tipos de consulta por id** (el listado ya lo hacía; la escritura no), las **tarjetas de General**, los **pendientes de asistencia** y el **enlace para compartir** (`enlaces_turno.user_id` — los turnos que entran por él van a quien lo generó, no al owner). Lo que queda clínica-wide a propósito: los bloqueos de mail/IP del formulario público y la unicidad de DNI.
- **La agenda es de CADA PROFESIONAL, no de la clínica** (Fase 3.2.5, corregido 2026-09-14): horario de atención y horarios reservados se filtran con `soloMiAgenda` (`internal/http/visibilidad.go`) y se crean con `user_id`. `calcularDisponibilidad` recibe el profesional además de la clínica, y filtra horarios, bloqueos **y turnos** por él — contarlos por clínica reintroducía en la pantalla el mismo bug que la 3.2.1 sacó del `EXCLUDE`. El índice `idx_horario_atencion_general_por_profesional` reemplaza al que imponía una fila general por clínica.
- **Un turno cargado desde el panel es de QUIEN LO CARGA, si atiende** (`profesionalQueAtiende`, corregido 2026-09-14). Hasta esa fecha era siempre el owner —un provisorio de la 3.2.1 que caducó en la 3.2.4 sin que nadie lo mirara— y el turno del colega, con su paciente, aparecía en la agenda del titular. El aislamiento no se rompe solo por una query mal filtrada: también por el dato que esas queries leen (`atendido_por_user_id`). Recepción sigue cayendo al owner hasta que la 3.2.6 traiga el selector.
- **`onboardingCompletado` se DERIVA (perfil + clínica activa), no sale de `onboarding_step`** (corregido 2026-09-14): ese paso solo se marca al crear una clínica propia, y desde la 3.2.3 eso dejó de ser obligatorio — un invitado quedaba rebotado para siempre. La columna sigue sirviendo para saber en qué paso retomar el wizard.
- **El aislamiento entre colegas vive en `soloMisTurnos` / `soloMisPacientes`** (`internal/http/visibilidad.go`, Fase 3.2.2, TR-138), no en cada handler: están aplicados en 6 queries de turnos y 3 de pacientes —contados el 2026-09-14, el número anterior describía la intención y no lo implementado—, y una fuga de aislamiento **no se nota mirando la pantalla** (los datos aparecen, solo que de más gente). Cualquier query nueva que liste turnos o pacientes del panel tiene que pasar por esos scopes. **Ve toda la clínica SOLO `recepcion`** (brief: "acceso a todas las vistas de los N profesionales"); `owner`, `admin` y `profesional` ven lo suyo — el titular es `owner`+`admin`+`profesional` y atiende pacientes como cualquier otro. **`admin` habilita solo la página pública** (`/personalizar-pagina`), nada de agendas. La ficha de un paciente ajeno da **404, no 403**.
- **La clínica activa se elige y vive en la SESIÓN** (`sessions.clinic_id`, Fase 3.2.3, TR-139). `membresiaDeLaSesion` (`internal/http/middleware.go`) la busca JUNTO con la membresía activa —si sacaron a la persona del equipo, la elección deja de valer sola— y cae a "la más antigua" si no eligió ninguna. `/me` devuelve la clínica **activa**, no la propia. El punto de partida de toda sesión es `/clinicas` (`apps/web/src/app/clinicas/`), no `/seleccionar-servicio`.
- **Cada tarjeta de "¿Qué necesitás hoy?" depende de un rol** (Fase 3.2.4): agenda → `profesional`/`recepcion`, página → `admin`, colaboradores → `owner`. **Y la pantalla verifica el rol, no solo la tarjeta**: `/personalizar-pagina` redirige a quien no es `admin`. Esconder el botón nunca fue cerrar la puerta. Los roles completos vienen en `me.clinica.roles` (el viejo `me.clinica.rol` es solo el de mayor alcance, para etiquetar).
- **`admin` es "administrador de PÁGINA", no de la clínica** — habilita `/personalizar-pagina` y nada más. Es invitable y delegable desde Colaboradores (Fase 3.2.4); `PUT /equipo/miembros/{userId}/roles` recibe el juego COMPLETO de roles, no un agregado, y `owner` no se puede asignar por ahí.
- **La matrícula es ÚNICA en todo el sistema** (`idx_matricula_unica`, TR-141): índice único **parcial** sobre `(matricula_tipo, matricula_numero)`, con `WHERE matricula_numero <> ''` porque los perfiles `actividades` la guardan vacía y todas esas cadenas vacías chocarían entre sí. El tipo va en la clave porque `nacional 1234` y `provincial 1234` son registros distintos. Los dos caminos de escritura del perfil (`PATCH /onboarding/perfil` y `PATCH /me`) traducen el 23505 a **409**, no a 500 — con `esMatriculaDuplicada`, que mira el nombre de la constraint y no el texto del error. **Limitación escrita a propósito:** una matrícula provincial es única por provincia y el perfil no guarda cuál; se acepta mientras el producto sea de Córdoba. Los fixtures de test derivan la matrícula del mail (`matriculaDePrueba`) — una constante hace fallar a cualquier test que arme dos personas.
- **Los campos de formulario usan `border border-linea bg-hueso`** (`--color-linea`, #dbd3c2), no `border-[0.5px] border-arena bg-marfil`: a medio píxel y tres puntos de luminosidad, el borde desaparecía sobre el marfil de un modal. Un campo tiene que leerse como un hueco donde escribir.
- **El header vive en el layout RAÍZ: no se re-renderiza al navegar.** Cualquier cosa del header que dependa de la ruta (el topbar de `/panel`, Fase 3.2.5) tiene que resolverse en el CLIENTE con `usePathname` y pedir sus datos por Server Action — ver `components/panel/panel-topbar.tsx`. Hacerlo en un Server Component del layout funciona solo con F5 parado en la ruta.
- **Cuál es la clínica activa lo dice `/me`, no el flag `activa` de `/me/clinicas`** (Fase 3.2.5): ese flag vale `true` solo si la sesión la eligió a mano (`sessions.clinic_id`), y quien entró por el fallback de "la más antigua" tiene todas en `false`. Si una pantalla necesita saber en qué clínica está parada, sale de `/me`.
- **La presencia de colaboradores sale de `sessions`, no de un socket** (Fase 3.2.5, TR-142): `last_seen_at` + `clinic_id` + no revocada + no vencida. `GET /equipo/presencia` es **el latido Y la lectura**: refresca el último latido de quien pregunta antes de responder, así que no hay endpoint de "sigo acá". El umbral (5 min) y el intervalo (60 s) los sirve el backend en la respuesta — no los dupliques como constantes del frontend. Si agregás algo de tiempo real, este es el patrón: estado en Postgres, no en memoria del proceso, porque es lo que deja escalar a N instancias.
- **Un tipo de consulta es de UN profesional** (Fase 3.2.5): `GET /tipos-consulta` devuelve los tuyos (`user_id = vos`, más los de `user_id` nulo, anteriores a la 3.2.1); los de los colegas están en `/tipos-consulta/de-colegas`, y se ofrecen como **punto de partida dentro del modal de alta** ("Tipos de consulta ya creados"): elegir uno rellena nombre y color, y el tipo se crea por el alta de siempre con los tiempos que configure la persona. Nunca compartas la fila: duración y preferencia horaria son configuración de agenda, y cambiarla le movería los huecos del día a otro. Al crear uno, ponele `user_id`.
- **Crear una clínica `organizacion` termina en `/colaboradores`**, no en `/seleccionar-servicio` (`individual` sigue yendo ahí). Esa pantalla es entonces un punto de llegada, no solo un desvío: tiene al final un botón "Ir al panel de gestión" que vuelve a `/seleccionar-servicio` (no a `/panel`, y por eso sin candado por rol — esa pantalla ya filtra las tarjetas sola).
- **Una invitación se dirige a un MAIL, no a un usuario** (`clinic_invitations`, Fase 3.2.4, TR-140): por eso se puede invitar a alguien sin cuenta, y por eso las invitaciones se buscan por `email` y no por `user_id`. **Las dos formas de invitar —código de perfil y mail— quedan pendientes de confirmar**: la membresía recién nace cuando la persona acepta desde `/clinicas`. No hay link de aceptación de un clic, a propósito. Aceptar una invitación de `profesional` exige matrícula, igual que crear la clínica propia o entrar a atender.
- **No todo el que entra a la app atiende pacientes** (Fase 3.2.3, TR-139). `professional_profiles.tipo_perfil` es `profesional` o `actividades` (recepción / administración de la página); con `actividades` **no hay matrícula ni especialidades**, y el backend las descarta si llegan. Default `profesional` cuando el campo no viene. **Crear la clínica propia exige `profesional`, y entrar a una clínica con rol de `profesional` también** — el frontend pide los datos que faltan antes, en un modal encadenado, y los dos caminos tienen su guard en el backend. Crear una clínica exige además provincia, ciudad, dirección y teléfono: son los datos de la página pública y del buscador.
- **El onboarding es UN paso: el perfil** (Fase 3.2.3). Crear la clínica dejó de ser obligatorio —se entra a la app también porque un colega te sumó a la suya— y pasó a ser una acción de `/clinicas`. Crear la propia ya no exige estar en el paso `clinica` del wizard; lo que se rechaza es tener dos (**409**, no 403).
- **Una ficha de paciente cargada a mano guarda `creado_por_user_id`**, y `soloMisPacientes` la incluye por eso: sin esa columna, un profesional cargaba una ficha con "+ Agregar paciente" y desaparecía de su listado hasta tener el primer turno. No lo vuelve dueño del paciente (siguen siendo de la clínica).
- **`requireClinic` admite cualquier membresía ACTIVA, no solo al dueño** (Fase 3.2.2). Exigía `owner`, y eso dejaba a cualquier colaborador invitado con 403 en todo el panel. Deja en el contexto la clínica **y los roles**; con varias clínicas toma la más antigua hasta que la 3.2.3 traiga la elección explícita. Para exigir un rol en una ruta: `requireRol(db.RoleAdmin)` encadenado después. Para preguntar desde un handler: `tieneAlgunRol(r, ...)`.
- **El titular arranca con `owner` + `admin` + `profesional`**, como pide el brief. `owner` no es un nivel más alto: es lo que habilita a invitar y repartir roles. Si agregás una ruta que exija `admin`, acordate de que un profesional invitado NO lo tiene.
- **Los roles de un miembro viven en `clinic_member_roles`, no en una columna** (desde la Fase 3.2.1). Son acumulables, y la exclusión `profesional`/`recepcion` la impone un **índice único parcial**, no la aplicación. Para filtrar por rol usar el scope `db.ConRol(...)`; para mostrar uno solo, `db.RolPrincipal(...)`. Asignar con `db.AsignarRol` (idempotente). **La membresía no se borra nunca**: se marca `status='removed'`, porque la FK compuesta de `turnos` bloquearía la baja de cualquier profesional con historial.
- **Los pacientes son de la CLÍNICA; la configuración de agenda es del PROFESIONAL.** Una ficha por persona aunque la atiendan dos odontólogos ("los pacientes de Lucía" se deriva de sus turnos); tipos de consulta, horario de atención y bloqueos pasan a colgar del profesional.
- **El `EXCLUDE` de no-solapamiento hay que mudarlo a `atendido_por_user_id`.** Hoy es sobre `profesional_id` (= la clínica), así que con N profesionales rechazaría dos turnos simultáneos en sillones distintos: pasa de garantía a bug.
- **Los tipos de consulta se comparten como sugerencia, no como fila común**: incluir el de un colega COPIA la fila, porque lleva duración/color/preferencias que cada uno ajusta.

## Flujo de ramas

Mismo criterio que Marcuzzi_Madryn: `main` (prod) ← solo merge cuando el usuario lo pide explícitamente ("mergeá") · `dev` (integración, push libre) ← `feature/`/`fix/` para trabajo grande, cambios chicos van directo a `dev`. Merge a `main` siempre vía `git merge --ff-only`.

**Fase 2 — proceso de QA por ítem (TR-083 en `docs/Arquitectura y base/tradeoffs.md`):** pedido explícito del cliente en `docs/Fases post MVP/Fase 2/fase2-dental-mirage.md` — implementar los 5 ítems uno por uno, cada uno en su propia rama `feature/fase2-NN-descripcion` (no una sola rama larga para toda la fase). **Nunca hacer commit ni push de un ítem hasta que el cliente apruebe su QA** — a diferencia del resto del proyecto, donde push a `dev` es libre. Una vez aprobado un ítem, commit a su rama y PR a `dev` (no push directo). Este proceso aplica solo mientras dure la Fase 2, no cambia el flujo general de arriba para el resto del trabajo.
