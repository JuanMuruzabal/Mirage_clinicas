## TR-001: Tipos de consulta como catálogo fijo por profesional, no tags libres *(reconstruida)*

- **Fecha:** anterior a Sprint 1 (fecha exacta no recuperada)
- **Fase:** plan — responde spec §7, pregunta 1 ("¿Cuáles son los tipos de consulta reales a soportar en el MVP?")
- **Decisión:** `tipo_consulta` es un catálogo **por profesional** (no global, a diferencia de `especialidad` — ver TR-004), sembrado automáticamente al registrarse con dos valores fijos: "Consulta general" y "Urgencia", cada uno con un color asociado (los tokens `cascarón`/`urgencia` del Sistema Cascarón, TR-010). El profesional elige entre estos al crear un turno — no es un campo de texto libre.
- **Alternativas consideradas** *(reconstruida)*: (a) catálogo global compartido por todos los profesionales — descartada, cada clínica maneja categorías propias de facto; (b) campo de texto libre sin catálogo — descartada, rompe la diferenciación de color por tipo en el calendario, que es un requisito explícito de la spec.
- **Por qué** *(reconstruida)*: la spec pedía "al menos un segundo tipo de consulta" para poder probar la diferenciación de color del calendario de verdad — sembrar dos valores concretos (no dejarlo vacío) resuelve la pregunta abierta sin esperar una respuesta del cliente que hubiera bloqueado Sprint 2.
- **Qué se sacrifica:** el profesional no puede crear tipos de consulta propios en el MVP — vive fijo con "Consulta general"/"Urgencia" hasta que se confirme la lista real (spec §7, pregunta 1 seguía abierta).
- **Reversibilidad:** Alta — es agregar un CRUD sobre una tabla que ya existe, sin cambios de modelo.

## TR-002: Validaciones de DNI/teléfono/mail en el formulario público *(reconstruida)*

- **Fecha:** anterior a Sprint 1 (fecha exacta no recuperada)
- **Fase:** plan — responde spec §7, pregunta 2 ("¿hay reglas de formato/obligatoriedad ya definidas?")
- **Decisión:** reglas concretas asumidas ante la falta de definición: DNI numérico de 7-8 dígitos (`^\d{7,8}$`), teléfono argentino de 10-13 dígitos con un "+" líder opcional (`^\+?\d{10,13}$`), email con el patrón estándar `^[^\s@]+@[^\s@]+\.[^\s@]+$`. Aplicadas en dos capas — `internal/http/turno_publico.go` (backend, fuente de verdad) y replicadas en el frontend (`PedirTurnoForm`, `EditarPacienteModal`) para feedback inmediato antes de tocar la red.
- **Alternativas consideradas** *(reconstruida)*: (a) sin validación de formato, solo obligatoriedad — descartada, un DNI o teléfono con formato inválido llega igual al panel del profesional y ensucia su lista de pacientes; (b) validación asíncrona contra un servicio externo (RENAPER, etc.) — descartada por alcance, fuera de lo que pide el MVP.
- **Por qué** *(reconstruida)*: son las reglas mínimas necesarias para que el turno pendiente que llega desde la página pública tenga datos de contacto utilizables — sin esto, el profesional podría recibir un DNI con letras o un teléfono sin dígitos suficientes para reconocer al paciente.
- **Qué se sacrifica:** son reglas asumidas, no confirmadas por el cliente — si el DNI real necesita otro formato (extranjeros, por ejemplo) esto habría que revisarlo.
- **Reversibilidad:** Alta — son dos regex en un único lugar de cada lado (`turno_publico.go` y `pedir-turno-form.tsx`), fáciles de ajustar.

## TR-003: Envío del formulario público vía link `wa.me`, no WhatsApp Business API *(reconstruida)*

- **Fecha:** anterior a Sprint 1 (fecha exacta no recuperada)
- **Fase:** plan — responde spec §7, pregunta 3 ("¿es un link `wa.me` con mensaje prellenado, o una integración con API de WhatsApp Business?")
- **Decisión:** al confirmar el formulario público de pedir turno, el frontend arma un link `https://wa.me/{numero}?text={mensaje prellenado}` client-side con los datos que el propio profesional publicó (su teléfono) — en paralelo, el backend ya creó el `turno` en estado `pendiente` de forma independiente. No hay integración con la API de WhatsApp Business: ningún envío/confirmación de entrega real, es un link que abre WhatsApp (web o app) del lado del visitante. `CLAUDE.md` es explícito: este camino **no** usa el patrón de interfaz dev/prod reservado para integraciones de backend — ese patrón queda para recordatorios automatizados futuros (Fase 2).
- **Alternativas consideradas** *(reconstruida)*: (a) integración real con WhatsApp Business API — descartada por alcance/costo (requiere cuenta de negocio verificada, aprobación de Meta, y una interfaz dev/prod de verdad); (b) no ofrecer WhatsApp en el MVP, solo el turno pendiente en el panel — descartada, la spec pide explícitamente que el paciente pueda "además" escribirle directo al profesional.
- **Por qué** *(reconstruida)*: `wa.me` no requiere backend, credenciales, ni aprobación de terceros — el turno pendiente en el panel es la fuente de verdad real (no depende de que el link se abra con éxito), el WhatsApp es una comodidad extra para el paciente.
- **Qué se sacrifica:** sin confirmación de entrega ni reintento — si el visitante no tiene WhatsApp instalado/accesible, el link simplemente no hace nada útil (mitigado: el turno pendiente ya existe en el panel de todos modos, ver riesgo R4 de `implementation-plan.md`).
- **Reversibilidad:** Media — migrar a la API real de WhatsApp Business es un cambio de arquitectura (backend, credenciales, interfaz dev/prod), no un ajuste menor.

## TR-004: Especialidades como catálogo cerrado predefinido por Mirage, no tags libres *(reconstruida)*

- **Fecha:** anterior a Sprint 1 (fecha exacta no recuperada)
- **Fase:** plan — responde spec §7, pregunta 4 ("¿es una lista cerrada predefinida por Mirage, o el profesional puede crear tags libres?")
- **Decisión:** `especialidad` es un catálogo **global** (a diferencia de `tipo_consulta`, por profesional — TR-001), predefinido y sembrado por Mirage (`internal/db.SeedEspecialidadesCatalogo`, `CatalogoEspecialidades` en `seed.go`). El profesional elige de esta lista cerrada al registrarse (`especialidadIds` en el wizard de alta) — no puede crear especialidades propias. Tabla puente `profesional_especialidad` (N:M).
- **Alternativas consideradas** *(reconstruida)*: (a) tags libres por profesional — descartada, rompe la utilidad del filtro por especialidad en el buscador público (spec §6) si cada profesional escribe la suya con su propia ortografía/criterio; (b) catálogo cerrado pero editable solo por un admin de Mirage vía panel propio — de hecho es lo implementado, sin un panel de admin todavía (se edita el seed directo).
- **Por qué** *(reconstruida)*: un catálogo cerrado es lo único que permite que el filtro de especialidad del buscador (spec §6) funcione de verdad — "Ortodoncia" tiene que significar lo mismo para todos los profesionales que la eligen.
- **Qué se sacrifica:** un profesional con una especialidad realmente fuera del catálogo no tiene forma de registrarla — depende de que Mirage la sume al seed.
- **Reversibilidad:** Media — sumar especialidades nuevas al catálogo es trivial (una fila más en `CatalogoEspecialidades`); pasar a tags libres sería un cambio de modelo más profundo (perder la tabla puente cerrada).

## TR-005: Autenticación email+password propia (JWT), sin login social en el MVP *(reconstruida)*

- **Fecha:** anterior a Sprint 1 (fecha exacta no recuperada)
- **Fase:** plan — responde spec §7, pregunta 5 ("no se especifica el mecanismo de login/registro")
- **Decisión:** autenticación propia con email+password (`internal/http/auth.go`), password hasheado con bcrypt, JWT de sesión (7 días, mismo TTL en `apps/api` y en la cookie de `apps/web`) en cookie `httpOnly` (spec §9.3) — nunca en `localStorage`. Sin OAuth/login social (Google, etc.) en el MVP.
- **Alternativas consideradas** *(reconstruida)*: (a) login social (Google) — descartada del MVP por alcance/tiempo, aunque queda como backlog explícito de Fase 2 si el cliente confirma que hace falta; (b) sesiones de servidor con almacenamiento en base en vez de JWT — descartada, JWT es el mismo patrón ya validado en Marcuzzi_Madryn.
- **Por qué** *(reconstruida)*: email+password es el mecanismo mínimo funcional sin depender de configurar credenciales OAuth de terceros antes de poder probar el resto del producto — reduce superficie de configuración en Sprint 0.
- **Qué se sacrifica:** sin "iniciar sesión con Google", cada profesional necesita recordar una contraseña más — aceptado como backlog de Fase 2 (ver `docs/implementation-plan.md` sección 6).
- **Reversibilidad:** Media — sumar OAuth es aditivo (no reemplaza el mecanismo actual), pero toca `auth.go`, el modelo de `Profesional` y el flujo de `/ingresar`/`/sumarse`.

## TR-006: El exclusion constraint de turnos aplica solo a `estado='agendado'` *(reconstruida)*

- **Fecha:** anterior a Sprint 1 (fecha exacta no recuperada)
- **Fase:** plan
- **Decisión:** el `EXCLUDE USING gist` sobre `(profesional_id, rango_horario)` en la tabla `turno` (el requisito no negociable de spec §4.3: turnos sin solapamiento) solo es válido para filas en estado `agendado`. Los turnos `pendiente` —recién llegados del formulario público, sin horario todavía— no tienen `rango_horario` fijo (columna nullable), así que no participan del constraint hasta que se confirman en el modal "+ Agregar turno" (T2.4) y pasan a `agendado`.
- **Alternativas consideradas** *(reconstruida)*: (a) exigir un horario tentativo desde que el turno es `pendiente` — descartada, el paciente no elige horario en el formulario público (spec §4.4), solo pide turno; inventar uno arbitrario para satisfacer el constraint sería un dato falso; (b) constraint separado por estado, permitiendo solapamiento entre `pendiente`s — es la opción elegida, ya que dos pedidos pendientes en el mismo rango no son un problema real hasta que alguno se confirma.
- **Por qué** *(reconstruida)*: el constraint tiene que reflejar la garantía real del negocio — "dos turnos *confirmados* de un mismo profesional no se solapan" — no "dos *pedidos* no se solapan", que no tiene sentido antes de que exista un horario de verdad.
- **Qué se sacrifica:** nada de fondo — es la lectura correcta del propio modelo de datos, no una concesión.
- **Reversibilidad:** Baja/Media — es un constraint a nivel de base de datos (migración), tocarlo requiere una migración nueva, no solo un cambio de código de aplicación.

## TR-007: Gate de coverage 80% activo desde Sprint 0, no como iniciativa tardía *(reconstruida)*

- **Fecha:** anterior a Sprint 1 (fecha exacta no recuperada)
- **Fase:** plan — lección aplicada de la experiencia de Marcuzzi_Madryn (mismo stack/modo de trabajo, spec §9), donde este gate se agregó recién al final del proyecto
- **Decisión:** CI (`.github/workflows/ci.yml`) falla si la cobertura de cualquiera de los dos stacks cae debajo del 80%, activo desde el primer PR de código de negocio (T0.4) — no un retrofit al final. Backend: tests contra Postgres real (`internal/testdb`), nunca mocks, cada test en su propia transacción revertida, con una red de seguridad (`requireTestDatabaseName`) que impide correr la suite contra una base que no termine en `_test`. Frontend: Vitest + Testing Library + jsdom, con `fetch`/Server Actions siempre mockeados, y las páginas Server Component (`src/app/**/page.tsx`) excluidas del cálculo de cobertura — se verifican mejor con QA end-to-end (T5.4) que con unit tests.
- **Alternativas consideradas** *(reconstruida)*: (a) agregar el gate más adelante, cuando el producto esté más maduro (lo que pasó en Marcuzzi_Madryn) — descartada explícitamente, es la lección que este proyecto dice no repetir; (b) mockear la capa de datos del backend en vez de una base real — descartada, el exclusion constraint (TR-006) no se puede probar con sentido contra un mock.
- **Por qué:** un gate agregado tarde encuentra código ya escrito sin tests, mucho más caro de cubrir retroactivamente que de mantener alto desde el día 1.
- **Qué se sacrifica:** cada sprint corre más lento al principio (hay que escribir tests junto con cada feature, no después) — aceptado a cambio de nunca acumular deuda de cobertura.
- **Reversibilidad:** Alta — es un umbral en configuración de CI/Vitest, bajarlo o subirlo es un cambio de una línea (aunque bajarlo sería ir contra la lección que motivó la decisión).

## TR-008: Sin CAPTCHA/Turnstile en el formulario público del MVP *(reconstruida)*

- **Fecha:** anterior a Sprint 1 (fecha exacta no recuperada)
- **Fase:** plan
- **Decisión:** el formulario público de pedir turno (T3.1) no tiene CAPTCHA ni Cloudflare Turnstile ni ningún anti-spam en el MVP — riesgo aceptado y registrado explícitamente como R3 en `docs/implementation-plan.md`.
- **Alternativas consideradas** *(reconstruida)*: (a) sumar Turnstile desde el día 1 — descartada por alcance, es una dependencia externa más para un riesgo todavía no confirmado como real; (b) rate-limiting por IP sin CAPTCHA visual — quedó fuera también, mismo criterio de alcance.
- **Por qué** *(reconstruida)*: agregar protección anti-spam antes de saber si el spam es un problema real es trabajo especulativo — el MVP prioriza validar el flujo completo primero.
- **Qué se sacrifica:** el formulario puede recibir `turno`s pendientes falsos que ensucian el panel del profesional — mitigado parcialmente porque la vista Turnos (T3.3) permite cancelar en lote, y queda como backlog explícito sumar `turnstile.Verifier` con el mismo patrón dev/prod de spec §9.4 en cuanto se confirme que es un problema real.
- **Reversibilidad:** Alta — sumar Turnstile más adelante es aditivo, no requiere deshacer nada.

## TR-009: La opción "organización" se omite del flujo de onboarding, no se muestra deshabilitada *(reconstruida)*

- **Fecha:** anterior a Sprint 1 (fecha exacta no recuperada)
- **Fase:** plan — el MVP es solo alta de profesional individual (spec §2), sin cuentas de organización multi-profesional
- **Decisión:** el wizard de alta (`SumarseWizard`) arranca directo en el camino "particular" — la opción "organización" que pudiera sugerir el brief original **se omite por completo** del flujo, no aparece como una opción deshabilitada/"próximamente".
- **Alternativas consideradas** *(reconstruida)*: (a) mostrarla deshabilitada con un tooltip "próximamente" — descartada, generar expectativa sobre algo que no está en el MVP (y es explícitamente Fase 2 en `CLAUDE.md`) es peor que no mostrarla; (b) omitirla del todo — la elegida.
- **Por qué** *(reconstruida)*: mostrar una opción que no funciona invita a que un visitante la pruebe y se encuentre con un camino muerto — omitirla es más honesto que simular que existe.
- **Qué se sacrifica:** nada de funcionalidad real (organizaciones no están construidas); sí se sacrifica la oportunidad de "avisar" desde ya que viene en el futuro, si eso fuera valioso comercialmente.
- **Reversibilidad:** Alta — sumar el camino "organización" al wizard es aditivo cuando exista esa feature (Fase 2), no hay que deshacer nada de este MVP.

## TR-010: Identidad visual — Sistema Cascarón (paleta + tipografía) *(reconstruida)*

- **Fecha:** anterior a Sprint 1 (fecha exacta no recuperada) — adelantado a la fase de planificación (T5.1 originalmente en Sprint 5)
- **Fase:** plan — spec §9.7: "robar el lenguaje estructural de bungie.net... traducido a un tono de confianza clínica", vía `/frontend-design`
- **Decisión:** paleta de 6 tokens — `ink` (texto/fondo oscuro), `porcelain` (superficie clara), `panel` (blanco puro), `steel` (acento), `line`/`line-strong` (bordes), `muted` (texto secundario) — más `cascarón`/`urgencia` como semánticos reservados exclusivamente al bloque de `tipo_consulta` del calendario (nunca reutilizados para otra cosa). Tipografía: Big Shoulders (display condensada de alto contraste, uso restringido a títulos/cifras/rótulos), Public Sans (cuerpo), IBM Plex Mono (utilitaria — DNI, teléfono, horarios, cifras tabulares). Elemento firma: `QuadrantMark`, una grilla 2×2 de borde duro que replica la estructura de un odontograma real — con variante que encodea el estado de un turno en tablas (1 cuadrante lleno = pendiente, 4 llenos = agendado, tachado diagonal = cancelada).
- **Alternativas consideradas** *(reconstruida)*: no quedó registro de las alternativas de paleta/tipografía descartadas en el pase de diseño original — es la única entrada de este bloque donde la reconstrucción no puede ofrecer ni siquiera una aproximación razonable de qué otras opciones se pesaron.
- **Por qué** *(reconstruida)*: adelantar T5.1 a la fase de planificación (en vez de esperar a Sprint 5) permitió que Sprint 1 arrancara con tokens reales en vez de placeholders — evitó tener que re-skinnear pantallas ya construidas más adelante.
- **Qué se sacrifica:** un look estructural/condensado que se aleja del "cálido" que después pidió el cliente para el panel de gestión — resuelto en TR-013, no reemplazando esta identidad sino sumando una segunda paleta coexistente acotada a `/panel/**`.
- **Reversibilidad:** Alta — tokens centralizados en `globals.css`, `QuadrantMark` es un componente único reusado en todos lados.

## TR-011: Catálogo de especialidades visible acotado a "Odontología general" *(reconstruida)*

- **Fecha:** 2026-08-22 (confirmada por comentario de código en `internal/db/seed.go`)
- **Fase:** ejecución
- **Decisión:** aunque el catálogo cerrado completo (TR-004, `CatalogoEspecialidades`) sigue sembrado entero, `GET /especialidades` (y por lo tanto el wizard de alta y el filtro del buscador) solo expone hoy el subconjunto `EspecialidadesVisibles` — que es únicamente "Odontología general" — vía el flag `Especialidad.Activa`. El resto del catálogo queda sembrado pero oculto hasta que el cliente confirme la lista completa de especialidades reales a soportar.
- **Alternativas consideradas** *(reconstruida)*: (a) mostrar el catálogo completo asumido desde el día 1 — descartada, exponer especialidades no confirmadas por el cliente como si fueran definitivas genera expectativa sobre una lista que puede cambiar; (b) no sembrar nada hasta la confirmación — descartada, sin al menos una especialidad real no se puede probar el flujo de alta ni el filtro del buscador de punta a punta.
- **Por qué** *(reconstruida)*: separa "qué existe en la base" (todo el catálogo, listo para activarse) de "qué ve un usuario hoy" (solo lo confirmado) — activar el resto cuando el cliente responda es cambiar un flag, no re-sembrar ni migrar nada.
- **Qué se sacrifica:** el wizard de alta y el buscador público solo ofrecen una especialidad real por ahora — aceptado como estado transitorio, no el estado final del catálogo.
- **Reversibilidad:** Alta — activar el resto del catálogo es poner `Activa = true` en las filas correspondientes, sin migración.

## TR-012: Buscador público de clínicas adelantado a Sprint 1, sin el filtro de deploy todavía *(cerrada en Sprint 4/T4.5 — ver también el bloque de decisiones de Sprint 4 en `docs/implementation-plan.md`)*

- **Fecha:** 2026-08-22 (adelanto) — filtro cerrado 2026-08-23 (T4.5)
- **Fase:** ejecución
- **Decisión:** `GET /clinicas` (buscador por nombre de clínica/profesional/especialidad, spec §6, FR-10) y `/buscar` se adelantaron desde Sprint 4 a Sprint 1 a pedido directo del cliente (2026-08-22) — con una simplificación documentada en su momento: al no existir todavía el flujo de deploy de la página pública (T4.2), esa primera versión buscaba entre TODOS los profesionales registrados, no solo los que tuvieran `deployada_en` no nulo como pide la spec §5.2 ("para que el buscador no muestre páginas vacías o incompletas"). El filtro real (`JOIN paginas_publicas ... AND deployada_en IS NOT NULL` en `buscarClinicasHandler`) se sumó recién al cerrar T4.5 en Sprint 4 (2026-08-23) — ver ese mismo día en `docs/implementation-plan.md`.
- **Alternativas consideradas** *(reconstruida)*: (a) esperar a Sprint 4 completo (con el toggle de deploy ya armado) para recién ahí construir el buscador — descartada, el cliente pidió explícitamente adelantarlo; (b) adelantar el buscador pero bloquearlo por completo hasta que existiera el filtro — descartada, un buscador vacío no sirve para validar el flujo de búsqueda de punta a punta durante 3 sprints.
- **Por qué** *(reconstruida)*: adelantar la funcionalidad real (búsqueda contra la base de verdad) sin esperar a una feature secundaria (el toggle de deploy) permitió empezar a probar el buscador mucho antes, aceptando temporalmente que toda clínica registrada apareciera.
- **Qué se sacrifica:** entre Sprint 1 y el cierre de T4.5, cualquier clínica recién registrada (incluso sin haber tocado su página pública ni una vez) aparecía en el buscador — riesgo aceptado y ya cerrado.
- **Reversibilidad:** Alta — el filtro ya está cerrado (T4.5); revertirlo sería sacar una cláusula `JOIN`.

## TR-013: Restyle cálido del panel de gestión — segunda piel de color, sobre el mismo Sistema Cascarón (TR-010)
- **Fecha:** 2026-08-23
- **Fase:** ejecución (pedido explícito del cliente, antes de arrancar Sprint 4: "restylear el frontend ya implementado de la app de gestión... para que se vea más cálido, más suave y menos monocromático — sin tocar layout, estructura, componentes ni copys")
- **Decisión:** Paleta nueva de 10 tokens agregada a `apps/web/src/app/globals.css` (`@theme`), **coexistiendo** con los tokens del Sistema Cascarón (TR-010) en vez de reemplazarlos — la home pública/marketing, el onboarding (`/sumarse`, `/ingresar`, `/seleccionar-servicio`, `/perfil`) y el hero conservan ink/porcelain/steel/line tal cual, sin tocar un solo archivo de esas rutas:
  - `hueso` #F6F2EA (fondo de página del panel), `marfil` #FFFDF9 (superficie de cards/sidebar/topbar), `grafito` #35312B (texto principal, reemplaza ink solo dentro de /panel), `arena` #E7DFD1 (bordes 0.5px, reemplaza los bordes duros de 1-2px).
  - `salvia` #6E8F72 (acento principal) y `terracota` #C97F5A (acento cálido) llegan cada uno con una variante `-claro` (fondo pastel) y `-oscuro` (texto/relleno sólido) — **el tono medio nunca se usa como texto ni como relleno con texto encima**: contra blanco/marfil da ~3.1–3.6:1, por debajo del 4.5:1 de AA para texto normal (verificado a mano con la fórmula de contraste WCAG). `-oscuro` sobre `-claro` da ~6.6–6.8:1; `-oscuro` como relleno sólido con texto marfil encima da ~6.6–7.6:1. El tono medio queda para bordes, puntos/indicadores decorativos y hovers de borde — nunca portando texto.
  - Radius nuevo vía `@theme`: `--radius-card` (18px, cards/contenedores/modales) y `--radius-field` (12px, inputs/selects); botones/chips/badges/avatares usan el `rounded-full` nativo de Tailwind.
  - `--shadow-soft` (sombra difusa de dos capas, sin bordes duros) reemplaza los bordes de 1-2px negros de TR-010 dentro del panel.
  - Textura de fondo: `public/textures/soft-cross.svg` (tile de 52×52px, cruces suaves, opacidad 0.065–0.08) aplicada solo vía la clase `.panel-texture` en `app/panel/layout.tsx` — el único punto de montaje de las cuatro pantallas de gestión (General/Calendario/Turnos/Pacientes), nunca dentro de una card.
  - Chips de tipo de consulta: en vez de tocar el hex sembrado en `apps/api` (TR-001, `ColorTipoConsultaGeneral`/`ColorTipoConsultaUrgencia`, todavía cascarón/urgencia), `lib/turno-format.ts` suma `temaTipoConsulta()` — un resolver **solo de apps/web** que mapea por nombre ("Consulta general" → tema salvia, cualquier otro → tema terracota) y devuelve `{fondo, texto, acento}`. ## TR-016: Editor de página (T4.1/T4.2) — `PaginaPublica` se crea perezosa, y "previsualizar" no depende de "deployar"

- **Fecha:** 2026-08-23
- **Fase:** ejecución (Sprint 4, spec §5)
- **Decisión:**
  - `PaginaPublica` (1:1 con `Profesional`, la tabla existe desde T0.3) no se crea al registrarse — se crea con get-or-create la primera vez que hace falta (`GET/PATCH /panel/pagina/*`, `internal/http/pagina_publica.go`). Sin fila todavía, la página pública se comporta como "no oculta" (el default de la columna) — no hace falta que el profesional haya abierto el editor ni una sola vez para que su `/{slug}` funcione.
  - `GET /clinicas/{slug}` (la URL propia de la clínica) nunca se bloquea por falta de deploy, solo por `oculta` — "Ver página" desde la barra del editor tiene que poder previsualizar la página tal cual antes del primer deploy. Lo único gateado por `deployada_en IS NOT NULL` es el buscador público (`GET /clinicas`, T4.5, `buscarClinicasHandler` vía `JOIN paginas_publicas`).
  - "Deployar" es de una sola dirección — el backend es idempotente (llamarlo de nuevo no pisa la fecha original) y no existe un endpoint para "des-deployar". "Ocultar" es independiente y sí reversible en cualquier dirección: no afecta `deployada_en`, así que ocultar una página ya deployada no la saca del buscador (aparece igual, pero un visitante que entre ve mantenimiento) — son dos preguntas distintas ("¿está publicada?" vs. "¿se puede ver ahora?").
  - `ClinicaPublicaTemplate` es un único componente para dos consumidores: la página pública real (`/[slug]`) y la previsualización en vivo del editor (`/personalizar-pagina`, ver TR-017) — así la previsualización nunca puede desincronizarse de lo que ve un visitante real, no hay dos plantillas que mantener en paralelo.
  - "Guardar cambios" (barra de acciones) y todos los campos del panel de edición (T4.1) están deshabilitados a propósito, sin backend detrás — muestran de solo lectura los datos que ya existen en "Tu perfil" (nombre de clínica, teléfono, especialidades) más un placeholder fijo de "Sobre nosotros". La personalización real de contenido/diseño es trabajo posterior explícito (spec §5.1: "queda para desarrollo posterior") y está fuera del alcance del MVP salvo pedido explícito (`CLAUDE.md`).
- **Alternativas consideradas:** (a) Crear la fila de `PaginaPublica` en el flujo de registro — descartada: es una feature de Sprint 4, tocar el registro (Sprint 1) por una tabla que no se usa hasta dos sprints después agrega una dependencia innecesaria; el get-or-create resuelve lo mismo sin tocar `auth.go`. (b) Bloquear `/{slug}` también por falta de deploy (mostrar 404 o "no publicada" en vez del contenido) — descartada: el botón "Ver página" del editor necesita previsualizar antes de publicar, y la spec solo pide que el *buscador* no muestre páginas incompletas, no que la URL directa esté bloqueada. (c) Que "Deployar" reaparezca si se oculta la página (tratar "ocultar" como una especie de "des-deploy") — descartada: la spec los describe como dos acciones separadas en la misma barra, y mezclarlas haría que ocultar temporalmente una página real la sacara también del buscador, un efecto secundario no pedido.
- **Por qué:** Cada decisión evita acoplar dos cosas que la spec ya trata por separado (publicar vs. mostrar; contenido de la página vs. cuenta del profesional) — desacoplarlas ahora, aunque el MVP no explote esa flexibilidad todavía, evita tener que desenredarlas más adelante cuando sí haya edición de contenido real.
- **Qué se sacrifica:** Un profesional que nunca pasó por `/panel/pagina` ni una vez tiene una fila de `PaginaPublica` que no existe hasta su primera interacción — cualquier código nuevo que lea esa tabla directo (sin pasar por `getOrCrearPaginaPublica` o el mismo fallback de `getClinicaPublicaHandler`) tiene que acordarse de que puede no haber fila todavía, documentado en el comentario del handler para que no se repita el error de asumir que siempre existe.
- **Reversibilidad:** Alta — sin cambios de modelo de datos más allá de usar columnas que ya existían desde T0.3; los tres endpoints nuevos (`GET/PATCH /panel/pagina*`) y el join nuevo en `buscarClinicasHandler` se pueden revertir sin tocar el resto del backend.

## TR-017: El editor de página vive en `/personalizar-pagina`, fuera de `/panel/**` — corrección tras la primera entrega de T4.1

- **Fecha:** 2026-08-23
- **Fase:** ejecución (corrección pedida por el cliente sobre la primera entrega de T4.1/T4.2: "personalizar pagina es una pagina aparte por fuera de gestiona clinica... si doy click a tu pagina desde gestion clinica me lleva a esta pagina de edicion")
- **Decisión:** La primera versión de T4.1 montó el editor en `/panel/pagina`, dentro de `app/panel/layout.tsx` — heredaba el sidebar de navegación de clínica (General/Calendario/Turnos/Pacientes) y la textura de fondo de esas cuatro pantallas. Se corrige moviéndolo a `/personalizar-pagina`, una ruta de nivel superior, hermana de `/panel` (no una sub-ruta suya):
  - `app/panel/pagina/**` se elimina; nace `app/personalizar-pagina/page.tsx`, con su propio guard (`requireProfesional()` directo, ya no lo hereda de `panel/layout.tsx`) y su propio `<main>` (fondo `bg-hueso`, sin `.panel-texture` — esa sigue reservada a las 4 pantallas de gestión de verdad).

  - `lib/site-routes.ts` (qué rutas ocultan el footer público) suma `/personalizar-pagina` a la lista explícita — al dejar de vivir bajo `/panel`, ya no hereda ese prefijo automáticamente.
- **Alternativas consideradas:** (a) Dejarlo en `/panel/pagina` pero ocultar el `PanelSidebar` solo en esa ruta (un caso especial dentro del layout compartido) — descartada: el pedido es que sea "una página aparte", no una página de gestión con un layout distinto; mantenerla bajo `/panel/**` la sigue atando conceptualmente a "gestión de clínica" aunque no se vea el sidebar. (b) Una URL más corta como `/pagina` — descartada por posible confusión de lectura junto a `/[slug]` (la página pública de una clínica cualquiera); `/personalizar-pagina` es más largo pero inequívoco y ya sigue el mismo patrón de nombre verbo+objeto que `/seleccionar-servicio`.

Anidar el editor bajo `/panel` fue una lectura de implementación más simple (reusar el layout ya armado) que no reflejaba esa separación conceptual; esta corrección alinea la URL y el layout con lo que la spec y el cliente ya esperaban.
- **Qué se sacrifica:** Dos guards de sesión independientes (`panel/layout.tsx` y `personalizar-pagina/page.tsx`) en vez de uno solo compartido — duplicación mínima (una línea, `requireProfesional()`), aceptable a cambio de que cada área sea de verdad independiente y no dependa de la existencia del layout de la otra.
- **Reversibilidad:** Alta — es mover archivos y actualizar un puñado de `href`/`revalidatePath`, sin tocar el backend ni el modelo de datos (los tres endpoints de `pagina_publica.go` no se movieron, siguen en `/panel/pagina/*` — esa sigue siendo la ruta de la API, no de una página).

## TR-018: La página pública de una clínica pierde el header/footer de Mirage — primer paso hacia el subdominio propio (spec §5)

- **Fecha:** 2026-08-23
- **Fase:** ejecución (ronda de ajustes sobre Sprint 4/T4.3, pedido explícito del cliente: "ya sea en el buscador de clinicas o en la opcion ver pagina, deberia dejar de verse el header de la pagina principal de mirage y ver el del de la pagina del profesional, se habrira en un pagina aparte independiente del de la app, ya que la idea como se dijo al principio es que este alojada en subdominios")
- **Decisión:**
  - `/{slug}` (la página pública de cada clínica) deja de mostrar el `SiteHeader`/`SiteFooter` globales de Mirage — el único header que le queda es el propio, el "header básico" con anclas a cada sección que ya vive dentro de `ClinicaPublicaTemplate`. Nuevo helper `isClinicaPublicaRoute(pathname)` en `lib/site-routes.ts`: cualquier ruta de un solo segmento que no esté en la lista explícita de rutas propias de Mirage (`/buscar`, `/panel`, etc.) se trata como la página de una clínica — mismo criterio con el que Next.js resuelve `[slug]` de verdad, expresado en un helper reusable porque un Client Component solo tiene el `pathname`, no los route params.
  - Nuevo `SiteHeaderVisibility` (Client Component), mismo patrón que `SiteFooterVisibility` ya existente: recibe `<SiteHeader />` ya renderizado como `children` y decide ocultarlo según la ruta. `isFooterHidden` también empieza a usar `isClinicaPublicaRoute` — el footer de Mirage tampoco se muestra ahí.
  - Con el header global ausente en esa ruta, `[slug]/page.tsx` deja de compensar su altura (`pt-[var(--header-height)]`) y las anclas de `ClinicaPublicaTemplate` pasan de `scroll-mt-[calc(var(--header-height)+1rem)]` a un `scroll-mt-6` fijo, ya sin depender de una variable que en esta ruta nunca se termina de fijar (nadie mide la altura de un header que no está montado).
- **Alternativas consideradas:** (a) Mover `/[slug]` (y el resto del sitio) a route groups de Next.js con layouts raíz separados (`app/(sitio)/layout.tsx` con header/footer, `app/(clinica)/[slug]/layout.tsx` sin ellos) — la forma "correcta" a largo plazo, pero implica reubicar prácticamente todo el árbol de `app/` en un solo cambio; se descarta por ahora a favor de la opción (b), de mucho menor riesgo, dejando la migración a route groups como el paso natural cuando se implemente el subdominio real (Fase 2, fuera de alcance del MVP — CLAUDE.md: "subdominios propios... no las implementes solo porque aparecen como preparación futura"). (b) Ocultarlo del lado del cliente con el mismo patrón que `SiteFooterVisibility` — la elegida: mínimo diff, reutiliza un patrón ya probado en este mismo proyecto, sin restructurar el árbol de rutas.
- **Por qué:** La spec (§5) ya preveía el subdominio propio como el destino final de cada página de clínica — "para que se sienta una página aparte" es exactamente lo que un subdominio real da gratis (otro origen, sin nada compartido). Hasta que ese trabajo de infraestructura exista, ocultar el header/footer compartidos es la aproximación visual más fiel sin anticipar esa migración.
- **Qué se sacrifica:** La independencia es visual/de cliente, no estructural — el HTML inicial que llega del servidor todavía incluye (y luego oculta) el `SiteHeader` resuelto; no es una separación real de layouts raíz como daría route groups. Documentado acá para que la futura migración a subdominio no la mal-lea como "ya está resuelto del todo".

## TR-020: CI/deploy en Render — seis recursos (dos entornos completos), deploy automático por rama; convención de storage multi-tenant para cuando exista

- **Fecha:** 2026-08-24
- **Fase:** ejecución (T5.5, pedido explícito del cliente: "ahora entramos a la parte de CI y deploy en render con bluprint, de manera similar a Marcuzzi_Madryn pero ahora vamos a tener 6 servicios, un servicio de api y web de prod y otra de dev con sus bases de datos separadas... el deploy de la pagina sera atomatico al subir un commit a cualquiera de los stages usando los deploy hooks")
- **Decisión:**
  - **Dos entornos completos, no uno**: a diferencia de Marcuzzi_Madryn (3 recursos: 1 base + api + web, todo "prod"), acá `render.yaml` declara 6 — `dental-mirage-db`/`-api`/`-web` (prod) y `dental-mirage-db-dev`/`-api-dev`/`-web-dev` (dev), cada trío completamente separado, nunca comparten base de datos entre sí.
  - **Deploy automático atado a la rama, uno por entorno**: `.github/workflows/ci.yml` pasa a correr también en push directo a `dev` (antes solo `main` + pull requests), y el job `deploy` se separa en `deploy-prod` (`if: github.ref == 'refs/heads/main'`, dispara `RENDER_DEPLOY_HOOK_API`/`_WEB`) y `deploy-dev` (`if: github.ref == 'refs/heads/dev'`, dispara `RENDER_DEPLOY_HOOK_API_DEV`/`_WEB_DEV`) — mismo patrón de gateo que Marcuzzi_Madryn (necesita los 4 jobs de test/build en verde), duplicado una vez por rama.
  - **Dockerfiles nuevos** (`apps/api/Dockerfile`, `apps/web/Dockerfile`) y `.dockerignore` (raíz + `apps/api/`) — mismo patrón de build en dos etapas que Marcuzzi_Madryn, pero **más simples**: sin el baile de `ARG`/`--build-arg` para variables `NEXT_PUBLIC_*` (Dental Mirage no tiene ninguna — spec §9.3, BFF sin excepciones, `API_URL`/`CONTACTO_EMAIL` son server-only) y sin el volumen de `UPLOADS_DIR`/`api_uploads` (todavía no existe la feature de subir fotos). Los dos Dockerfiles se buildearon y corrieron de verdad contra el código real (`docker build` + `docker compose up --build`, con un registro/health-check/página SSR probados contra los contenedores) antes de darlos por buenos — no se asumió que el patrón de Marcuzzi_Madryn iba a aplicar igual sin probarlo.
  - **`docker-compose.yml`** se extiende con `migrate`/`api`/`web` (antes solo levantaba Postgres) — mismo Dockerfile que usa Render, para que "anda en mi máquina" y "anda en Render" sean literalmente la misma imagen.
  - **Storage de fotos multi-tenant, reservado pero no construido**: `render.yaml` ya declara los env vars de R2 (`sync: false`, sin cargar) en los 4 servicios `api`, con buckets separados por entorno (prod/dev) — pero la feature en sí (subir foto de perfil o de página pública) no existe todavía en el código (fuera del alcance del MVP salvo pedido explícito, `CLAUDE.md`). La diferencia real de fondo con Marcuzzi_Madryn no es técnica sino de escala: esa es una sola aplicación con un dueño (una key por foto alcanza); acá va a haber **N profesionales**, cada uno subiendo sus propias fotos de perfil y de página — sin un namespace por profesional, dos profesionales podrían pisarse archivos con el mismo nombre. Convención decidida ahora, para no tener que migrar keys ya escritas el día que la feature se construya: `paginas/{profesionalId}/{filename}` y `perfiles/{profesionalId}/{filename}`.
- **Alternativas consideradas:** (a) Un solo entorno (como Marcuzzi_Madryn), probando features nuevas directo en prod antes de un release — descartada, pedido explícito del cliente de tener dev separado con su propia base; con turnos/pacientes/datos reales de profesionales en juego, probar en prod deja de ser aceptable mucho antes que en un sitio de turismo sin cuentas de usuario críticas. (b) Una sola base de datos con un schema o prefijo distinto por entorno en vez de dos bases separadas — descartada: una migración con bug corriendo contra "dev" en la misma instancia física que prod es un radio de explosión mucho mayor que dos bases completamente aisladas: el aislamiento físico es más caro (dos planes free en vez de uno) pero elimina la clase de bug entera. (c) Construir ya la feature de storage (interfaz `storage.Storage` + R2) ya que se estaba tocando el deploy — descartada: no está pedida todavía, sigue fuera del alcance del MVP; se dejaron los env vars reservados y la convención de key documentada para no repetir este análisis desde cero cuando sí se pida, sin construir código sin una feature real que lo consuma.
- **Por qué:** El cliente pidió explícitamente reproducir "de manera similar a Marcuzzi_Madryn" pero con la duplicación completa prod/dev — la razón de fondo (aunque no la dijo así) es que Dental Mirage maneja datos reales de terceros (profesionales, sus pacientes, sus turnos) desde el día 1 de producción, a diferencia de Marcuzzi_Madryn en su etapa actual (sin reservas reales todavía) — tener un entorno de prueba real, con su propia base, deja de ser un lujo.
- **Qué se sacrifica:** El doble de recursos de Render en el plan free (2 bases, 4 servicios web) — dentro de los límites gratuitos por ahora, pero es la primera cuenta atrás explícita a tener en la cabeza si Render cambia esos límites. Cada cambio a `render.yaml` (agregar un env var, por ejemplo) hay que hacerlo en el par prod/dev a mano — no hay una forma nativa en Render de "heredar" configuración entre dos servicios del mismo blueprint.
- **Reversibilidad:** Alta — volver a un solo entorno es borrar la mitad de `services:`/`databases:` de `render.yaml` y el job `deploy-dev` de `ci.yml`, sin tocar el código de la aplicación en sí (los Dockerfiles no saben nada de "prod" vs. "dev", reciben esa distinción entera vía env vars).

## TR-021: Un solo entorno en Render, no dos — corrección tras un límite real del plan free (no se puede tener más de una base Postgres por cuenta)

- **Fecha:** 2026-08-24
- **Fase:** ejecución (corrección sobre TR-020, mismo día — pedido explícito del cliente al toparse con el límite real de Render: "me dice que no puedo tener mas de una database en el plan free, por el momento quitemos los servicios de prod y que solo queden los de main, que se deployan a los commits de dev")
- **Decisión:** `render.yaml` pasa de 6 recursos (dos entornos completos) a **3** — un solo trío `dental-mirage-db`/`-api`/`-web`, sin sufijo. El deploy de ese único entorno se dispara con push a `dev` (no `main`) — `ci.yml` colapsa `deploy-prod`/`deploy-dev` de vuelta a un solo job `deploy`, con `if: github.ref == 'refs/heads/dev'`. `main` sigue corriendo el pipeline completo de tests/build en cada push (sigue en la lista de `on: push: branches:`), simplemente no dispara ningún redeploy por ahora. `APP_ENV` del servicio `api` pasa de `production` a `development`, honesto con lo que ese servicio es hoy (el entorno de integración/prueba, no uno de prod real todavía). Los env vars de R2 (TR-020) se mantienen reservados tal cual, sin cambios — la convención de key multi-tenant sigue siendo válida sea cual sea la cantidad de entornos.

(b) Compartir una sola base entre "prod" y "dev" con un prefijo de tabla o un schema distinto — descartada, mismo argumento que ya cerraba esta puerta en TR-020: el aislamiento físico es la única garantía real de que un bug de dev no le toca un dato a prod, y una vez que se abre esa puerta "temporalmente" es fácil que quede así de forma permanente por inercia.
- **Por qué:** Es una restricción real de la plataforma, no una preferencia de diseño — Render no ofrece una segunda base Postgres gratis por cuenta. Elegir qué rama se queda con el único entorno disponible (`dev`, no `main`) prioriza tener *algo* desplegado y probable de verdad sobre tener nada desplegado hasta poder pagar dos bases; `main` (que además solo recibe merge cuando el cliente lo pide explícitamente, spec de flujo de ramas) puede esperar a que exista presupuesto para un entorno de prod separado sin que eso bloquee nada del trabajo diario.
- **Qué se sacrifica:** No hay, hoy, ningún entorno que se comporte como "producción real" — el único servicio desplegado se redeploya con cada push a `dev`, así que cualquier commit que rompa algo en runtime (aunque pase CI) llega ahí directo, sin la capa extra de seguridad que daba tener un `main` protegido y separado. Aceptado como riesgo temporal, documentado para que quede claro que es una consecuencia directa del límite del plan free, no una relajación deliberada de rigor.
- **Reversibilidad:** Alta — volver a separar los dos entornos es agregar de nuevo el segundo trío de recursos a `render.yaml` (el patrón anterior queda documentado en el comentario del archivo) y el job `deploy-dev` a `ci.yml`, en cuanto haya presupuesto para una segunda base Postgres.

El sidebar de `/panel` (TR-023, riel de íconos angosto en mobile) y el header con menú desplegable (TR-023) **no se tocan** — el cliente los confirmó explícitamente ("primero no quitar el sidebar desplegable de mobile"). `/personalizar-pagina` (el editor de página, que TR-017 ya estableció como un área separada de "gestión de clínica") tampoco se toca esta ronda — su apilado en mobile (TR-023) sigue vigente, fuera del alcance de este pedido puntual.

Solo se les suma el mismo `WebkitOverflowScrolling: "touch"`.

(c) Revertir también el sidebar/header de TR-023 ya que están relacionados con "mobile" en general — descartada, el cliente fue explícito en preservarlos ("primero no quitar el sidebar desplegable de mobile") y el pedido de esta ronda es puntualmente sobre calendario/tablas.

El bug real que motivó la corrección de `calendar-grid.tsx` (el `minmax(140px,1fr)` incondicional podía tocar desktop en viewports angostos) era una falla genuina de la implementación anterior, no solo una preferencia — se corrige independientemente de cuál de las dos filosofías gane.

Las tablas no cambian nada (ya cumplían el patrón pedido).
- **Reversibilidad:** Alta — la variable CSS (`globals.css`) y el `style` de `calendar-grid.tsx` son el único cambio de comportamiento real; volver al criterio de TR-023 (compactar en vez de scrollear) es bajar el valor de `--panel-dia-min-w` o volver a `minmax(0, 1fr)` sin condicional. Verificado: pipeline completo (`typecheck`/`lint`/`test:coverage`/`build`) limpio, 307 tests → 92.7% cobertura (sin tests nuevos — cambios puros de CSS/estilo inline, sin lógica nueva que cubrir).

## TR-025: Segunda vuelta sobre TR-024 — sidebar vuelve a su toggle único (sin breakpoint), y el ancho mínimo del calendario se fuerza una vez por contenedor, no por columna

- **Fecha:** 2026-08-24

## TR-026: Gestión de clínica en mobile — estructura fija (header/sidebar/página) + una sola área de scroll por página + tamaños fluidos con `clamp()`/`vw`

- **Fecha:** 2026-08-24
- **Fase:** ejecución (tercera vuelta sobre TR-024/TR-025, mismo día, rama `fix/mobile` — pedido explícito y muy detallado del cliente: header/sidebar fijos, "la página en sí NO debe scrollear (el layout raíz con altura 100vh y overflow: hidden)", "únicamente el área de contenido... se puede desplazar horizontal y verticalmente", "el contenido debe adaptarse al tamaño de la pantalla... ni gigante ni diminuto... clamp() usando vw", "en vez de un ancho fijo enorme, usá min-width... para que se estire y llene la pantalla, y que solo desborde... lo que realmente no entra", "no modifiques el meta viewport global")
- **Decisión:**
  - **Estructura fija, un solo scroll por página** (`app/panel/layout.tsx`, mobile-only vía `max-md:`): la raíz de gestión de clínica pasa a medir exactamente `100dvh` (no `100vh` — en mobile Safari `dvh` descuenta la barra de direcciones, más preciso que lo que pidió el cliente literalmente pero sin cambiar la intención) menos el header, con `overflow-hidden` — así el documento (`html`/`body`, compartido con el resto del sitio, **no tocado**) nunca llega a necesitar scroll propio, sin que haga falta editar `app/layout.tsx`. `PanelSidebar` queda como hermano de `<main>`, fuera del área que scrollea — al no moverse nunca, queda visualmente "fijo" (además de su `sticky` ya existente, que sigue sin romper nada, solo se vuelve redundante en mobile). `<main>` pasa a ser el ÚNICO elemento que scrollea verticalmente (`overflow-y-auto`, `overflow-x-hidden`, `min-h-0` para el gotcha clásico de flexbox) — cada página adentro fluye con su alto natural (título + filtros + tabla/calendario juntos, como cualquier página), en vez de que cada widget interno tuviera su propio recorte vertical (que hubiera significado *dos* scrolls anidados: uno en `<main>` y otro dentro de la tabla).
  - **Scroll horizontal solo donde hace falta, no en toda la pantalla**: el calendario (`calendar-view.tsx`) y las tres tablas (`TurnosTable`, Pacientes, `PacienteTurnosTable`) pierden su recorte/scroll VERTICAL propio en mobile (`max-md:overflow-y-visible`, y en las tablas también `max-md:max-h-none`) — ese scroll ahora lo da `<main>` — pero conservan su `overflow-x-auto` sin cambios, en las dos direcciones de viewport: es el único mecanismo de scroll horizontal, acotado a ese widget puntual.
  - **Ancho mínimo "que llena y solo desborda lo que no entra", no "un ancho fijo enorme" (tercera vuelta sobre `calendar-grid.tsx`)**: TR-024 (primera vuelta) ya había puesto un piso de ancho *por columna* (`minmax(150px, 1fr)`) — funcionaba para la vista Semana, pero no hacía nada en la vista Día (una sola columna: `1fr` siempre gana el 100% del ancho sin importar el piso), así que esa vista seguía "apretada". TR-025 (segunda vuelta) sobrecorrigió al revés: forzó un ancho ENORME fijo sobre TODO el contenedor (720px para Día, hasta 1400px para Semana) — resolvía lo de la vista Día, pero es exactamente lo que el cliente ahora pide evitar explícitamente ("en vez de un ancho fijo enorme..."). Esta vuelta reinstala el piso *por columna* de TR-024, con dos cambios: (a) el valor es `clamp(6.5rem, 30vw, 10.5rem)` (~104px–~168px) en vez de un px fijo, escalando con el viewport como pidió el cliente; (b) la vista Día deja de necesitar ningún piso especial — con el nuevo entendimiento del pedido, que una sola columna llene el 100% del ancho vía `1fr` sin desbordar nada **es exactamente lo correcto** ("que se estire y llene la pantalla"), no un bug a corregir. El piso por columna en `.panel-calendar-dias` (definido en `globals.css`, `@media (max-width: 767px)`) solo se activa cuando de verdad no entra (Semana, 7 columnas) — ahí sí desborda a propósito y el `overflow-x-auto` del contenedor lo hace navegable. `CalendarMonthGrid` recibe el mismo criterio: su `min-w-[490px]` incondicional pasa a `max-md:min-w-[clamp(280px,90vw,420px)]` — en escritorio ya no tiene ningún min-width propio (nunca hacía falta, el `grid-cols-7` se reparte solo).
  - **Tamaños fluidos con `clamp()`/`vw`**: cada `h1` de las cinco pantallas de `/panel` (General/Calendario/Turnos/Pacientes/detalle de paciente) pasa de `text-3xl` fijo a sumar `max-md:text-[clamp(1.25rem,6vw,1.875rem)]` (o `6.5vw` según el ancho de página); el padding raíz de cada página pasa de `p-8` fijo a sumar `max-md:p-[clamp(1rem,4vw,2rem)]`. El techo de cada `clamp()` coincide con el valor de escritorio (`1.875rem`≈`text-3xl`, `2rem`=`p-8`), así que el propio `clamp()` converge al mismo número que ya usaba escritorio a medida que el viewport crece — no hace falta un breakpoint aparte para "volver" al tamaño de escritorio.
  - **Sidebar** (`panel-sidebar.tsx`): sin cambios respecto de TR-025 (ya había vuelto a su comportamiento único, sin variante mobile) — la única novedad acá es el ajuste de `100vh`→`max-md:100dvh` en su propia altura, por el mismo motivo que la raíz del layout.
  - **Meta viewport**: no tocado — sigue siendo el default de Next.js (`width=device-width, initial-scale=1`), nunca se editó `app/layout.tsx` ni se agregó un `<meta>` propio.
- **Alternativas consideradas:** (a) Aislar el scroll vertical DENTRO de cada widget (tabla/calendario) en vez de en `<main>`, fijando el título/filtros de cada página con `flex-shrink-0` y solo el widget con `flex-1 overflow-y-auto` — descartada: requiere una cadena de `min-h-0` en cada nivel (layout → main → página → widget) mucho más frágil de mantener y más difícil de verificar sin poder correr un browser real en este entorno; y hubiera dejado DOS scrolls verticales anidados (uno en el widget, uno potencial en la página si algo no encaja bien), justo lo que "un solo scroll" busca evitar. La opción elegida (un solo `overflow-y-auto` en `<main>`) es más simple y con menos superficie de bugs de flexbox. (b) Mantener el ancho fijo enorme de TR-025 pero "bajarlo" a algo más moderado — descartada, el cliente no pidió un número más chico, pidió el mecanismo contrario (`min-width` que se adapta y solo desborda lo necesario, no un valor fijo). (c) Usar `100vh` en vez de `100dvh` para seguir la letra del pedido ("altura 100vh") — descartada a favor de `dvh`: es la unidad correcta para lo que el cliente describe (que la página no scrollee en mobile), `100vh` en Safari mobile incluye el espacio de la barra de direcciones y de hecho *reintroduce* un scroll fantasma cuando esa barra está visible; documentado acá para que quede claro que es una mejora técnica sobre el pedido literal, no una desviación de la intención.
- **Por qué:** El pedido de esta ronda es mucho más específico y prescriptivo que las dos anteriores — describe el mecanismo exacto (contenedor raíz 100vh+overflow:hidden, un área de contenido con su propio overflow:auto, min-width en vez de ancho fijo, clamp()/vw) en vez de solo el síntoma. Seguirlo al pie de la letra (con el único ajuste técnico de `dvh` sobre `vh`, justificado arriba) es lo que finalmente separa con claridad "estructura de la app" (header/sidebar, que no deberían moverse nunca) de "contenido de la sección" (calendario/tablas, que sí necesitan moverse para mostrar más de lo que entra) — una distinción que las dos rondas anteriores no habían modelado explícitamente a nivel de layout, solo a nivel de cada widget por separado.
- **Qué se sacrifica:** Nada de fondo — es una reestructuración de layout puramente en CSS/Tailwind (`max-md:`), sin tocar el modelo de datos, sin tocar `app/layout.tsx` ni el meta viewport, sin tocar ningún componente fuera de `/panel/**`. La complejidad de mantener una cadena `min-h-0`/`overflow` correcta a través de `panel/layout.tsx` → `<main>` queda documentada acá para quien la toque después: si se agrega un nuevo nivel de anidamiento flex dentro de `/panel/**` en el futuro, hay que revisar si necesita su propio `min-h-0` para no romper el `overflow-y-auto` de `<main>`.
- **Reversibilidad:** Alta — todo son clases `max-md:`/`clamp()` y una regla de `globals.css`, reversible sin tocar modelo de datos ni backend. Verificado: pipeline completo (`typecheck`/`lint`/`test:coverage`/`build`) limpio, 307 tests → 92.7% cobertura (sin tests nuevos — cambios puros de CSS/estilo, sin ramas de lógica nuevas que cubrir); además se inspeccionó el CSS compilado de producción (`.next/static/chunks/*.css`) para confirmar que Tailwind generó correctamente el bloque `@media not all and (min-width:48rem)` (el `max-md:` de Tailwind v4) con todas las clases esperadas adentro (`h-[100dvh]`, `overflow-hidden`, `min-h-0`, `max-h-none`, `overflow-y-visible`, los `clamp()` de padding/tipografía) — no se puede probar en un browser real dentro de este entorno, así que esta inspección del CSS generado fue la verificación más cercana disponible antes de pedirle al cliente que lo pruebe en su celular real.

## TR-027: El header/sidebar de gestión de clínica "se movían" en mobile — no era un bug de anidamiento, era el rebote elástico del documento filtrándose desde un scroll anidado

- **Fecha:** 2026-08-24
- **Fase:** ejecución (cuarta vuelta sobre TR-024/025/026, mismo día, rama `fix/mobile` — el cliente reportó, tras probar TR-026 en su celular: "el scroll que implementaste mueve todo junto (sidebar y header incluidos)... el header y el sidebar están DENTRO del contenedor que scrollea, y tienen que estar FUERA", con una jerarquía exacta pedida y la instrucción explícita de mostrar la jerarquía actual y confirmar antes de tocar código)
- **Diagnóstico (antes de codear, como pidió el cliente):** se reconstruyó la jerarquía real del DOM leyendo el código (no de memoria) y se confirmó que `<header>` (`position: fixed`, `HeaderFrame`) y `PanelSidebar` (`position: sticky`) **ya eran hermanos** del área que scrollea, no descendientes — `<header>` vive en `app/layout.tsx`, antes de `{children}`; `PanelSidebar` es hermano directo de `<main>` (el único `overflow-auto`) dentro de `app/panel/layout.tsx`. La jerarquía que pedía el cliente ya existía. Con el anidamiento descartado como causa, el diagnóstico pasó a un comportamiento conocido de mobile Safari: un gesto táctil dentro de un scroll anidado (el `overflow-x-auto` del calendario o de una tabla) que llega a su borde puede disparar el "rebote elástico" (overscroll) del **documento** — y como `position: fixed` ancla al viewport visual, ese rebote arrastra visualmente al header aunque nunca estuvo dentro del contenedor que scrollea. Diagnóstico presentado al cliente antes de codear (`AskUserQuestion`), confirmado antes de implementar el fix.
- **Decisión:**
  - **`PanelScrollLock`** (`components/panel-scroll-lock.tsx`, nuevo Client Component, mismo patrón que `SiteHeaderVisibility`/`SiteFooterVisibility`: `usePathname` + un efecto que toca `document.documentElement` directo, igual que ya hace `HeaderFrame` con `--header-height`) — agrega la clase `panel-locked` a `<html>` mientras la ruta está dentro de `/panel/**`, la saca al salir o desmontarse. Montado una sola vez en `app/layout.tsx`, antes de `SiteHeaderVisibility`.
  - **`globals.css`**, `@media (max-width: 767px)`: `html.panel-locked, html.panel-locked body { overflow: hidden; overscroll-behavior: contain; }` — bloquea el documento por completo (no solo el contenedor raíz de `/panel`, que ya tenía su propio `overflow-hidden` desde TR-026) mientras se está en gestión de clínica, cerrando la vía de filtración del rebote hacia el nivel más alto. Solo debajo de 768px — arriba de eso `.panel-locked` no tiene ninguna regla, cero efecto en escritorio.
  - **`overscroll-behavior: contain`** (`max-md:overscroll-contain`, la utilidad nativa de Tailwind) sumado a los CUATRO contenedores con scroll de gestión de clínica (`<main>` en `app/panel/layout.tsx`, el cuadro del calendario en `calendar-view.tsx`, y las tres tablas — Turnos/Pacientes/turnos del detalle de paciente) — la otra mitad del arreglo: incluso con el documento bloqueado, sin esto un gesto en el borde de cualquiera de estos scrolls podía iniciar el efecto de rebote antes de que el navegador terminara de descartarlo.
- **Alternativas consideradas:** (a) Restructurar el DOM de todos modos (mover header/sidebar a otro lugar), asumiendo que el cliente tenía razón sobre el anidamiento — descartada tras confirmar con el código real que la jerarquía ya era la pedida; mover elementos que ya están bien ubicados no solo no arregla nada, sino que arriesga romper otras cosas (el `--header-height` que mide `HeaderFrame`, el `sticky` del sidebar) sin atacar la causa real. (b) Bloquear el documento SIEMPRE (no solo en `/panel`) — descartada: rompería el scroll natural de Home/`/buscar`/`/ingresar`/etc., que si dependen del scroll normal del documento (no tienen su propia estructura de `<main>` acotado); `PanelScrollLock` existe justamente para acotar el bloqueo a la única sección que lo necesita, replicando el mismo patrón ya usado por `SiteHeaderVisibility`. (c) Usar solo `overscroll-behavior: contain` sin el bloqueo de `html`/`body` — descartada como insuficiente: `overscroll-behavior` en el contenedor anidado reduce la chance de que el rebote se dispare, pero no la elimina con la misma garantía que bloquear el documento directamente (ambas capas juntas es lo robusto, no una sola).
- **Por qué:** El pedido explícito del cliente de "mostrame la jerarquía y confirmame antes de codear" resultó ser la decisión correcta — permitió descartar la hipótesis original (anidamiento) con evidencia real del código en vez de reestructurar a ciegas, y encontrar la causa real (un comportamiento de plataforma, no un error de construcción del layout). Bloquear el documento + contener el overscroll en cada scroll anidado es el arreglo estándar para este bug conocido de WebKit/mobile Safari.

## TR-029: Scroll vertical roto (bug real: el fallback `vh`→`dvh` se perdía en el minificador), anchos inconsistentes entre filas, gap bajo el header, y sidebar colapsado/íconos faltantes

- **Fecha:** 2026-08-24
- **Fase:** ejecución (sexta vuelta sobre TR-024 a TR-028, mismo día, rama `fix/mobile` — el cliente probó TR-028 y reportó una lista de 5 bugs puntuales: scroll vertical roto ("no puedo ver las horas de abajo del calendario", marcado prioridad), anchos inconsistentes entre la toolbar y el calendario según la vista ("lo mismo en Turnos"), un espacio de más entre el header y el contenido, el sidebar colapsado debía medir ~52px con íconos centrados, y faltaban íconos para "Tu página"/"Tu perfil". El cliente mencionó un archivo `referencia-v6.html` que **no se encontró en el repo ni en el resto del sistema** — se avisó y se procedió igual, ya que la lista de bugs era lo bastante precisa y técnica para actuar sin él.)
- **Decisión:**
  - **Scroll vertical (bug real encontrado, no solo un ajuste de criterio)**: la corrección de TR-026/028 usaba `height: 100vh; height: 100dvh;` (dos declaraciones de la misma propiedad en una sola regla) como fallback para navegadores sin soporte de `dvh` — técnica CSS válida en teoría, pero **Lightning CSS (el minificador de Tailwind v4) la trata como código muerto y descarta la primera declaración al compilar** — confirmado inspeccionando el CSS de producción real, donde solo sobrevivía `height:100dvh`, sin ningún `100vh` de respaldo. En un navegador sin soporte de `dvh`, esa declaración se ignora entera y el alto de la raíz de `/panel` queda SIN ACOTAR — y como `.panel-locked` (TR-027) bloquea `html`/`body` sin darles scroll propio, cualquier contenido que excediera el viewport quedaba recortado, inalcanzable con ningún gesto: exactamente "no puedo ver las horas de abajo". Se corrige partiendo el fallback en dos REGLAS distintas (`.panel-shell-h`/`.panel-sidebar-h` con `height: 100vh` como base, más un bloque `@supports (height: 100dvh) { ... }` aparte que la pisa) — un minificador no puede evaluar `@supports` en build time, así que preserva ambas reglas, y el fallback real vuelve a funcionar (verificado en el CSS de producción tras el fix). Además, se agrega `min-height: 0` a la raíz de `/panel` (antes solo estaba en `<main>`) — la raíz también es un flex item de `<body>` (`flex flex-col`) y sin este ajuste podía terminar más alta que el viewport por la misma trampa de flexbox de siempre, agravando el mismo bug.
  - **Anchos inconsistentes**: en `calendar-view.tsx`, TR-028 le daba un `min-width` INDEPENDIENTE a título/toolbar (640px fijo) y otro distinto al calendario (nada en Día, ~974px en Semana) — terminaban midiendo distinto entre sí según la vista. Se corrige envolviendo título+toolbar+calendario en un único wrapper con UN SOLO `min-width` (`--panel-cal-min-w`, 640px de piso, más si la vista Semana necesita más días), y cada fila adentro pasa de su propio `min-w` a `w-full` (mide lo que mida el wrapper, nunca menos ni más). Mismo criterio aplicado a `turnos/page.tsx` (filtros+tabla comparten 720px, el mínimo que ya tenía la tabla) y `pacientes/page.tsx` (buscador+tabla comparten 600px).
  - **Gap bajo el header**: cada página de `/panel` pasa de `p-8`/`max-md:p-[clamp(...)]` (padding parejo en los 4 lados) a separar el padding superior del resto — lateral/inferior siguen en `clamp()` (TR-026), el superior baja a un valor chico y fijo (`pt-3`, 12px) — el espacio real que compensa la altura del header ya lo da `pt-[var(--header-height)]` en `app/panel/layout.tsx` (sin tocar), el `clamp()` de arriba de cada página era una segunda capa de aire redundante encima de esa.
  - **Sidebar colapsado**: `w-16` (64px) pasa a `w-[52px]` exacto; los íconos suman `justify-center` cuando está colapsado (antes quedaban pegados a la izquierda del riel angosto, sin nada que los centre horizontalmente al no haber texto al lado empujándolos).
  - **Íconos faltantes**: "Tu página"/"Tu perfil" (antes texto plano, con un "•" como único indicador al colapsar) suman `IconPagina` (ventana de navegador con barra de encabezado) e `IconPerfil` (una sola persona, versión simplificada de `IconPacientes`) en `sidebar-icons.tsx`, mismo trazo/grosor que las otras 4 herramientas.
- **Alternativas consideradas:** (a) Para el fallback de altura, usar `@supports not (height: 100dvh) { .panel-shell-h { height: 100vh } }` en vez de una regla base + `@supports (height: 100dvh)` — funciona igual de bien, se prefirió la versión con base+@supports-positivo por quedar más corta (una condición en vez de dos) y porque `@supports (propiedad: valor)` tiene mejor soporte histórico que `@supports not (...)` en navegadores más viejos, justo el caso que este fallback existe para cubrir. (b) Para los anchos inconsistentes, mantener min-widths independientes por fila pero forzarlos a coincidir "a mano" (mismo número hardcodeado en cada uno) — descartada: es frágil, cualquier cambio futuro en un lugar rompe la coincidencia sin avisar; un solo wrapper con un solo número fuente es la forma correcta de garantizar que nunca se desincronicen. (c) Para el sidebar colapsado, usar `w-13` (la utilidad nombrada de Tailwind v4 para 52px) en vez de `w-[52px]` arbitrario — se prefirió el arbitrario por ser inequívoco al leer el código (no hay que recordar que `13 × 4px = 52px`).
- **Por qué:** El bug del scroll vertical es la lección más importante de esta ronda: una técnica de fallback CSS *correcta en la especificación* puede quedar rota por una herramienta del pipeline de build (el minificador) sin que el código fuente delate nada — la única forma de haberlo encontrado fue inspeccionar el CSS de producción REAL después de cada build, algo que ya se venía haciendo en rondas anteriores por prudencia, y que acá resultó decisivo. Los demás bugs (anchos, gap, sidebar) son refinamientos directos de pedidos explícitos y puntuales, sin ambigüedad de interpretación.
- **Qué se sacrifica:** Nada de fondo — todo sigue siendo aditivo/reversible, sin tocar modelo de datos ni archivos fuera de `/panel/**`. El archivo `referencia-v6.html` que el cliente mencionó no llegó a incorporarse al repo (no se encontró) — si aparece más adelante y muestra algo distinto a lo implementado acá, hay que revisar contra él.
- **Reversibilidad:** Alta — mismo mecanismo que las rondas anteriores (clases `max-md:`, variables CSS, un par de reglas `@supports`), sin tocar backend. Verificado: pipeline completo (`typecheck`/`lint`/`test:coverage`/`build`) limpio, 313 tests → 92.79% cobertura (2 tests nuevos para el sidebar colapsado/íconos); CSS de producción inspeccionado dos veces — la primera confirmó el bug real del fallback `vh`/`dvh` (la declaración `100vh` efectivamente desaparecía), la segunda confirmó que la corrección con `@supports` sí sobrevive la minificación, además de verificar `min-width:45rem`/`37.5rem`, `.max-md\:pt-3`, `.max-md\:w-full`, `.max-md\:max-w-none`, `.w-\[52px\]` y `.justify-center` compilados donde correspondía.

## TR-030: "El sidebar tapa el contenido" no era el sidebar — los modales, `position:fixed` pero descendientes de `<main>`, quedaban recortados por el `overflow` de un ancestro

- **Fecha:** 2026-08-24
- **Fase:** ejecución (séptima vuelta sobre TR-024 a TR-029, mismo día, rama `fix/mobile` — el cliente pidió analizar juntos una lista de bugs porque "casi todos vienen de la misma causa raíz": el sidebar superpuesto sobre el contenido, evidenciado en un video — el modal mostraba "gregar turno" en vez de "Agregar turno", el buscador "mbre, apellido, DNI" en vez de "Nombre, apellido, DNI", la fecha del calendario cortada; más scroll vertical roto "en toda la app", modales que se salen de los límites, gap header/contenido, y tablas desalineadas con su fila de filtros — con el pedido explícito de aplicar el mismo tratamiento a la sección General)
- **Diagnóstico:** el sidebar (`PanelSidebar`) **no es y nunca fue** `position: fixed`/`absolute` en esta rama — es `position: sticky`, hermano real de `<main>` dentro de un `flex` row, confirmado y verificado por tercera vez (TR-027, TR-028, y de nuevo acá). La causa real es más sutil y menos intuitiva: los 5 modales de gestión de clínica (`AgregarTurnoModal`, `EditarTurnoModal`, `CancelarTurnoModal`, `EditarPacienteModal`, `TurnoDetalle`) usan `position: fixed; inset: 0` — eso ancla sus *offsets* al viewport completo, pero **no los exime de ser recortados al pintar por un ancestro con `overflow` distinto de `visible`** — y ese ancestro es `<main>` (`overflow-auto` en mobile desde TR-026), que estos modales seguían teniendo como padre en el árbol del DOM (aunque su posición se calculara relativa al viewport). El resultado: el modal, centrado sobre el viewport COMPLETO, tenía su borde izquierdo cayendo exactamente en la franja de pantalla que `<main>` no incluye (la que ocupa el sidebar, ya que `<main>` es más angosto que el viewport) — esa franja quedaba invisible, comiéndose las primeras letras del texto alineado a la izquierda adentro del modal. Coincide exactamente con el patrón reportado (pierde caracteres del principio, no el modal completo) y con por qué se "sentía" como si el sidebar tapara cosas, sin serlo literalmente.
- **Decisión:**
  - **Nuevo `ModalPortal`** (`components/panel/modal-portal.tsx`) — un wrapper `"use client"` de una línea que hace `createPortal(children, document.body)`. Los 5 modales pasan a envolver su `<div role="dialog">` con `<ModalPortal>` — el nodo DOM del modal deja de ser descendiente de `<main>` (o de cualquier otro contenedor con `overflow`), pasa a ser hijo directo de `<body>`, sin ningún ancestro con overflow no-visible entre él y el documento. `.panel-locked` (TR-027) sí bloquea `<body>` con `overflow: hidden`, pero la caja de `<body>` coincide con el viewport COMPLETO (a diferencia de `<main>`, que está reducido por el ancho del sidebar) — así que ese bloqueo ya no recorta nada.
  - **`max-md:max-w-[90vw]`** sumado a la caja interna de los 5 modales (algunos ya tenían `max-h-[90vh]`/`overflow-y-auto`, los que no lo sumaron también) — cumple literalmente el pedido del cliente ("max-width: 90vw; max-height: 90vh; overflow: auto en el cuadro del modal").
  - **`paciente-turnos-table.tsx`** (usado dos veces en la ficha del paciente: "Turnos activos"/"Historial de turnos"): mismo bug de ancho inconsistente que TR-029 ya había corregido en Calendario/Turnos — la fila de filtros (tipo de consulta/fecha desde-hasta) y la tabla tenían cada una su propio `min-width`, terminaban midiendo distinto entre sí. Se corrige con el mismo patrón: un único `min-width` (35rem/560px, el que ya tenía la tabla) en el wrapper que envuelve a ambas, con `w-full` en la fila de filtros y en la caja de la tabla.
  - **General y ficha del paciente, revisados sin necesitar cambios estructurales**: ya comparten el mismo `<main>` (único punto de scroll de toda `/panel/**`) y ya tenían el mismo `pt-3` (gap header/contenido, TR-029) desde la ronda anterior — el pedido de "aplicale a General el mismo tratamiento" ya estaba satisfecho por construcción, al ser `<main>` compartido por las cinco pantallas.
- **Alternativas consideradas:** (a) Restructurar el sidebar de nuevo, asumiendo (como el cliente) que el problema era su posicionamiento — descartada por tercera vez consecutiva tras confirmar con el DOM real que ya es `sticky`, hermano de `<main>`; el video del cliente muestra el SÍNTOMA (texto cortado cerca de donde está el sidebar) pero la causa vive en los modales, no en el sidebar. (b) Sacar el `overflow-auto` de `<main>` para que los modales `fixed` dejaran de recortarse — descartada: `<main>` necesita ese `overflow` para ser el único punto de scroll de la sección (TR-028/029), sacarlo hubiera roto todo el trabajo de esas dos rondas para arreglar UN síntoma puntual de los modales. (c) Mover los modales a un nivel más alto del árbol de componentes (afuera de `<main>` pero todavía dentro de React, sin portal) — técnicamente posible pero mucho más invasivo (cada modal tendría que "burbujear" su estado hasta `app/panel/layout.tsx` o más arriba) — un portal resuelve lo mismo sin tocar de dónde viene el estado de cada modal.
- **Por qué:** `position: fixed` cambia respecto a qué se calculan los *offsets* de un elemento, no si un ancestro con `overflow` lo recorta al pintar — es una distinción real de CSS, no obvia, y la única forma de confirmarla fue razonar la cadena completa de ancestros (`<main>` → fila → raíz de `/panel`) contra el patrón exacto del bug reportado (pérdida de caracteres del borde izquierdo, no el modal entero desaparecido). Un portal a `document.body` es la solución estándar para este problema exacto — saca el nodo del DOM de cualquier ancestro con overflow, sin tener que reestructurar el árbol de React.
- **Qué se sacrifica:** Nada de fondo — es aditivo (un componente nuevo de una línea + 5 imports), sin tocar el modelo de datos ni ningún archivo fuera de `/panel/**`. Cualquier modal NUEVO que se agregue a gestión de clínica en el futuro tiene que recordar envolverse en `ModalPortal` para no reintroducir este mismo bug — documentado acá para que quede el porqué, no solo el "hacelo así".
- **Reversibilidad:** Alta — sacar `<ModalPortal>` de los 5 modales revierte al comportamiento anterior (con el bug) sin tocar nada más. Verificado: pipeline completo (`typecheck`/`lint`/`test:coverage`/`build`) limpio, 313 tests → 92.8% cobertura (sin tests nuevos — los tests existentes de cada modal siguen pasando sin cambios, porque las queries de Testing Library buscan en todo `document.body`, no solo en el `container` del render, así que el contenido portal-eado se sigue encontrando igual); CSS de producción inspeccionado para confirmar `.max-md\:max-w-\[90vw\]{max-width:90vw}` y `min-width:35rem` compilados donde correspondía.

## TR-031: Scroll vertical "congelado" al aterrizar en Calendario o en la ficha de un paciente — bug conocido de iOS Safari (contenido nuevo no reconocido sin un reflow externo)

- **Fecha:** 2026-08-24
- **Fase:** ejecución (octava vuelta sobre TR-024 a TR-030, mismo día, rama `fix/mobile` — el cliente reportó, tras probar TR-030: "sigue sin responder el movimiento vertical en el apartado de calendario y sigue viendose el gap entre el header y el sidebar, creo que tiene que ver algo con el calendario, ya que se arregla momentaneamente cuando cambio de dia a semana o de mes... El mismo problema tiene cuando toco la ficha de un paciente")
- **Diagnóstico:** la pista decisiva es "se arregla al cambiar de Día a Semana/Mes" — un click en esos botones no toca nada relacionado con scroll ni con el layout general, solo cambia qué componente de calendario se renderiza adentro de `<main>`. Que ESO "arregle" el scroll señala un bug conocido de iOS Safari: un contenedor con `overflow: auto` (acá, `<main>`, el único punto de scroll desde TR-028) a veces no reconoce que tiene contenido nuevo — o que recién se montó — hasta que ALGÚN cambio en el DOM dispara un reflow del layout. El clic en Día/Semana/Mes termina siendo ese disparador por pura casualidad (cambia el DOM adentro de `<main>`, y ESO fuerza el reflow que debería haber pasado solo al entrar a la pantalla). Mismo mecanismo explica "el mismo problema... en la ficha de un paciente": `app/panel/layout.tsx` es un layout COMPARTIDO por todo `/panel/**` — no se remonta al navegar de `/panel/calendario` a `/panel/pacientes/[id]`, solo cambia `{children}` adentro del mismo `<main>` — así que el único momento real en que hace falta el reflow es el cambio de ruta, sea cual sea la pantalla de destino.
- **Decisión:**
  - **`PanelShell`** (`components/panel/panel-shell.tsx`, nuevo Client Component) reemplaza el `<div>` raíz que antes vivía inline en `app/panel/layout.tsx` (Server Component). Con `usePathname()` + `useLayoutEffect` (no `useEffect` — tiene que correr ANTES de que el navegador pinte el siguiente frame, si no habría un parpadeo real y visible), fuerza un reflow verdadero cada vez que cambia la ruta: alterna `display: none` → lee `offsetHeight` (fuerza el layout a resolverse de verdad, no alcanza con solo leer sin cambiar nada) → restaura el `display` original. `useLayoutEffect` tira un warning en el server ("does nothing on the server") — se resuelve con el patrón isomorphic estándar (`useEffect` en el server, `useLayoutEffect` de verdad en el cliente, elegido según `typeof window`).
  - **Se saca `WebkitOverflowScrolling: "touch"` de `<main>`** — esa propiedad es vestigial en iOS moderno (el scroll con inercia es nativo para `overflow: auto` desde iOS 13) y hay reportes documentados de que declararla explícitamente puede ser justo lo que dispara bugs de "contenido nuevo no reconocido" en ciertas versiones de WebKit — sacarla es la corrección más segura, sumada como respaldo al reflow forzado (no una apuesta única, las dos cosas juntas).
  - **El "gap entre header y sidebar"** que el cliente reporta junto con el scroll queda cubierto por el mismo mecanismo: al forzar el reflow de TODA la raíz (`panel-texture`, que contiene sidebar Y `<main>` juntos, no solo `<main>`), cualquier desajuste transitorio entre el `padding-top: var(--header-height)` de la raíz y la altura real del header (que `HeaderFrame` mide de forma asincrónica vía `ResizeObserver`, después del primer paint) también se vuelve a resolver en el mismo golpe.
- **Alternativas consideradas:** (a) Nudge de reflow solo en `<main>` (no en toda la raíz) — descartada: no cubre el "gap" reportado junto al scroll, que involucra al sidebar (hermano de `<main>`, fuera de su alcance); forzar el reflow en la raíz completa (sidebar + `<main>` juntos) resuelve las dos cosas con un solo mecanismo. (b) Solo leer `el.offsetHeight` sin alternar `display` — descartada, es la variante "liviana" de este truco pero está bien documentado que NO alcanza para este bug puntual de WebKit (una lectura sola fuerza layout geométrico, pero no necesariamente la re-evaluación de la región de scroll/hit-testing que es la que falla acá); alternar una propiedad que además dispara un repintado (`display`) es la variante que sí funciona según los reportes. (c) `useEffect` en vez de `useLayoutEffect` — descartada por el parpadeo visible que introduciría (el toggle de `display` se vería un frame completo antes de revertirse).
- **Por qué:** La pista que dio el cliente ("se arregla momentáneamente cuando cambio de vista") es justo el patrón que distingue este bug de un error de CSS/layout genuino (que no se "arreglaría solo" con una interacción no relacionada) — apuntó directo a un problema de sincronización entre el motor de renderizado y el DOM, no a una regla de `overflow`/`min-height` mal puesta (esas ya se habían verificado exhaustivamente, con inspección del CSS compilado, en TR-026 a TR-029). Forzar un reflow en el momento correcto (el cambio de ruta) es el arreglo estándar documentado para esta clase de bug de iOS Safari.
- **Qué se sacrifica:** Un micro-costo de performance (un reflow forzado extra por cada navegación dentro de `/panel/**`) — imperceptible en la práctica (`useLayoutEffect` corre una sola vez por cambio de ruta, no en cada render) y muchísimo menor que el costo de un scroll roto. Nada de fondo más allá de eso — aditivo, sin tocar modelo de datos ni archivos fuera de `/panel/**`.
- **Reversibilidad:** Alta — revertir es volver a inlinear el `<div>` en `app/panel/layout.tsx` sin `PanelShell` y sin el reflow forzado; la remoción de `WebkitOverflowScrolling` es un cambio de una línea. Verificado: pipeline completo (`typecheck`/`lint`/`test:coverage`/`build`) limpio, 316 tests → 92.79% cobertura (3 tests nuevos para `PanelShell` — no pueden reproducir el bug de WebKit en sí desde jsdom, que no simula reflow real, pero confirman que el wrapper no rompe nada y que el toggle de `display` siempre queda restaurado). No se puede confirmar en un browser mobile real desde este entorno — pendiente de que el cliente lo pruebe en su celular, específicamente aterrizando en frío en Calendario y en la ficha de un paciente (sin tocar ningún botón antes).

## TR-032: `<main>` sin alto propio explícito — dependía de un `stretch` heredado que fallaba con contenido simultáneamente ancho y alto (Calendario, ficha de paciente)

- **Fecha:** 2026-08-24
- **Fase:** ejecución (novena vuelta sobre TR-024 a TR-031, mismo día, rama `fix/mobile` — TR-031 no resolvió el problema; el cliente confirmó, vía un cuestionario de diagnóstico dirigido, datos clave: el scroll no responde NADA (no es lento ni entrecortado), pasa **solo** en Calendario y en la ficha de un paciente (Turnos/Pacientes/General andan bien), el scroll HORIZONTAL en esas mismas pantallas sí funciona, es independiente del navegador (Safari y Chrome por igual — descarta a WebKit como causa, invalidando el diagnóstico de TR-031), y el contenido visible "se corta de golpe: veo hasta cierta hora y después no hay nada más (ni blanco, termina ahí)")
- **Diagnóstico:** el patrón "se corta de golpe, sin blanco, sin scrollbar" es la firma de un `overflow: hidden` recortando contenido — no la de "un scroll que no responde al gesto". Con eso, más el dato de que el scroll horizontal SÍ funciona en las mismas pantallas (descarta que `<main>` esté totalmente roto), la pista apunta a que `<main>` no queda correctamente ACOTADO en altura para estas dos páginas en particular. `<main>` nunca tuvo un alto propio explícito — dependía enteramente de `align-items: stretch`, heredado de `.panel-shell-h` (el `flex` row padre, `PanelSidebar` + `<main>`), para quedar limitado a la altura del viewport. Ese stretch funcionaba para Turnos/Pacientes/General, pero Calendario y la ficha de un paciente son las dos páginas con contenido simultáneamente MUY ancho (fuerza scroll horizontal, TR-028/029: el calendario en vista Semana, o las tablas de turnos del paciente) Y muy alto — y todo indica que el cálculo de stretch de flexbox no se resuelve de forma confiable cuando el contenido de un flex item es así de grande en las dos direcciones a la vez. Cuando `<main>` no queda acotado, su contenido se desborda hacia `.panel-shell-h` (el padre), que sí tiene `overflow: hidden` — y ESE es el que recorta, sin ofrecer ningún scroll (coincide exactamente con "se corta de golpe... termina ahí").
- **Decisión:** nueva clase `.panel-main-h` (mismo patrón `vh`+`@supports (height:100dvh)` que ya usa `.panel-sidebar-h`, ver TR-029) le da a `<main>` un alto EXPLÍCITO — `calc(100dvh - var(--header-height))`, el mismo cálculo que ya tiene el sidebar — en vez de depender de ningún `stretch` heredado del padre. Con esto, `<main>` queda acotado siempre, sin importar cuánto mida su contenido en ninguna de las dos direcciones, y es su propio `overflow-auto` (no el `overflow-hidden` del padre, que pasa a ser un resguardo de última instancia en vez del mecanismo principal) el que absorbe el resto.
- **Alternativas consideradas:** (a) Sacar `overflow-hidden` de `.panel-shell-h` para que, si `<main>` se desborda, al menos el contenido quede VISIBLE (aunque sin scroll) en vez de cortado — descartada: eso hubiera roto la premisa central de "la página en sí no scrollea" (pedido explícito, TR-026) dejando que el documento (`html`/`body`) volviera a crecer y scrollear, exactamente lo que se vino corrigiendo desde esa ronda. (b) Investigar más a fondo por qué exactamente falla el `stretch` de flexbox en vez de darle a `<main>` un alto explícito — descartada por pragmatismo: un alto explícito elimina la dependencia del comportamiento heredado por completo, en vez de intentar entender/parchear un caso límite de flexbox que ya demostró ser poco confiable en la práctica (dos rondas de diagnóstico fallidas alrededor de esta misma área).
- **Por qué:** El cuestionario de diagnóstico dirigido (en vez de seguir adivinando con otra corrección especulativa) fue lo que permitió descartar la hipótesis de TR-031 (bug de WebKit — inválida, el problema es igual en Chrome) y encontrar el patrón real ("se corta de golpe, sin blanco" = recorte, no scroll inerte) en dos preguntas. Un alto explícito en `<main>`, en vez de confiar en que el `stretch` de flexbox se calcule bien con contenido extremo en las dos direcciones, es la corrección más robusta: elimina la variable en vez de intentar predecir cuándo el navegador la calcula mal.
- **Qué se sacrifica:** Nada de fondo — aditivo (una clase CSS + un className en `app/panel/layout.tsx`), sin tocar modelo de datos ni archivos fuera de `/panel/**`.
- **Reversibilidad:** Alta — sacar `panel-main-h` de `<main>` y la regla de `globals.css` revierte al comportamiento anterior (con el bug) sin tocar nada más. Verificado: pipeline completo (`typecheck`/`lint`/`test:coverage`/`build`) limpio, 316 tests → 92.79% cobertura (sin tests nuevos — cambio puro de CSS, sin lógica nueva que cubrir); CSS de producción inspeccionado, confirmando que Lightning CSS agrupó correctamente `.panel-sidebar-h,.panel-main-h{height:calc(100vh - var(--header-height))}` (y su variante `100dvh` dentro de `@supports`) sin perder ninguna de las dos declaraciones. Sigue pendiente de confirmación real del cliente — el video que envió (`docs/WhatsApp Video 2026-08-24 at 9.51.59 PM.mp4`) no se pudo reproducir en este entorno (sin `ffmpeg` ni visor de video disponible); el diagnóstico de esta ronda se hizo con un cuestionario dirigido en su lugar.

## TR-033: El "gap" entre header y sidebar — el offset de `sticky` se sumaba dos veces sobre el mismo padding

- **Fecha:** 2026-08-24
- **Fase:** ejecución (décima vuelta sobre TR-024 a TR-032, mismo día, rama `fix/mobile` — el cliente mandó capturas de pantalla (el video no se pudo reproducir en este entorno, sin `ffmpeg`) que permitieron ver el bug directamente: en una captura de Calendario recién cargado, el botón "+ Agregar turno" aparece pegado al header, pero los íconos del sidebar (dashboard, calendario, turnos, pacientes) recién aparecen bastante más abajo — una franja vacía de fondo texturado solo en la columna del sidebar, nada en la columna de contenido. El cliente confirmó por separado que la grilla del calendario en sí estaba completa (el "área vacía" de una captura anterior era solo la posición del scroll horizontal, no un bug de renderizado) y que los dos problemas reales eran el gap y el scroll vertical)
- **Diagnóstico:** `PanelSidebar` es `position: sticky` con `top: var(--header-height)` — ese offset tiene sentido en escritorio, donde es el DOCUMENTO el que scrollea y el sidebar necesita saber cuánta altura de header dejar libre antes de "pegarse" mientras se scrollea la página. En mobile, desde TR-026, el documento dejó de scrollear — la raíz de `/panel` (`PanelShell`) ya reserva ese mismo espacio con `padding-top: var(--header-height)`. El offset de `sticky` (que se mide desde el borde de scroll del contenedor, ANTES de descontar el padding) terminaba sumándose una SEGUNDA vez sobre ese padding — el sidebar aparecía renderizado un tramo extra de `header-height` más abajo de lo que le correspondía, dejando la franja vacía observada.
- **Decisión:** `max-md:top-0` en `PanelSidebar` — solo debajo de 768px, el offset de `sticky` pasa a `0` (el padding-top de la raíz ya hace todo el trabajo de compensación); arriba de ese breakpoint sigue con `top-[var(--header-height)]` sin cambios, comportamiento de escritorio intacto.
- **Alternativas consideradas:** Sacar `padding-top` de la raíz y dejar que todo el compensado de header dependa solo del `top` de `sticky` — descartada: `<main>` (hermano del sidebar, sin `position: sticky`) también necesita ese espacio libre arriba, y no tiene ningún mecanismo de "offset de scroll" propio — el padding en el contenedor común es la única forma de compensar a los dos hermanos por igual.
- **Por qué:** Las capturas de pantalla que mandó el cliente fueron decisivas — permitieron ver la asimetría exacta (contenido arranca arriba, sidebar arranca abajo) que ningún cuestionario de texto hubiera descrito con la misma precisión. Con esa asimetría visible, la explicación de "un offset que tenía sentido en un modelo de scroll de documento, pero quedó duplicando trabajo en el modelo de scroll interno nuevo" fue directa.
- **Qué se sacrifica:** Nada de fondo — aditivo (`max-md:top-0`, una clase), sin tocar modelo de datos ni archivos fuera de `/panel/**`.
- **Reversibilidad:** Alta — sacar `max-md:top-0` revierte al comportamiento anterior (con el gap) sin tocar nada más. Verificado: pipeline completo (`typecheck`/`lint`/`test:coverage`/`build`) limpio, 316 tests → 92.79% cobertura (sin tests nuevos — cambio puro de CSS); CSS de producción inspeccionado, `.max-md\:top-0{top:0}` compilado dentro del bloque `max-md` esperado. Pendiente de confirmación real del cliente, junto con TR-032 (scroll vertical), que se deployó en el mismo lote.

## TR-034: Cinco ajustes puntuales tras confirmar el fix de scroll/gap — General, botón de Calendario, alineación de Turnos, sidebar colapsado por defecto, y un fix de escritorio (scrollbar-gutter)

- **Fecha:** 2026-08-24
- **Fase:** ejecución (undécima vuelta sobre TR-024 a TR-033, mismo día, rama `fix/mobile` — el cliente confirmó "bien solucionado" el scroll/gap de la ronda anterior y pidió cinco ajustes más: (1) General se aplasta cuando el sidebar está expandido, con captura; (2) en escritorio el header "se modifica un poco de lugar" al navegar entre secciones; (3) captura de Calendario mostrando el botón "+ Agregar turno" lejos del título "Calendario"; (4) captura de Turnos mostrando la tabla desalineada respecto de la fila de filtros de arriba; (5) pedido adicional a mitad de la ronda: que el sidebar arranque colapsado en la primera vista en mobile)
- **Decisión:**
  1. **General** (`panel/page.tsx`): la grilla de 2 tarjetas pasa de `sm:grid-cols-2` (1 columna por debajo de 640px, sin ningún piso de ancho) a `grid-cols-2` incondicional + `max-md:min-w-[40rem]` — mismo criterio que el resto de `/panel/**` desde TR-028/029: sin un mínimo propio, con el sidebar expandido (w-60, 240px) el ancho disponible se reducía a ~135px en un teléfono común y las tarjetas quedaban aplastadas en una sola columna angosta.
  2. **Botón "+ Agregar turno" en Calendario** (`calendar-view.tsx`): la fila de título tenía `justify-between` sin condición — sobre una fila que en mobile mide 640px+ (el `min-width` del wrapper, TR-029), el botón quedaba pegado al borde derecho de esa fila, fuera de la pantalla visible sin deslizar. `max-md:justify-start` lo deja pegado al título, como pidió el cliente; escritorio sigue con `justify-between` sin cambios (esa fila entra completa en pantalla ahí).
  3. **Tabla de Turnos desalineada** (`turnos-table.tsx`): a la caja de la tabla le faltaba `max-md:w-full` — ya se lo había dado a la fila de filtros (`turnos/page.tsx`) y a las otras tablas (Pacientes, `PacienteTurnosTable`) en TR-029/030, pero se había quedado afuera acá. Sin eso, la caja medía su propio ancho intrínseco en vez de estirarse a coincidir con el wrapper que la envuelve, desalineándose de la fila de arriba al scrollear.
  4. **Sidebar colapsado por defecto en mobile** (`panel-sidebar.tsx`): nuevo hook compartido `useIsomorphicLayoutEffect` (extraído de `panel-shell.tsx`, mismo patrón `vh`+`@supports`/reflow ya usado ahí — ver TR-031) — al montar, si `window.matchMedia("(max-width: 767px)").matches`, arranca `collapsed`. Corre ANTES del primer paint (layout effect, no efecto normal) para que el ajuste nunca se vea como un parpadeo (el HTML servido por el servidor, sin `window`, sigue arrancando expandido — nadie lo ve así en mobile).
  5. **Header que "se corre" en escritorio al navegar** (`globals.css`, `html { scrollbar-gutter: stable }`): el header es `position: fixed` a lo ancho del viewport, pero un scrollbar vertical de verdad (no overlay, el caso típico en Windows/Linux) le resta ~15-17px al ancho disponible mientras está presente — y páginas distintas de `/panel/**` (Turnos con muchas filas vs. General con dos tarjetas) tienen alturas de contenido distintas, así que el scrollbar aparece o desaparece según la página, corriendo el contenido del header esos mismos píxeles de un lado a otro. `scrollbar-gutter: stable` reserva ese espacio siempre, haya o no haya contenido para scrollear, eliminando la diferencia entre páginas.
- **Alternativas consideradas:** (a) Para el sidebar colapsado, decidir el estado inicial directo en el `useState`, chequeando `window` ahí mismo — descartada: el inicializador de `useState` corre tanto en el servidor (sin `window`, SSR) como en el cliente durante la hidratación, y si dieran resultados distintos sería un mismatch de hidratación real (React lo detecta y tira warnings, en el peor caso un glitch visual). El layout effect evita el problema por completo, corriendo solo en el cliente y solo una vez montado. (b) Para el header en escritorio, forzar `overflow-y: scroll` (scrollbar siempre visible) en vez de `scrollbar-gutter: stable` — descartada: eso muestra un scrollbar VACÍO incluso en páginas sin nada para scrollear, un cambio visual más notorio que simplemente reservar el espacio sin necesariamente mostrar la barra.
- **Por qué:** Los cuatro primeros ajustes son correcciones directas y sin ambigüedad sobre capturas de pantalla concretas — mismo patrón ya aplicado en rondas anteriores (min-width + `w-full`), solo faltaba aplicarlo consistentemente en los lugares señalados. El quinto (scrollbar-gutter) es la explicación más común y bien documentada para "el header se corre entre páginas" en cualquier sitio con contenido de alto variable — una vez identificado el síntoma exacto (desplazamiento del header, no del contenido), la causa técnica (scrollbar apareciendo/desapareciendo) es la explicación estándar.
- **Qué se sacrifica:** Nada de fondo — todo aditivo, sin tocar modelo de datos. `scrollbar-gutter: stable` es la única regla de esta ronda que aplica a TODO el sitio (no solo `/panel/**`) — deliberado, ya que el problema de fondo (scrollbar apareciendo/desapareciendo corriendo el header) no es exclusivo de gestión de clínica, aunque ahí fue donde se notó.
- **Reversibilidad:** Alta — cada cambio es independiente y reversible por separado (clases `max-md:`, un hook chico, una propiedad CSS). Verificado: pipeline completo (`typecheck`/`lint`/`test:coverage`/`build`) limpio, 318 tests → 92.82% cobertura (2 tests nuevos para el sidebar colapsado en mobile); CSS de producción inspeccionado, confirmando `scrollbar-gutter:stable`, `.max-md\:justify-start{justify-content:flex-start}` y el resto de las clases nuevas compiladas donde correspondía. Pendiente de confirmación real del cliente.

## TR-036: Auth/onboarding nuevo — se extiende el JWT-en-Go custom, no se agrega NextAuth/Better Auth/Supabase/Lucia

- **Fecha:** 2026-08-25
- **Fase:** plan → ejecución (`docs/feature-sumarte-login.md`, feature completa: Google OAuth + verificación de mail + wizard de 3 pasos + clínicas tipo organización)
- **Decisión:** la nueva capa de auth se construye extendiendo el patrón custom ya usado (Go firma/valida, Next.js solo relee la cookie) — ninguna librería de auth de Next.js entra al proyecto.
- **Alternativas consideradas:** NextAuth/Auth.js, Better Auth, Supabase Auth, Lucia — todas asumen que Next.js mismo posee la sesión/DB/adapters, lo que rompe la invariante BFF no negociable de CLAUDE.md ("el navegador nunca llama a la API Go directo... nunca un fetch nuevo desde Client Component"). Marcuzzi_Madryn (mismo stack, spec §9) tiene Google OAuth funcionando en producción sin ninguna de estas librerías — precedente directo de que no hacen falta ni para OAuth.

- **Qué se sacrifica:** más código propio que mantener (session.go, onboarding.go, etc.) en vez de configuración de una librería — aceptado, es el mismo tradeoff que ya se hizo para el auth original (TR-005).

## TR-037: Sesión server-side (tabla `Session`) reemplaza al JWT stateless

- **Fecha:** 2026-08-25
- **Fase:** plan → ejecución
- **Decisión:** se abandona el JWT stateless de TR-005 (7 días, HS256, sin revocación posible) por sesiones opaquen-token en Postgres (`db.Session`, `internal/auth/session.go`) — mismo patrón de hash que `VerificationToken` (32 bytes CSPRNG en la cookie, solo el SHA-256 persiste).
- **Alternativas consideradas:** mantener JWT + una tabla de blocklist de tokens revocados — descartada, técnicamente equivalente en complejidad a una tabla de sesiones de verdad, pero peor: todavía habría que consultar la blocklist en cada request, sin ganar nada del "stateless" que se supone es la ventaja del JWT.
- **Por qué:** la spec exige literalmente "logout invalida la sesión en el servidor" y "cambiar la contraseña cierra las sesiones abiertas en otros dispositivos" — ninguna de las dos es posible con un JWT puro. La rotación de sesión en login/verificación de mail (mitiga session fixation) también sale gratis: cada `NewSession`/`RotateSession` emite un token nuevo, nunca reutiliza uno existente.
- **Qué se sacrifica:** un lookup a Postgres en cada request protegido (antes: solo verificar una firma HMAC, sin ir a la base) — el `LastSeenAt` se actualiza con throttle de 5 minutos para no convertir cada request en un `UPDATE` de todos modos.
- **Reversibilidad:** Media — volver a JWT stateless implicaría resignar la invalidación server-side, un requisito explícito de seguridad, no sería un simple revert.

## TR-038: Google OAuth — flujo popup + Authorization Code, sin PKCE (documentado, no simulado)

- **Fecha:** 2026-08-25
- **Fase:** plan (decisión #1, confirmada explícitamente con el cliente vía pregunta directa) → ejecución
- **Decisión:** mismo patrón ya validado en producción por Marcuzzi_Madryn — botón popup (Google Identity Services, `initCodeClient`), el `code` viaja a una Server Action que lo manda a Go, que lo intercambia server-to-server (`internal/googleauth`) usando el client secret (nunca sale del backend). Se agrega un `state` propio firmado con HMAC (`internal/http/oauthstate.go`) y verificado con ventana de 10 minutos.
- **Alternativas consideradas:** flujo de redirect completo con una Route Handler `/auth/google/callback` y `redirect_uri` en allowlist + PKCE real — es lo que la letra de la spec §7 describe (`state + nonce + PKCE`), pero PKCE existe específicamente para proteger clients PÚBLICOS que no pueden guardar un secret (SPAs, apps móviles) — acá el secret vive solo en Go, nunca en el navegador, así que PKCE no cierra ningún vector de ataque real que el `state` firmado no cierre ya. Implementarlo de todos modos hubiera sido superficie nueva sin beneficio de seguridad medible.
- **Por qué:** reutilizar un patrón ya en producción reduce la superficie de bugs nuevos a cero para la parte más sensible (intercambio de tokens con un proveedor externo).
- **Qué se sacrifica:** no hay `redirect_uri` en allowlist porque no hay redirect — el whitelisting equivalente es que `GOOGLE_REDIRECT_URI` es una env var fija del backend (`"postmessage"`, el valor mágico de Google para el flujo popup), no algo que el cliente pueda influir.
- **Reversibilidad:** Media — migrar a redirect completo más adelante (si Google deprecara el flujo popup) es un cambio de superficie, no de modelo de datos.

## TR-040: argon2id nuevo, pero `security.Verify` sigue aceptando bcrypt legacy sin forzar rehash

## TR-041: Rate limit por-cuenta en Postgres, por-IP en memoria — no sobrevive a escalar horizontal

- **Fecha:** 2026-08-25
- **Fase:** ejecución (`internal/ratelimit`)
- **Decisión:** límites por-cuenta (login, registro, reenvío, reset) persisten en una tabla-contador por ventana fija (`db.AuthRateCounter`, upsert, no fila-por-intento). Límites por-IP viven en memoria (`sync.Map`-like con mutex), reseteados si el proceso reinicia.
- **Qué se sacrifica:** con más de una instancia del backend corriendo (horizontal scaling), cada instancia tendría su propio contador por-IP — el límite real efectivo sería N veces el configurado, con N instancias. El límite por-cuenta (en Postgres, compartido) sigue siendo correcto siempre.
- **Por qué no resolverlo ahora:** el MVP corre en una sola instancia (mismo criterio que TR-021, un solo entorno en Render); agregar Redis o un contador centralizado sería infraestructura nueva sin necesidad actual.
- **Reversibilidad:** Alta — migrar el contador por-IP a Redis (o a la misma tabla Postgres) es un cambio aislado a `internal/ratelimit`, sin tocar los call sites de `auth.go`.

## TR-047: Log de auditoría — esquema existía desde TR-036, se detectó sin cablear y se cerró en la misma feature

## TR-048: Bug real en producción — CSP sin nonce bloqueaba la hidratación de toda la app

- **Fecha:** 2026-08-26
- **Fase:** ejecución (bug reportado por el cliente tras el merge a `dev` de TR-036 a TR-047)
- **Síntoma:** tras deployar, el Home perdía casi todo su texto/botones, `/ingresar` y `/sumarse` cargaban en blanco. Consola: la CSP bloqueaba "inline script" en varias páginas, más `React error #412` (hydration mismatch).
- **Causa real:** `apps/web/src/middleware.ts` (TR-036/spec §7) seteaba `script-src` sin `'unsafe-inline'` **ni nonce** — Next.js App Router inyecta sus propios `<script>` inline para hidratar/streamear RSC (`self.__next_f.push(...)`), y la CSP los bloqueaba a todos. El bug no se detectó antes de mergear porque la verificación de esa fase fue solo `curl`/tests contra la API — nunca se abrió una página real en un navegador contra un build de producción.
- **Decisión:** nonce por request (patrón oficial de Next.js, ver https://nextjs.org/docs/app/guides/content-security-policy) — la CSP de la respuesta lleva `'nonce-<valor>'` en `script-src`, y el mismo valor se reenvía como header de REQUEST (`x-nonce`) para que el renderer de Next lo use al estampar sus propios `<script>`. Mantiene `script-src` sin `unsafe-inline` (el objetivo original de TR-036), a diferencia de la alternativa más simple de agregar `unsafe-inline`.
- **Alternativas consideradas:** (1) agregar `'unsafe-inline'` a `script-src` — más simple pero abandona el objetivo explícito de la spec ("CSP sin unsafe-inline donde sea viable"); (2) `'strict-dynamic'` en vez de mantener el allowlist de hosts — descartado por innecesariamente más complejo para este caso (el allowlist de `accounts.google.com`/`challenges.cloudflare.com` ya resuelve los dos únicos scripts de terceros que carga la app).
- **Qué se sacrifica:** nada funcional — es aditivo sobre TR-036. Sí queda como lección: **cualquier cambio a `middleware.ts` de acá en más debe verificarse contra un build de producción real (`pnpm build && pnpm start`) en un navegador, no solo con tests/curl**, antes de mergear a `dev`.
- **Reversibilidad:** Alta. Test de regresión agregado en `apps/web/src/middleware.test.ts` (verifica que el nonce se reenvía en el header de request, no solo en el de la respuesta — el paso que faltaba).

## TR-049: `getMe()` no puede limpiar la cookie de sesión inválida — Next.js lo prohíbe fuera de una Server Action/Route Handler

- **Fecha:** 2026-08-26
- **Fase:** ejecución (segundo bug real en producción del mismo día, después de TR-048 — reportado por el cliente con el log real de Render)
- **Síntoma:** `GET /sumarse` y `GET /ingresar` devolvían 500 en Render (no en local con `pnpm start`/`next start` — solo se reprodujo con el mismo Dockerfile/`output: standalone` que usa Render, mandando un `dm_session` inválido). Log real del servicio: `Error: Cookies can only be modified in a Server Action or Route Handler` (digest `362305294@E1180`).
- **Causa real:** `getMe()` (`lib/session.ts`) intentaba `clearSessionCookie()` (un `cookies().delete()`) cada vez que `apiMe()` devolvía `!ok` — pero `getMe()` se llama desde Server Components durante el RENDER de una página (`/sumarse`, `/ingresar`, guards de `/panel`, `site-header.tsx`), no desde una Server Action ni un Route Handler. Next.js App Router prohíbe mutar cookies fuera de esos dos contextos — tira, no advierte. Cualquier visitante con una cookie `dm_session` inválida (la causa más probable: quedó de antes de esta feature, cuando la sesión era JWT y no un token opaco — ese valor viejo ahora falla la validación en `apiMe`) crasheaba la página entera con un 500.
- **Por qué no se detectó en la verificación de TR-036/TR-037:** los tests automatizados mockean `apiMe`/`cookies()` (nunca ejercitan la restricción real del framework), y la verificación manual de esa fase nunca probó el caso "visitante con una cookie de sesión vieja/inválida real" contra un build de producción.
- **Decisión:** `getMe()` deja de intentar limpiar la cookie — si `apiMe()` dice que el token no sirve, devuelve `null` y no toca la cookie. La única `clearSessionCookie()` que queda activa es la de `logoutAction` (`app/actions/auth.ts`), que sí corre dentro de una Server Action.
- **Qué se sacrifica:** una cookie de sesión inválida queda en el navegador del visitante hasta que haga login u logout explícito (en vez de auto-limpiarse en la primera visita) — inofensivo: `apiMe` la vuelve a rechazar en cada request sin loop ni efecto visible, es shipear una cookie de más, no un bug.
- **Reversibilidad:** Alta. Si más adelante hace falta auto-limpiar cookies inválidas de verdad, el lugar correcto es `middleware.ts` (corre en un contexto que sí puede mutar cookies) o un Route Handler dedicado — no un helper de lectura llamado desde Server Components.

## TR-052: Cuentas abandonadas sin verificar — se borran, no quedan "reservando" el mail para siempre

- **Fecha:** 2026-08-26
- **Fase:** ejecución (pedido explícito del cliente, con seguimiento propio: "el manejo de cuentas sin verificar... se debería eliminar de la base de datos y rehacer el proceso" + "¿si vuelvo después de un tiempo y no hay cuenta que confirmar, me tira automáticamente al paso anterior?")
- **Decisión, dos puntos de entrada complementarios** (ambos con el mismo umbral: `cuentaAbandonadaTTL`, 24h — nombre actualizado en TR-055, que introduce un `verificationCodeTTL` de 15 min SEPARADO para el código en sí; el umbral de "cuenta abandonada" sigue siendo el de 24h, deliberadamente más largo):
  1. **`register()`** (`internal/http/auth.go`): si alguien intenta registrarse con un mail que ya existe pero sigue sin verificar y su cuenta pasó el TTL (o `AutoVerifyEmail` está activo, sin esperar TTL — TR-051, no hay verificación real que esperar en ese modo), la cuenta vieja se borra (`Unscoped().Delete`, no soft-delete — el índice único de `email` no excluye soft-deleted, así que un soft-delete dejaría el mail inutilizable igual) y el request cae al alta normal, como si nunca hubiera existido.
  2. **`meHandler()`** (`internal/http/me.go`): cubre el caso que (1) NO alcanza — alguien que simplemente vuelve a abrir la app con la sesión que ya tenía, sin volver a pasar por el formulario de registro. Sin `AutoVerifyEmail`, si la cuenta del propio caller está sin verificar y pasó el TTL, se borra ahí mismo y el endpoint responde 404 "usuario no encontrado" — exactamente la misma respuesta que si esa cuenta nunca hubiera existido. El wizard (`sumarse-wizard.tsx`), al recibir `me: null` de `GET /me`, muestra el Paso 1 de cero — nunca queda mostrando "revisá tu correo" indefinidamente para un código que ya venció.
- **Por qué dos lugares y no uno solo (ej. un cron job):** un job en background es infraestructura nueva (scheduler, ventana de ejecución, qué pasa si el proceso está caído) para un problema que se resuelve completo con lógica perezosa en los dos puntos donde de verdad importa — el momento de registrarse de nuevo, y el momento de preguntar "¿quién soy?". Ninguna cuenta abandonada se vuelve visible para nadie más mientras tanto (nunca se lista ni se expone), así que no hay urgencia de limpieza proactiva fuera de esos dos momentos.
- **Qué se sacrifica:** una cuenta abandonada ocupa una fila en la base entre el momento en que se abandona y el momento en que alguien (el mismo dueño u otro registro con el mismo mail) la toca — aceptable, es exactamente el mismo tipo de fila temporal que ya tolera cualquier sistema con verificación por mail.
- **Reversibilidad:** Alta — es lógica pura de aplicación, sin infraestructura nueva; ambos puntos comparten la misma constante de TTL, así que cambiarla es un solo lugar.

## TR-055: Verificación de mail por código de 6 dígitos, no por link — supersede TR-043

- **Fecha:** 2026-08-26
- **Fase:** ejecución (pedido explícito del cliente, probando el registro en producción: "en vez de que sea un link de confirmación, quiero un código de 6 dígitos mejor")
- **Decisión:** el mail de verificación manda un código numérico de 6 dígitos (`security.NewNumericCode`, `crypto/rand`, no `math/rand`) en vez de un link con token de 32 bytes. Mismo criterio de storage que antes (spec §7: solo se persiste el hash SHA-256, nunca el código en claro, reusando `security.HashToken`/`db.VerificationToken`). `POST /auth/verificar-email` pasa de recibir `{token}` a `{email, codigo}` — un código de 6 dígitos no es único globalmente (a diferencia de un token de 256 bits), así que hace falta el mail para saber contra qué cuenta compararlo; la búsqueda queda scopeada por `user_id` además de por el hash.
- **TTL más corto y desacoplado del umbral de "cuenta abandonada":** el código vence en 15 minutos (`verificationCodeTTL`), no en 24h — estándar para un código que la persona escribe mientras sigue mirando la pantalla donde se registró, no algo pensado para abrir "más tarde" como un link. El umbral de "cuenta abandonada" de TR-052 (ahora `cuentaAbandonadaTTL`, sigue en 24h) se separó a propósito de este TTL: un código vencido a los 15 minutos no significa que la persona abandonó el registro (puede pedir uno nuevo con "reenviar" sin perder su sesión ni sus datos), recién a las 24h sin verificar se considera abandonada de verdad.
- **Límite de intentos por CUENTA, no solo por IP — la razón de seguridad no negociable de este cambio:** un código de 6 dígitos tiene 10^6 combinaciones, muchísima menos entropía que el token de 32 bytes que reemplaza (2^256). El límite por IP que ya existía (`LimitTokenConfirmPerIP`, 30/hora) no alcanza solo — un atacante puede rotar de IP para seguir probando contra la MISMA cuenta. Se agregó `LimitConfirmCodePerAccount` (8 intentos/15 min por cuenta, `ratelimit.AccountLimiter`, scope nuevo `RateLimitScopeConfirmCode`), independiente de la IP de origen. De paso se corrigió un bug real preexistente: el endpoint compartía el scope `"login"` con el rate limit de login por IP (copia sin ajustar de una versión anterior) — ahora tiene su propio scope.
- **UX: un solo componente compartido (`ConfirmarCodigoForm`) en tres pantallas** — antes había un botón dedicado solo alcanzable desde el link del mail (`/verificar-mail`, con `ConfirmarMailButton`, eliminado). Ahora el código se puede escribir sin salir de donde ya se estaba: inline en `RevisaCorreo` (`/sumarse`, mail ya conocido por contexto — campo fijo, no editable), inline en el aviso de "mail no verificado" de `/ingresar` (mismo criterio), y en `/verificar-mail` como acceso de respaldo para quien abre el código en otro dispositivo sin sesión (ahí el mail queda editable, prellenado desde `?email=` si viene en la URL).
- **Alternativas consideradas:** guardar el código en texto plano en la fila del usuario (patrón de Marcuzzi_Madryn, `Usuario.CodigoConfirmacion *string`) — descartada: contradice el "no negociable" de la spec §7 de este proyecto ("en base de datos se guarda solo el hash, nunca el token en claro"), que ya se venía respetando para el token de link; no hay motivo para bajar ese estándar solo porque el valor en sí es más corto. Se mantuvo la tabla `VerificationToken` existente sin cambios de esquema — el código es, para la base, un "token" más, solo que de 6 dígitos en vez de 43 caracteres base64url.
- **Qué se sacrifica:** nada del checklist de seguridad original — el link tenía 2^256 de entropía "gratis" por diseño; un código de 6 dígitos necesita el límite de intentos por cuenta para llegar a un nivel de seguridad práctico equivalente, y ya quedó implementado. `/verificar-mail?token=...` (el link viejo) ya no existe como concepto — cualquier mail viejo en tránsito con ese formato de link, si quedó alguno en un buzón real durante el rollout, dejaría de funcionar (aceptable, es justo el cambio pedido).
- **Reversibilidad:** Media — volver a un link requeriría revertir el cambio de contrato de `POST /auth/verificar-email` (`{token}` en vez de `{email, codigo}`) y el frontend correspondiente; el mecanismo de storage (hash-only) es idéntico en ambos casos, así que esa parte no cambiaría.

## TR-056: Registrarse con un mail sin verificar existente SOBREESCRIBE la cuenta, no la trata como "ya existe" — simplifica y reemplaza el mecanismo TTL de TR-052 en `register()`

- **Fecha:** 2026-08-26
- **Fase:** ejecución (pedido explícito del cliente probando el flujo completo: "cuál sería el caso de que me confundí de mail... qué ocurre si quiero crear con el mismo mail y diferente contraseña... si el mail existe y está en estado de verificación, sobreescribir los datos y volver a la verificación")

Esto **elimina** el borrado (`Unscoped().Delete`) que tenía `register()` en TR-052 — ya no hace falta, actualizar en el lugar es más simple y no deja un hueco de "la fila no existe por un instante" a mitad de transacción.

## TR-059: Header con sesión vieja tras verificar/loguearse (bug real) + tarjetas del modal de bienvenida más anchas y con scroll interno

- **Fecha:** 2026-08-26
- **Fase:** ejecución (bug real reportado por el cliente probando el flujo en producción: "cuando termino de verificar mi cuenta y me lleva a la pestaña de seleccionar servicios hay algunos errores, primero el header que aparece corresponde al home para un usuario no logeado, esto se corrige al refrescar la página... segundo los formularios[del modal de bienvenida], son tan largos que sobresalen de la página, deberían estar más delimitados y contenidos")

## TR-061: Investigación de un reporte de "cuenta hijackeable" (sin bug real) + hardening defensivo en `verificarEmail` + se saca "Volver al inicio" del header

- **Fecha:** 2026-08-26
- **Fase:** ejecución (reporte del cliente, urgente: "hay un error critico! me deja crear una cuenta con un mail de una cuenta ya creada!" — luego, tras revisar de nuevo: "cuando pongo un mail de una cuenta ya creada me deja pasar al paso de verificar mail, pero no me llega nada")
- **Investigación:** se auditó `register()` en TODAS las versiones desplegadas hoy (según el historial real de CI/deploy en GitHub Actions, no solo el HEAD de `dev`) — ninguna permite sobreescribir ni emitir sesión para una cuenta con `EmailVerifiedAt` seteado. El síntoma reportado (pasar al paso de código sin que llegue nada) es exactamente el comportamiento esperado del anti-enumeración de la spec §7: la respuesta a "registrarse con un mail ya verificado" es IDÉNTICA a un alta nueva (mismo `mensaje`, mismo status, sin token) para no revelar si esa cuenta existe — pero al ser una cuenta verificada, `register()` nunca genera ni manda un código real para ese intento. El cliente confirmó que no llegó ningún mail — consistente con que la cuenta SÍ estaba protegida, no con un hijack. **Conclusión: no hay bug de seguridad.**
- **Hardening igual aplicado (cinturón y tirantes):** `verificarEmail()` no tenía un chequeo explícito de `user.EmailVerifiedAt != nil` antes de procesar un código — no se encontró forma de explotarlo (el código se valida contra `user_id` específico, no alcanza con conocer un código válido de otra cuenta), pero un guard explícito ahí es más barato que confiar en que ningún otro punto del código deje de generarle un token válido a una cuenta verificada. Ahora rechaza con el mismo mensaje genérico (`mensajeCodigoInvalido`) sin importar si el código en sí era válido.
- **Decisión — "Volver al inicio" fuera del header:** pedido explícito del cliente en el mismo mensaje. Con el logo ya yendo siempre a `/` (TR-060), el link quedaba redundante — se borra `components/volver-al-inicio-link.tsx` (y su test) por completo, ya no tiene otro uso.
- **Reversibilidad:** Alta en ambos casos — el hardening es un guard adicional sin cambiar ningún contrato; sacar el link es puramente de presentación.
