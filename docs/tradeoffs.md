## TR-001: Tipos de consulta como catálogo fijo por profesional, no tags libres *(reconstruida)*

- **Fecha:** anterior a Sprint 1 (fecha exacta no recuperada)
- **Fase:** plan — responde spec §7, pregunta 1 ("¿Cuáles son los tipos de consulta reales a soportar en el MVP?")
- **Decisión:** `tipo_consulta` es un catálogo **por profesional** (no global, a diferencia de `especialidad` — ver TR-004), sembrado automáticamente al registrarse con dos valores fijos: "Consulta general" y "Urgencia", cada uno con un color asociado (los tokens `cascarón`/`urgencia` del Sistema Cascarón, TR-010). El profesional elige entre estos al crear un turno — no es un campo de texto libre.
- **Alternativas consideradas** *(reconstruida)*: (a) catálogo global compartido por todos los profesionales — descartada, cada clínica maneja categorías propias de facto; (b) campo de texto libre sin catálogo — descartada, rompe la diferenciación de color por tipo en el calendario, que es un requisito explícito de la spec.
- **Por qué** *(reconstruida)*: la spec pedía "al menos un segundo tipo de consulta" para poder probar la diferenciación de color del calendario de verdad — sembrar dos valores concretos (no dejarlo vacío) resuelve la pregunta abierta sin esperar una respuesta del cliente que hubiera bloqueado Sprint 2.
- **Qué se sacrifica:** el profesional no puede crear tipos de consulta propios en el MVP — vive fijo con "Consulta general"/"Urgencia" hasta que se confirme la lista real (spec §7, pregunta 1 seguía abierta).
- **Reversibilidad:** Alta — es agregar un CRUD sobre una tabla que ya existe, sin cambios de modelo.

## TR-002: Validaciones de DNI/teléfono/mail en el formulario público *(reconstruida)*

- **Fecha:** anterior a Sprint 1 (fecha exacta no recuperada)
- **Fase:** plan — responde spec §7, pregunta 2 ("¿hay reglas de formato/obligatoriedad ya definidas?")
- **Decisión:** reglas concretas asumidas ante la falta de definición: DNI numérico de 7-8 dígitos (`^\d{7,8}$`), teléfono argentino de 10-13 dígitos con un "+" líder opcional (`^\+?\d{10,13}$`), email con el patrón estándar `^[^\s@]+@[^\s@]+\.[^\s@]+$`. Aplicadas en dos capas — `internal/http/turno_publico.go` (backend, fuente de verdad) y replicadas en el frontend (`PedirTurnoForm`, `EditarPacienteModal`) para feedback inmediato antes de tocar la red.
- **Alternativas consideradas** *(reconstruida)*: (a) sin validación de formato, solo obligatoriedad — descartada, un DNI o teléfono con formato inválido llega igual al panel del profesional y ensucia su lista de pacientes; (b) validación asíncrona contra un servicio externo (RENAPER, etc.) — descartada por alcance, fuera de lo que pide el MVP.
- **Por qué** *(reconstruida)*: son las reglas mínimas necesarias para que el turno pendiente que llega desde la página pública tenga datos de contacto utilizables — sin esto, el profesional podría recibir un DNI con letras o un teléfono sin dígitos suficientes para reconocer al paciente.
- **Qué se sacrifica:** son reglas asumidas, no confirmadas por el cliente — si el DNI real necesita otro formato (extranjeros, por ejemplo) esto habría que revisarlo.
- **Reversibilidad:** Alta — son dos regex en un único lugar de cada lado (`turno_publico.go` y `pedir-turno-form.tsx`), fáciles de ajustar.

## TR-003: Envío del formulario público vía link `wa.me`, no WhatsApp Business API *(reconstruida)*

- **Fecha:** anterior a Sprint 1 (fecha exacta no recuperada)
- **Fase:** plan — responde spec §7, pregunta 3 ("¿es un link `wa.me` con mensaje prellenado, o una integración con API de WhatsApp Business?")
- **Decisión:** al confirmar el formulario público de pedir turno, el frontend arma un link `https://wa.me/{numero}?text={mensaje prellenado}` client-side con los datos que el propio profesional publicó (su teléfono) — en paralelo, el backend ya creó el `turno` en estado `pendiente` de forma independiente. No hay integración con la API de WhatsApp Business: ningún envío/confirmación de entrega real, es un link que abre WhatsApp (web o app) del lado del visitante. `CLAUDE.md` es explícito: este camino **no** usa el patrón de interfaz dev/prod reservado para integraciones de backend — ese patrón queda para recordatorios automatizados futuros (Fase 2).
- **Alternativas consideradas** *(reconstruida)*: (a) integración real con WhatsApp Business API — descartada por alcance/costo (requiere cuenta de negocio verificada, aprobación de Meta, y una interfaz dev/prod de verdad); (b) no ofrecer WhatsApp en el MVP, solo el turno pendiente en el panel — descartada, la spec pide explícitamente que el paciente pueda "además" escribirle directo al profesional.
- **Por qué** *(reconstruida)*: `wa.me` no requiere backend, credenciales, ni aprobación de terceros — el turno pendiente en el panel es la fuente de verdad real (no depende de que el link se abra con éxito), el WhatsApp es una comodidad extra para el paciente.
- **Qué se sacrifica:** sin confirmación de entrega ni reintento — si el visitante no tiene WhatsApp instalado/accesible, el link simplemente no hace nada útil (mitigado: el turno pendiente ya existe en el panel de todos modos, ver riesgo R4 de `implementation-plan.md`).
- **Reversibilidad:** Media — migrar a la API real de WhatsApp Business es un cambio de arquitectura (backend, credenciales, interfaz dev/prod), no un ajuste menor.

## TR-004: Especialidades como catálogo cerrado predefinido por Mirage, no tags libres *(reconstruida)*

- **Fecha:** anterior a Sprint 1 (fecha exacta no recuperada)
- **Fase:** plan — responde spec §7, pregunta 4 ("¿es una lista cerrada predefinida por Mirage, o el profesional puede crear tags libres?")
- **Decisión:** `especialidad` es un catálogo **global** (a diferencia de `tipo_consulta`, por profesional — TR-001), predefinido y sembrado por Mirage (`internal/db.SeedEspecialidadesCatalogo`, `CatalogoEspecialidades` en `seed.go`). El profesional elige de esta lista cerrada al registrarse (`especialidadIds` en el wizard de alta) — no puede crear especialidades propias. Tabla puente `profesional_especialidad` (N:M).
- **Alternativas consideradas** *(reconstruida)*: (a) tags libres por profesional — descartada, rompe la utilidad del filtro por especialidad en el buscador público (spec §6) si cada profesional escribe la suya con su propia ortografía/criterio; (b) catálogo cerrado pero editable solo por un admin de Mirage vía panel propio — de hecho es lo implementado, sin un panel de admin todavía (se edita el seed directo).
- **Por qué** *(reconstruida)*: un catálogo cerrado es lo único que permite que el filtro de especialidad del buscador (spec §6) funcione de verdad — "Ortodoncia" tiene que significar lo mismo para todos los profesionales que la eligen.
- **Qué se sacrifica:** un profesional con una especialidad realmente fuera del catálogo no tiene forma de registrarla — depende de que Mirage la sume al seed.
- **Reversibilidad:** Media — sumar especialidades nuevas al catálogo es trivial (una fila más en `CatalogoEspecialidades`); pasar a tags libres sería un cambio de modelo más profundo (perder la tabla puente cerrada).

## TR-005: Autenticación email+password propia (JWT), sin login social en el MVP *(reconstruida)*

- **Fecha:** anterior a Sprint 1 (fecha exacta no recuperada)
- **Fase:** plan — responde spec §7, pregunta 5 ("no se especifica el mecanismo de login/registro")
- **Decisión:** autenticación propia con email+password (`internal/http/auth.go`), password hasheado con bcrypt, JWT de sesión (7 días, mismo TTL en `apps/api` y en la cookie de `apps/web`) en cookie `httpOnly` (spec §9.3) — nunca en `localStorage`. Sin OAuth/login social (Google, etc.) en el MVP.
- **Alternativas consideradas** *(reconstruida)*: (a) login social (Google) — descartada del MVP por alcance/tiempo, aunque queda como backlog explícito de Fase 2 si el cliente confirma que hace falta; (b) sesiones de servidor con almacenamiento en base en vez de JWT — descartada, JWT es el mismo patrón ya validado en Marcuzzi_Madryn.
- **Por qué** *(reconstruida)*: email+password es el mecanismo mínimo funcional sin depender de configurar credenciales OAuth de terceros antes de poder probar el resto del producto — reduce superficie de configuración en Sprint 0.
- **Qué se sacrifica:** sin "iniciar sesión con Google", cada profesional necesita recordar una contraseña más — aceptado como backlog de Fase 2 (ver `docs/implementation-plan.md` sección 6).
- **Reversibilidad:** Media — sumar OAuth es aditivo (no reemplaza el mecanismo actual), pero toca `auth.go`, el modelo de `Profesional` y el flujo de `/ingresar`/`/sumarse`.

## TR-006: El exclusion constraint de turnos aplica solo a `estado='agendado'` *(reconstruida)*

- **Fecha:** anterior a Sprint 1 (fecha exacta no recuperada)
- **Fase:** plan
- **Decisión:** el `EXCLUDE USING gist` sobre `(profesional_id, rango_horario)` en la tabla `turno` (el requisito no negociable de spec §4.3: turnos sin solapamiento) solo es válido para filas en estado `agendado`. Los turnos `pendiente` —recién llegados del formulario público, sin horario todavía— no tienen `rango_horario` fijo (columna nullable), así que no participan del constraint hasta que se confirman en el modal "+ Agregar turno" (T2.4) y pasan a `agendado`.
- **Alternativas consideradas** *(reconstruida)*: (a) exigir un horario tentativo desde que el turno es `pendiente` — descartada, el paciente no elige horario en el formulario público (spec §4.4), solo pide turno; inventar uno arbitrario para satisfacer el constraint sería un dato falso; (b) constraint separado por estado, permitiendo solapamiento entre `pendiente`s — es la opción elegida, ya que dos pedidos pendientes en el mismo rango no son un problema real hasta que alguno se confirma.
- **Por qué** *(reconstruida)*: el constraint tiene que reflejar la garantía real del negocio — "dos turnos *confirmados* de un mismo profesional no se solapan" — no "dos *pedidos* no se solapan", que no tiene sentido antes de que exista un horario de verdad.
- **Qué se sacrifica:** nada de fondo — es la lectura correcta del propio modelo de datos, no una concesión.
- **Reversibilidad:** Baja/Media — es un constraint a nivel de base de datos (migración), tocarlo requiere una migración nueva, no solo un cambio de código de aplicación.

## TR-007: Gate de coverage 80% activo desde Sprint 0, no como iniciativa tardía *(reconstruida)*

- **Fecha:** anterior a Sprint 1 (fecha exacta no recuperada)
- **Fase:** plan — lección aplicada de la experiencia de Marcuzzi_Madryn (mismo stack/modo de trabajo, spec §9), donde este gate se agregó recién al final del proyecto
- **Decisión:** CI (`.github/workflows/ci.yml`) falla si la cobertura de cualquiera de los dos stacks cae debajo del 80%, activo desde el primer PR de código de negocio (T0.4) — no un retrofit al final. Backend: tests contra Postgres real (`internal/testdb`), nunca mocks, cada test en su propia transacción revertida, con una red de seguridad (`requireTestDatabaseName`) que impide correr la suite contra una base que no termine en `_test`. Frontend: Vitest + Testing Library + jsdom, con `fetch`/Server Actions siempre mockeados, y las páginas Server Component (`src/app/**/page.tsx`) excluidas del cálculo de cobertura — se verifican mejor con QA end-to-end (T5.4) que con unit tests.
- **Alternativas consideradas** *(reconstruida)*: (a) agregar el gate más adelante, cuando el producto esté más maduro (lo que pasó en Marcuzzi_Madryn) — descartada explícitamente, es la lección que este proyecto dice no repetir; (b) mockear la capa de datos del backend en vez de una base real — descartada, el exclusion constraint (TR-006) no se puede probar con sentido contra un mock.
- **Por qué:** un gate agregado tarde encuentra código ya escrito sin tests, mucho más caro de cubrir retroactivamente que de mantener alto desde el día 1.
- **Qué se sacrifica:** cada sprint corre más lento al principio (hay que escribir tests junto con cada feature, no después) — aceptado a cambio de nunca acumular deuda de cobertura.
- **Reversibilidad:** Alta — es un umbral en configuración de CI/Vitest, bajarlo o subirlo es un cambio de una línea (aunque bajarlo sería ir contra la lección que motivó la decisión).

## TR-008: Sin CAPTCHA/Turnstile en el formulario público del MVP *(reconstruida)*

- **Fecha:** anterior a Sprint 1 (fecha exacta no recuperada)
- **Fase:** plan
- **Decisión:** el formulario público de pedir turno (T3.1) no tiene CAPTCHA ni Cloudflare Turnstile ni ningún anti-spam en el MVP — riesgo aceptado y registrado explícitamente como R3 en `docs/implementation-plan.md`.
- **Alternativas consideradas** *(reconstruida)*: (a) sumar Turnstile desde el día 1 — descartada por alcance, es una dependencia externa más para un riesgo todavía no confirmado como real; (b) rate-limiting por IP sin CAPTCHA visual — quedó fuera también, mismo criterio de alcance.
- **Por qué** *(reconstruida)*: agregar protección anti-spam antes de saber si el spam es un problema real es trabajo especulativo — el MVP prioriza validar el flujo completo primero.
- **Qué se sacrifica:** el formulario puede recibir `turno`s pendientes falsos que ensucian el panel del profesional — mitigado parcialmente porque la vista Turnos (T3.3) permite cancelar en lote, y queda como backlog explícito sumar `turnstile.Verifier` con el mismo patrón dev/prod de spec §9.4 en cuanto se confirme que es un problema real.
- **Reversibilidad:** Alta — sumar Turnstile más adelante es aditivo, no requiere deshacer nada.

## TR-009: La opción "organización" se omite del flujo de onboarding, no se muestra deshabilitada *(reconstruida)*

- **Fecha:** anterior a Sprint 1 (fecha exacta no recuperada)
- **Fase:** plan — el MVP es solo alta de profesional individual (spec §2), sin cuentas de organización multi-profesional
- **Decisión:** el wizard de alta (`SumarseWizard`) arranca directo en el camino "particular" — la opción "organización" que pudiera sugerir el brief original **se omite por completo** del flujo, no aparece como una opción deshabilitada/"próximamente".
- **Alternativas consideradas** *(reconstruida)*: (a) mostrarla deshabilitada con un tooltip "próximamente" — descartada, generar expectativa sobre algo que no está en el MVP (y es explícitamente Fase 2 en `CLAUDE.md`) es peor que no mostrarla; (b) omitirla del todo — la elegida.
- **Por qué** *(reconstruida)*: mostrar una opción que no funciona invita a que un visitante la pruebe y se encuentre con un camino muerto — omitirla es más honesto que simular que existe.
- **Qué se sacrifica:** nada de funcionalidad real (organizaciones no están construidas); sí se sacrifica la oportunidad de "avisar" desde ya que viene en el futuro, si eso fuera valioso comercialmente.
- **Reversibilidad:** Alta — sumar el camino "organización" al wizard es aditivo cuando exista esa feature (Fase 2), no hay que deshacer nada de este MVP.

## TR-010: Identidad visual — Sistema Cascarón (paleta + tipografía) *(reconstruida)*

- **Fecha:** anterior a Sprint 1 (fecha exacta no recuperada) — adelantado a la fase de planificación (T5.1 originalmente en Sprint 5)
- **Fase:** plan — spec §9.7: "robar el lenguaje estructural de bungie.net... traducido a un tono de confianza clínica", vía `/frontend-design`
- **Decisión:** paleta de 6 tokens — `ink` (texto/fondo oscuro), `porcelain` (superficie clara), `panel` (blanco puro), `steel` (acento), `line`/`line-strong` (bordes), `muted` (texto secundario) — más `cascarón`/`urgencia` como semánticos reservados exclusivamente al bloque de `tipo_consulta` del calendario (nunca reutilizados para otra cosa). Tipografía: Big Shoulders (display condensada de alto contraste, uso restringido a títulos/cifras/rótulos), Public Sans (cuerpo), IBM Plex Mono (utilitaria — DNI, teléfono, horarios, cifras tabulares). Elemento firma: `QuadrantMark`, una grilla 2×2 de borde duro que replica la estructura de un odontograma real — con variante que encodea el estado de un turno en tablas (1 cuadrante lleno = pendiente, 4 llenos = agendado, tachado diagonal = cancelada).
- **Alternativas consideradas** *(reconstruida)*: no quedó registro de las alternativas de paleta/tipografía descartadas en el pase de diseño original — es la única entrada de este bloque donde la reconstrucción no puede ofrecer ni siquiera una aproximación razonable de qué otras opciones se pesaron.
- **Por qué** *(reconstruida)*: adelantar T5.1 a la fase de planificación (en vez de esperar a Sprint 5) permitió que Sprint 1 arrancara con tokens reales en vez de placeholders — evitó tener que re-skinnear pantallas ya construidas más adelante.
- **Qué se sacrifica:** un look estructural/condensado que se aleja del "cálido" que después pidió el cliente para el panel de gestión — resuelto en TR-013, no reemplazando esta identidad sino sumando una segunda paleta coexistente acotada a `/panel/**`.
- **Reversibilidad:** Alta — tokens centralizados en `globals.css`, `QuadrantMark` es un componente único reusado en todos lados.

## TR-011: Catálogo de especialidades visible acotado a "Odontología general" *(reconstruida)*

- **Fecha:** 2026-08-22 (confirmada por comentario de código en `internal/db/seed.go`)
- **Fase:** ejecución
- **Decisión:** aunque el catálogo cerrado completo (TR-004, `CatalogoEspecialidades`) sigue sembrado entero, `GET /especialidades` (y por lo tanto el wizard de alta y el filtro del buscador) solo expone hoy el subconjunto `EspecialidadesVisibles` — que es únicamente "Odontología general" — vía el flag `Especialidad.Activa`. El resto del catálogo queda sembrado pero oculto hasta que el cliente confirme la lista completa de especialidades reales a soportar.
- **Alternativas consideradas** *(reconstruida)*: (a) mostrar el catálogo completo asumido desde el día 1 — descartada, exponer especialidades no confirmadas por el cliente como si fueran definitivas genera expectativa sobre una lista que puede cambiar; (b) no sembrar nada hasta la confirmación — descartada, sin al menos una especialidad real no se puede probar el flujo de alta ni el filtro del buscador de punta a punta.
- **Por qué** *(reconstruida)*: separa "qué existe en la base" (todo el catálogo, listo para activarse) de "qué ve un usuario hoy" (solo lo confirmado) — activar el resto cuando el cliente responda es cambiar un flag, no re-sembrar ni migrar nada.
- **Qué se sacrifica:** el wizard de alta y el buscador público solo ofrecen una especialidad real por ahora — aceptado como estado transitorio, no el estado final del catálogo.
- **Reversibilidad:** Alta — activar el resto del catálogo es poner `Activa = true` en las filas correspondientes, sin migración.

## TR-012: Buscador público de clínicas adelantado a Sprint 1, sin el filtro de deploy todavía *(cerrada en Sprint 4/T4.5 — ver también el bloque de decisiones de Sprint 4 en `docs/implementation-plan.md`)*

- **Fecha:** 2026-08-22 (adelanto) — filtro cerrado 2026-08-23 (T4.5)
- **Fase:** ejecución
- **Decisión:** `GET /clinicas` (buscador por nombre de clínica/profesional/especialidad, spec §6, FR-10) y `/buscar` se adelantaron desde Sprint 4 a Sprint 1 a pedido directo del cliente (2026-08-22) — con una simplificación documentada en su momento: al no existir todavía el flujo de deploy de la página pública (T4.2), esa primera versión buscaba entre TODOS los profesionales registrados, no solo los que tuvieran `deployada_en` no nulo como pide la spec §5.2 ("para que el buscador no muestre páginas vacías o incompletas"). El filtro real (`JOIN paginas_publicas ... AND deployada_en IS NOT NULL` en `buscarClinicasHandler`) se sumó recién al cerrar T4.5 en Sprint 4 (2026-08-23) — ver ese mismo día en `docs/implementation-plan.md`.
- **Alternativas consideradas** *(reconstruida)*: (a) esperar a Sprint 4 completo (con el toggle de deploy ya armado) para recién ahí construir el buscador — descartada, el cliente pidió explícitamente adelantarlo; (b) adelantar el buscador pero bloquearlo por completo hasta que existiera el filtro — descartada, un buscador vacío no sirve para validar el flujo de búsqueda de punta a punta durante 3 sprints.
- **Por qué** *(reconstruida)*: adelantar la funcionalidad real (búsqueda contra la base de verdad) sin esperar a una feature secundaria (el toggle de deploy) permitió empezar a probar el buscador mucho antes, aceptando temporalmente que toda clínica registrada apareciera.
- **Qué se sacrifica:** entre Sprint 1 y el cierre de T4.5, cualquier clínica recién registrada (incluso sin haber tocado su página pública ni una vez) aparecía en el buscador — riesgo aceptado y ya cerrado.
- **Reversibilidad:** Alta — el filtro ya está cerrado (T4.5); revertirlo sería sacar una cláusula `JOIN`.

## TR-013: Restyle cálido del panel de gestión — segunda piel de color, sobre el mismo Sistema Cascarón (TR-010)
- **Fecha:** 2026-08-23
- **Fase:** ejecución (pedido explícito del cliente, antes de arrancar Sprint 4: "restylear el frontend ya implementado de la app de gestión... para que se vea más cálido, más suave y menos monocromático — sin tocar layout, estructura, componentes ni copys")
- **Decisión:** Paleta nueva de 10 tokens agregada a `apps/web/src/app/globals.css` (`@theme`), **coexistiendo** con los tokens del Sistema Cascarón (TR-010) en vez de reemplazarlos — la home pública/marketing, el onboarding (`/sumarse`, `/ingresar`, `/seleccionar-servicio`, `/perfil`) y el hero conservan ink/porcelain/steel/line tal cual, sin tocar un solo archivo de esas rutas:
  - `hueso` #F6F2EA (fondo de página del panel), `marfil` #FFFDF9 (superficie de cards/sidebar/topbar), `grafito` #35312B (texto principal, reemplaza ink solo dentro de /panel), `arena` #E7DFD1 (bordes 0.5px, reemplaza los bordes duros de 1-2px).
  - `salvia` #6E8F72 (acento principal) y `terracota` #C97F5A (acento cálido) llegan cada uno con una variante `-claro` (fondo pastel) y `-oscuro` (texto/relleno sólido) — **el tono medio nunca se usa como texto ni como relleno con texto encima**: contra blanco/marfil da ~3.1–3.6:1, por debajo del 4.5:1 de AA para texto normal (verificado a mano con la fórmula de contraste WCAG). `-oscuro` sobre `-claro` da ~6.6–6.8:1; `-oscuro` como relleno sólido con texto marfil encima da ~6.6–7.6:1. El tono medio queda para bordes, puntos/indicadores decorativos y hovers de borde — nunca portando texto.
  - Radius nuevo vía `@theme`: `--radius-card` (18px, cards/contenedores/modales) y `--radius-field` (12px, inputs/selects); botones/chips/badges/avatares usan el `rounded-full` nativo de Tailwind.
  - `--shadow-soft` (sombra difusa de dos capas, sin bordes duros) reemplaza los bordes de 1-2px negros de TR-010 dentro del panel.
  - Textura de fondo: `public/textures/soft-cross.svg` (tile de 52×52px, cruces suaves, opacidad 0.065–0.08) aplicada solo vía la clase `.panel-texture` en `app/panel/layout.tsx` — el único punto de montaje de las cuatro pantallas de gestión (General/Calendario/Turnos/Pacientes), nunca dentro de una card.
  - Chips de tipo de consulta: en vez de tocar el hex sembrado en `apps/api` (TR-001, `ColorTipoConsultaGeneral`/`ColorTipoConsultaUrgencia`, todavía cascarón/urgencia), `lib/turno-format.ts` suma `temaTipoConsulta()` — un resolver **solo de apps/web** que mapea por nombre ("Consulta general" → tema salvia, cualquier otro → tema terracota) y devuelve `{fondo, texto, acento}`. ## TR-016: Editor de página (T4.1/T4.2) — `PaginaPublica` se crea perezosa, y "previsualizar" no depende de "deployar"

- **Fecha:** 2026-08-23
- **Fase:** ejecución (Sprint 4, spec §5)
- **Decisión:**
  - `PaginaPublica` (1:1 con `Profesional`, la tabla existe desde T0.3) no se crea al registrarse — se crea con get-or-create la primera vez que hace falta (`GET/PATCH /panel/pagina/*`, `internal/http/pagina_publica.go`). Sin fila todavía, la página pública se comporta como "no oculta" (el default de la columna) — no hace falta que el profesional haya abierto el editor ni una sola vez para que su `/{slug}` funcione.
  - `GET /clinicas/{slug}` (la URL propia de la clínica) nunca se bloquea por falta de deploy, solo por `oculta` — "Ver página" desde la barra del editor tiene que poder previsualizar la página tal cual antes del primer deploy. Lo único gateado por `deployada_en IS NOT NULL` es el buscador público (`GET /clinicas`, T4.5, `buscarClinicasHandler` vía `JOIN paginas_publicas`).
  - "Deployar" es de una sola dirección — el backend es idempotente (llamarlo de nuevo no pisa la fecha original) y no existe un endpoint para "des-deployar". "Ocultar" es independiente y sí reversible en cualquier dirección: no afecta `deployada_en`, así que ocultar una página ya deployada no la saca del buscador (aparece igual, pero un visitante que entre ve mantenimiento) — son dos preguntas distintas ("¿está publicada?" vs. "¿se puede ver ahora?").
  - `ClinicaPublicaTemplate` es un único componente para dos consumidores: la página pública real (`/[slug]`) y la previsualización en vivo del editor (`/personalizar-pagina`, ver TR-017) — así la previsualización nunca puede desincronizarse de lo que ve un visitante real, no hay dos plantillas que mantener en paralelo.
  - "Guardar cambios" (barra de acciones) y todos los campos del panel de edición (T4.1) están deshabilitados a propósito, sin backend detrás — muestran de solo lectura los datos que ya existen en "Tu perfil" (nombre de clínica, teléfono, especialidades) más un placeholder fijo de "Sobre nosotros". La personalización real de contenido/diseño es trabajo posterior explícito (spec §5.1: "queda para desarrollo posterior") y está fuera del alcance del MVP salvo pedido explícito (`CLAUDE.md`).
- **Alternativas consideradas:** (a) Crear la fila de `PaginaPublica` en el flujo de registro — descartada: es una feature de Sprint 4, tocar el registro (Sprint 1) por una tabla que no se usa hasta dos sprints después agrega una dependencia innecesaria; el get-or-create resuelve lo mismo sin tocar `auth.go`. (b) Bloquear `/{slug}` también por falta de deploy (mostrar 404 o "no publicada" en vez del contenido) — descartada: el botón "Ver página" del editor necesita previsualizar antes de publicar, y la spec solo pide que el *buscador* no muestre páginas incompletas, no que la URL directa esté bloqueada. (c) Que "Deployar" reaparezca si se oculta la página (tratar "ocultar" como una especie de "des-deploy") — descartada: la spec los describe como dos acciones separadas en la misma barra, y mezclarlas haría que ocultar temporalmente una página real la sacara también del buscador, un efecto secundario no pedido.
- **Por qué:** Cada decisión evita acoplar dos cosas que la spec ya trata por separado (publicar vs. mostrar; contenido de la página vs. cuenta del profesional) — desacoplarlas ahora, aunque el MVP no explote esa flexibilidad todavía, evita tener que desenredarlas más adelante cuando sí haya edición de contenido real.
- **Qué se sacrifica:** Un profesional que nunca pasó por `/panel/pagina` ni una vez tiene una fila de `PaginaPublica` que no existe hasta su primera interacción — cualquier código nuevo que lea esa tabla directo (sin pasar por `getOrCrearPaginaPublica` o el mismo fallback de `getClinicaPublicaHandler`) tiene que acordarse de que puede no haber fila todavía, documentado en el comentario del handler para que no se repita el error de asumir que siempre existe.
- **Reversibilidad:** Alta — sin cambios de modelo de datos más allá de usar columnas que ya existían desde T0.3; los tres endpoints nuevos (`GET/PATCH /panel/pagina*`) y el join nuevo en `buscarClinicasHandler` se pueden revertir sin tocar el resto del backend.

## TR-017: El editor de página vive en `/personalizar-pagina`, fuera de `/panel/**` — corrección tras la primera entrega de T4.1

- **Fecha:** 2026-08-23
- **Fase:** ejecución (corrección pedida por el cliente sobre la primera entrega de T4.1/T4.2: "personalizar pagina es una pagina aparte por fuera de gestiona clinica... si doy click a tu pagina desde gestion clinica me lleva a esta pagina de edicion")
- **Decisión:** La primera versión de T4.1 montó el editor en `/panel/pagina`, dentro de `app/panel/layout.tsx` — heredaba el sidebar de navegación de clínica (General/Calendario/Turnos/Pacientes) y la textura de fondo de esas cuatro pantallas. Se corrige moviéndolo a `/personalizar-pagina`, una ruta de nivel superior, hermana de `/panel` (no una sub-ruta suya):
  - `app/panel/pagina/**` se elimina; nace `app/personalizar-pagina/page.tsx`, con su propio guard (`requireProfesional()` directo, ya no lo hereda de `panel/layout.tsx`) y su propio `<main>` (fondo `bg-hueso`, sin `.panel-texture` — esa sigue reservada a las 4 pantallas de gestión de verdad).

  - `lib/site-routes.ts` (qué rutas ocultan el footer público) suma `/personalizar-pagina` a la lista explícita — al dejar de vivir bajo `/panel`, ya no hereda ese prefijo automáticamente.
- **Alternativas consideradas:** (a) Dejarlo en `/panel/pagina` pero ocultar el `PanelSidebar` solo en esa ruta (un caso especial dentro del layout compartido) — descartada: el pedido es que sea "una página aparte", no una página de gestión con un layout distinto; mantenerla bajo `/panel/**` la sigue atando conceptualmente a "gestión de clínica" aunque no se vea el sidebar. (b) Una URL más corta como `/pagina` — descartada por posible confusión de lectura junto a `/[slug]` (la página pública de una clínica cualquiera); `/personalizar-pagina` es más largo pero inequívoco y ya sigue el mismo patrón de nombre verbo+objeto que `/seleccionar-servicio`.

Anidar el editor bajo `/panel` fue una lectura de implementación más simple (reusar el layout ya armado) que no reflejaba esa separación conceptual; esta corrección alinea la URL y el layout con lo que la spec y el cliente ya esperaban.
- **Qué se sacrifica:** Dos guards de sesión independientes (`panel/layout.tsx` y `personalizar-pagina/page.tsx`) en vez de uno solo compartido — duplicación mínima (una línea, `requireProfesional()`), aceptable a cambio de que cada área sea de verdad independiente y no dependa de la existencia del layout de la otra.
- **Reversibilidad:** Alta — es mover archivos y actualizar un puñado de `href`/`revalidatePath`, sin tocar el backend ni el modelo de datos (los tres endpoints de `pagina_publica.go` no se movieron, siguen en `/panel/pagina/*` — esa sigue siendo la ruta de la API, no de una página).

## TR-018: La página pública de una clínica pierde el header/footer de Mirage — primer paso hacia el subdominio propio (spec §5)

- **Fecha:** 2026-08-23
- **Fase:** ejecución (ronda de ajustes sobre Sprint 4/T4.3, pedido explícito del cliente: "ya sea en el buscador de clinicas o en la opcion ver pagina, deberia dejar de verse el header de la pagina principal de mirage y ver el del de la pagina del profesional, se habrira en un pagina aparte independiente del de la app, ya que la idea como se dijo al principio es que este alojada en subdominios")
- **Decisión:**
  - `/{slug}` (la página pública de cada clínica) deja de mostrar el `SiteHeader`/`SiteFooter` globales de Mirage — el único header que le queda es el propio, el "header básico" con anclas a cada sección que ya vive dentro de `ClinicaPublicaTemplate`. Nuevo helper `isClinicaPublicaRoute(pathname)` en `lib/site-routes.ts`: cualquier ruta de un solo segmento que no esté en la lista explícita de rutas propias de Mirage (`/buscar`, `/panel`, etc.) se trata como la página de una clínica — mismo criterio con el que Next.js resuelve `[slug]` de verdad, expresado en un helper reusable porque un Client Component solo tiene el `pathname`, no los route params.
  - Nuevo `SiteHeaderVisibility` (Client Component), mismo patrón que `SiteFooterVisibility` ya existente: recibe `<SiteHeader />` ya renderizado como `children` y decide ocultarlo según la ruta. `isFooterHidden` también empieza a usar `isClinicaPublicaRoute` — el footer de Mirage tampoco se muestra ahí.
  - Con el header global ausente en esa ruta, `[slug]/page.tsx` deja de compensar su altura (`pt-[var(--header-height)]`) y las anclas de `ClinicaPublicaTemplate` pasan de `scroll-mt-[calc(var(--header-height)+1rem)]` a un `scroll-mt-6` fijo, ya sin depender de una variable que en esta ruta nunca se termina de fijar (nadie mide la altura de un header que no está montado).
- **Alternativas consideradas:** (a) Mover `/[slug]` (y el resto del sitio) a route groups de Next.js con layouts raíz separados (`app/(sitio)/layout.tsx` con header/footer, `app/(clinica)/[slug]/layout.tsx` sin ellos) — la forma "correcta" a largo plazo, pero implica reubicar prácticamente todo el árbol de `app/` en un solo cambio; se descarta por ahora a favor de la opción (b), de mucho menor riesgo, dejando la migración a route groups como el paso natural cuando se implemente el subdominio real (Fase 2, fuera de alcance del MVP — CLAUDE.md: "subdominios propios... no las implementes solo porque aparecen como preparación futura"). (b) Ocultarlo del lado del cliente con el mismo patrón que `SiteFooterVisibility` — la elegida: mínimo diff, reutiliza un patrón ya probado en este mismo proyecto, sin restructurar el árbol de rutas.
- **Por qué:** La spec (§5) ya preveía el subdominio propio como el destino final de cada página de clínica — "para que se sienta una página aparte" es exactamente lo que un subdominio real da gratis (otro origen, sin nada compartido). Hasta que ese trabajo de infraestructura exista, ocultar el header/footer compartidos es la aproximación visual más fiel sin anticipar esa migración.
- **Qué se sacrifica:** La independencia es visual/de cliente, no estructural — el HTML inicial que llega del servidor todavía incluye (y luego oculta) el `SiteHeader` resuelto; no es una separación real de layouts raíz como daría route groups. Documentado acá para que la futura migración a subdominio no la mal-lea como "ya está resuelto del todo".

## TR-020: CI/deploy en Render — seis recursos (dos entornos completos), deploy automático por rama; convención de storage multi-tenant para cuando exista

- **Fecha:** 2026-08-24
- **Fase:** ejecución (T5.5, pedido explícito del cliente: "ahora entramos a la parte de CI y deploy en render con bluprint, de manera similar a Marcuzzi_Madryn pero ahora vamos a tener 6 servicios, un servicio de api y web de prod y otra de dev con sus bases de datos separadas... el deploy de la pagina sera atomatico al subir un commit a cualquiera de los stages usando los deploy hooks")
- **Decisión:**
  - **Dos entornos completos, no uno**: a diferencia de Marcuzzi_Madryn (3 recursos: 1 base + api + web, todo "prod"), acá `render.yaml` declara 6 — `dental-mirage-db`/`-api`/`-web` (prod) y `dental-mirage-db-dev`/`-api-dev`/`-web-dev` (dev), cada trío completamente separado, nunca comparten base de datos entre sí.
  - **Deploy automático atado a la rama, uno por entorno**: `.github/workflows/ci.yml` pasa a correr también en push directo a `dev` (antes solo `main` + pull requests), y el job `deploy` se separa en `deploy-prod` (`if: github.ref == 'refs/heads/main'`, dispara `RENDER_DEPLOY_HOOK_API`/`_WEB`) y `deploy-dev` (`if: github.ref == 'refs/heads/dev'`, dispara `RENDER_DEPLOY_HOOK_API_DEV`/`_WEB_DEV`) — mismo patrón de gateo que Marcuzzi_Madryn (necesita los 4 jobs de test/build en verde), duplicado una vez por rama.
  - **Dockerfiles nuevos** (`apps/api/Dockerfile`, `apps/web/Dockerfile`) y `.dockerignore` (raíz + `apps/api/`) — mismo patrón de build en dos etapas que Marcuzzi_Madryn, pero **más simples**: sin el baile de `ARG`/`--build-arg` para variables `NEXT_PUBLIC_*` (Dental Mirage no tiene ninguna — spec §9.3, BFF sin excepciones, `API_URL`/`CONTACTO_EMAIL` son server-only) y sin el volumen de `UPLOADS_DIR`/`api_uploads` (todavía no existe la feature de subir fotos). Los dos Dockerfiles se buildearon y corrieron de verdad contra el código real (`docker build` + `docker compose up --build`, con un registro/health-check/página SSR probados contra los contenedores) antes de darlos por buenos — no se asumió que el patrón de Marcuzzi_Madryn iba a aplicar igual sin probarlo.
  - **`docker-compose.yml`** se extiende con `migrate`/`api`/`web` (antes solo levantaba Postgres) — mismo Dockerfile que usa Render, para que "anda en mi máquina" y "anda en Render" sean literalmente la misma imagen.
  - **Storage de fotos multi-tenant, reservado pero no construido**: `render.yaml` ya declara los env vars de R2 (`sync: false`, sin cargar) en los 4 servicios `api`, con buckets separados por entorno (prod/dev) — pero la feature en sí (subir foto de perfil o de página pública) no existe todavía en el código (fuera del alcance del MVP salvo pedido explícito, `CLAUDE.md`). La diferencia real de fondo con Marcuzzi_Madryn no es técnica sino de escala: esa es una sola aplicación con un dueño (una key por foto alcanza); acá va a haber **N profesionales**, cada uno subiendo sus propias fotos de perfil y de página — sin un namespace por profesional, dos profesionales podrían pisarse archivos con el mismo nombre. Convención decidida ahora, para no tener que migrar keys ya escritas el día que la feature se construya: `paginas/{profesionalId}/{filename}` y `perfiles/{profesionalId}/{filename}`.
- **Alternativas consideradas:** (a) Un solo entorno (como Marcuzzi_Madryn), probando features nuevas directo en prod antes de un release — descartada, pedido explícito del cliente de tener dev separado con su propia base; con turnos/pacientes/datos reales de profesionales en juego, probar en prod deja de ser aceptable mucho antes que en un sitio de turismo sin cuentas de usuario críticas. (b) Una sola base de datos con un schema o prefijo distinto por entorno en vez de dos bases separadas — descartada: una migración con bug corriendo contra "dev" en la misma instancia física que prod es un radio de explosión mucho mayor que dos bases completamente aisladas: el aislamiento físico es más caro (dos planes free en vez de uno) pero elimina la clase de bug entera. (c) Construir ya la feature de storage (interfaz `storage.Storage` + R2) ya que se estaba tocando el deploy — descartada: no está pedida todavía, sigue fuera del alcance del MVP; se dejaron los env vars reservados y la convención de key documentada para no repetir este análisis desde cero cuando sí se pida, sin construir código sin una feature real que lo consuma.
- **Por qué:** El cliente pidió explícitamente reproducir "de manera similar a Marcuzzi_Madryn" pero con la duplicación completa prod/dev — la razón de fondo (aunque no la dijo así) es que Dental Mirage maneja datos reales de terceros (profesionales, sus pacientes, sus turnos) desde el día 1 de producción, a diferencia de Marcuzzi_Madryn en su etapa actual (sin reservas reales todavía) — tener un entorno de prueba real, con su propia base, deja de ser un lujo.
- **Qué se sacrifica:** El doble de recursos de Render en el plan free (2 bases, 4 servicios web) — dentro de los límites gratuitos por ahora, pero es la primera cuenta atrás explícita a tener en la cabeza si Render cambia esos límites. Cada cambio a `render.yaml` (agregar un env var, por ejemplo) hay que hacerlo en el par prod/dev a mano — no hay una forma nativa en Render de "heredar" configuración entre dos servicios del mismo blueprint.
- **Reversibilidad:** Alta — volver a un solo entorno es borrar la mitad de `services:`/`databases:` de `render.yaml` y el job `deploy-dev` de `ci.yml`, sin tocar el código de la aplicación en sí (los Dockerfiles no saben nada de "prod" vs. "dev", reciben esa distinción entera vía env vars).

## TR-021: Un solo entorno en Render, no dos — corrección tras un límite real del plan free (no se puede tener más de una base Postgres por cuenta)

- **Fecha:** 2026-08-24
- **Fase:** ejecución (corrección sobre TR-020, mismo día — pedido explícito del cliente al toparse con el límite real de Render: "me dice que no puedo tener mas de una database en el plan free, por el momento quitemos los servicios de prod y que solo queden los de main, que se deployan a los commits de dev")
- **Decisión:** `render.yaml` pasa de 6 recursos (dos entornos completos) a **3** — un solo trío `dental-mirage-db`/`-api`/`-web`, sin sufijo. El deploy de ese único entorno se dispara con push a `dev` (no `main`) — `ci.yml` colapsa `deploy-prod`/`deploy-dev` de vuelta a un solo job `deploy`, con `if: github.ref == 'refs/heads/dev'`. `main` sigue corriendo el pipeline completo de tests/build en cada push (sigue en la lista de `on: push: branches:`), simplemente no dispara ningún redeploy por ahora. `APP_ENV` del servicio `api` pasa de `production` a `development`, honesto con lo que ese servicio es hoy (el entorno de integración/prueba, no uno de prod real todavía). Los env vars de R2 (TR-020) se mantienen reservados tal cual, sin cambios — la convención de key multi-tenant sigue siendo válida sea cual sea la cantidad de entornos.

(b) Compartir una sola base entre "prod" y "dev" con un prefijo de tabla o un schema distinto — descartada, mismo argumento que ya cerraba esta puerta en TR-020: el aislamiento físico es la única garantía real de que un bug de dev no le toca un dato a prod, y una vez que se abre esa puerta "temporalmente" es fácil que quede así de forma permanente por inercia.
- **Por qué:** Es una restricción real de la plataforma, no una preferencia de diseño — Render no ofrece una segunda base Postgres gratis por cuenta. Elegir qué rama se queda con el único entorno disponible (`dev`, no `main`) prioriza tener *algo* desplegado y probable de verdad sobre tener nada desplegado hasta poder pagar dos bases; `main` (que además solo recibe merge cuando el cliente lo pide explícitamente, spec de flujo de ramas) puede esperar a que exista presupuesto para un entorno de prod separado sin que eso bloquee nada del trabajo diario.
- **Qué se sacrifica:** No hay, hoy, ningún entorno que se comporte como "producción real" — el único servicio desplegado se redeploya con cada push a `dev`, así que cualquier commit que rompa algo en runtime (aunque pase CI) llega ahí directo, sin la capa extra de seguridad que daba tener un `main` protegido y separado. Aceptado como riesgo temporal, documentado para que quede claro que es una consecuencia directa del límite del plan free, no una relajación deliberada de rigor.
- **Reversibilidad:** Alta — volver a separar los dos entornos es agregar de nuevo el segundo trío de recursos a `render.yaml` (el patrón anterior queda documentado en el comentario del archivo) y el job `deploy-dev` a `ci.yml`, en cuanto haya presupuesto para una segunda base Postgres.

El sidebar de `/panel` (TR-023, riel de íconos angosto en mobile) y el header con menú desplegable (TR-023) **no se tocan** — el cliente los confirmó explícitamente ("primero no quitar el sidebar desplegable de mobile"). `/personalizar-pagina` (el editor de página, que TR-017 ya estableció como un área separada de "gestión de clínica") tampoco se toca esta ronda — su apilado en mobile (TR-023) sigue vigente, fuera del alcance de este pedido puntual.
  - **Calendario, vista Semana/Día** (`calendar-grid.tsx`): la ronda anterior (TR-023) había cambiado `minmax(0, 1fr)` a `minmax(140px, 1fr)` de forma **incondicional** (vía `style` inline) — eso técnicamente also podía alterar el layout de escritorio en una ventana angosta (un laptop de 1366px con el sidebar abierto deja cada columna en ~142px, al borde del piso fijado), violando "no modifiques la versión de escritorio". Se corrige con una variable CSS (`--panel-dia-min-w`, definida en `globals.css` con `@media (max-width: 767px)`, mismo breakpoint `md` que ya usa el resto del sitio) y `minmax(var(--panel-dia-min-w, 0px), 1fr)` en el `style` — arriba de 768px la variable no existe, cae al fallback `0px`, matemáticamente idéntico a `minmax(0, 1fr)` (cero cambio de escritorio a NINGÚN ancho de viewport); debajo de 768px pasa a `150px`.
  - **Calendario, contenedor scrolleable** (`calendar-view.tsx`): ya tenía `overflow-auto` (agregado en TR-023) — se suma `WebkitOverflowScrolling: "touch"` inline (Tailwind no tiene una utilidad para esta propiedad) para que el gesto de deslizar en iOS se sienta con inercia nativa, no "a los tirones".
  - **Tablas** (`TurnosTable`, Pacientes, `PacienteTurnosTable`): **no necesitaban ningún cambio de layout** — ya tenían `overflow-auto` + `min-w-[...]` fijo (`720px`/`600px`/`560px`) desde que se construyeron (T2.4/T3.3/T3.5), sin ningún breakpoint que las comprima — es exactamente el patrón que este pedido describe. Solo se les suma el mismo `WebkitOverflowScrolling: "touch"`.
  - **Vista Mes** (`calendar-month-grid.tsx`, `min-w-[490px]` agregado en TR-023): se revisó y se dejó sin cambios — es un floor incondicional, pero matemáticamente nunca se activa en ningún ancho de escritorio realista (el contenido disponible del panel nunca baja de ~700px ni en un viewport de 1024px), así que no hace falta la misma corrección con variable CSS que en la vista Semana/Día.
- **Alternativas consideradas:** (a) Usar JS (`window.matchMedia`) para decidir el `minmax` en runtime en vez de una variable CSS — descartada: agrega un `useEffect`/listener/estado por un problema que CSS puro ya resuelve sin re-render extra ni riesgo de desincronización con el breakpoint real de Tailwind. (b) Mover el floor de 140/150px directo a una clase Tailwind con `max-md:` — descartada porque `gridTemplateColumns` necesita ser dinámico (`dias.length` columnas, 1 en vista Día, 7 en Semana) y Tailwind no genera utilidades para un valor calculado en runtime; la variable CSS es el único mecanismo que combina "solo mobile" con "cantidad de columnas dinámica" sin JS extra. (c) Revertir también el sidebar/header de TR-023 ya que están relacionados con "mobile" en general — descartada, el cliente fue explícito en preservarlos ("primero no quitar el sidebar desplegable de mobile") y el pedido de esta ronda es puntualmente sobre calendario/tablas.
- **Por qué:** El pedido de TR-023 y el de acá parecen contradictorios a primera vista (uno "que no se comprima", el otro ya había resuelto "que no se comprima" a su manera) pero en realidad son dos filosofías distintas para el mismo síntoma: TR-023 optó por reorganizar el contenido para que quepa (compactar columnas hasta un piso razonable); este pedido prefiere, específicamente en gestión de clínica, preservar el layout de escritorio intacto y resolver el ancho con scroll en vez de compactación — un dentista mirando su agenda semanal en el celular prefiere ver los bloques de turno con su tamaño real (aunque tenga que deslizar) antes que verlos comprimidos a algo casi ilegible. El bug real que motivó la corrección de `calendar-grid.tsx` (el `minmax(140px,1fr)` incondicional podía tocar desktop en viewports angostos) era una falla genuina de la implementación anterior, no solo una preferencia — se corrige independientemente de cuál de las dos filosofías gane.
- **Qué se sacrifica:** En un celular en vertical, la vista Semana del calendario ahora requiere deslizar para ver los 7 días completos (antes, con TR-023, se veían todos comprimidos sin scroll, aunque casi ilegibles) — aceptado porque es exactamente lo que pidió el cliente. Las tablas no cambian nada (ya cumplían el patrón pedido).
- **Reversibilidad:** Alta — la variable CSS (`globals.css`) y el `style` de `calendar-grid.tsx` son el único cambio de comportamiento real; volver al criterio de TR-023 (compactar en vez de scrollear) es bajar el valor de `--panel-dia-min-w` o volver a `minmax(0, 1fr)` sin condicional. Verificado: pipeline completo (`typecheck`/`lint`/`test:coverage`/`build`) limpio, 307 tests → 92.7% cobertura (sin tests nuevos — cambios puros de CSS/estilo inline, sin lógica nueva que cubrir).

## TR-025: Segunda vuelta sobre TR-024 — sidebar vuelve a su toggle único (sin breakpoint), y el ancho mínimo del calendario se fuerza una vez por contenedor, no por columna

- **Fecha:** 2026-08-24
- **Fase:** ejecución (corrección sobre TR-024, mismo día, rama `fix/mobile` — el cliente probó el deploy real y reportó dos problemas puntuales: "el sidebar de herramientas de gestion de clinica sigue sin poder desplegarse con la flechita, el calendario sigue estando apelmazado, si bien puedo moverme dentro del calendario para verlo completo... el cuadro del calendario sigue estando apelmazado, quiero el mismo layout de escritorio... para poder ir relevando la informacion")
- **Decisión:**
  - **Sidebar** (`panel-sidebar.tsx`): TR-023 había forzado el sidebar a quedar SIEMPRE en riel de íconos debajo de `md`, ocultando el botón de toggle ahí (`hidden ... md:flex`) — el razonamiento era "menos ancho fijo = más espacio para el contenido", pero el cliente prefiere lo contrario: el control manual de siempre (la flechita), disponible y funcional en cualquier tamaño de pantalla, y que sea el CONTENIDO el que se navegue con scroll horizontal en vez de que el sidebar le imponga un ancho fijo. Revertido íntegro a como estaba antes de TR-023: `collapsed ? "w-16" : "w-60"` sin variante `md:`, botón de toggle sin `hidden`, labels con `{!collapsed && <span>}` sin el `hidden md:inline` agregado.
  - **Calendario** (`calendar-grid.tsx`): TR-024 había forzado un piso de ancho por COLUMNA (`minmax(150px, 1fr)`, activo solo debajo de 768px) — funcionaba para la vista Semana (7 columnas), pero no hacía nada en la vista Día (la que se ve por defecto al entrar al calendario): con una sola columna, `1fr` siempre gana el 100% del ancho disponible sin importar el piso, así que esa vista seguía viéndose apretada en mobile — es lo que el cliente reportó como "el cuadro del calendario sigue estando apelmazado" a pesar de poder scrollear. Se corrige aplicando el mínimo UNA vez al contenedor completo (gutter de horas + columnas), no columna por columna: nueva clase `.panel-calendar-dias` en el `<div className="flex">` raíz de `CalendarGrid`, con `--panel-calendar-min-w` seteado inline en JS según la vista (`720px` para Día — aproximación de cuánto ocupa una sola columna en escritorio: casi todo el ancho del panel; `200px × N` para Semana/otras vistas de N días) y consumido solo debajo de 768px en `globals.css` (`min-width: var(--panel-calendar-min-w, auto)`). Las columnas internas vuelven a `minmax(0, 1fr)`, la expresión original sin ningún condicional — con el contenedor ya forzado a ser ancho, se reparten ese ancho con total normalidad.
  - **Tablas** (Turnos/Pacientes/turnos del detalle de paciente): sin cambios — ya cumplían "layout de escritorio + scroll horizontal" desde que se construyeron (TR-024 ya lo había confirmado), el cliente las mencionó como parte del alcance a verificar, no como algo roto.
- **Alternativas consideradas:** (a) Para el sidebar, mantener el riel angosto en mobile pero volver a mostrar el botón de toggle (permitiendo expandir a w-60 solo mediante un tercer estado "expandido en mobile") — descartada: agrega un tercer estado (colapsado/riel-mobile/expandido-mobile) por encima del que ya existía, más complejidad que simplemente devolver el control original que el cliente pidió de vuelta explícitamente. (b) Para el calendario, subir el piso por-columna a un número enorme (ej. 900px) para que en vista Día ese único "columna" heredara ese piso igual — descartada: `minmax(900px, 1fr)` en una grilla de 1 sola columna sí fuerza 900px, pero es una coincidencia frágil (funciona por accidente de que N=1, no por diseño) y en Semana (N=7) el mismo número multiplicado por 7 sería absurdo (6300px) — separar el cálculo por vista (como quedó) es más explícito y correcto para cada caso. (c) Calcular el ancho mínimo con JS/`matchMedia` en vez de CSS var + media query — descartada, mismo motivo que TR-024: CSS puro evita un `useEffect`/listener extra y no puede desincronizarse del breakpoint real.
- **Por qué:** Ambos problemas comparten la misma causa: la ronda anterior optimizó por "ahorrar espacio" (sidebar angosto, piso modesto por columna) en vez de por "replicar fielmente lo que se ve en escritorio", que es literalmente lo que el cliente pidió dos mensajes seguidos. Una vez identificado ese desalineamiento, la corrección es aplicar el mismo criterio (layout de escritorio + scroll) de forma más completa: al sidebar (dejándolo intacto, controlado a mano) y al calendario (aplicando el mínimo donde realmente hace falta — el contenedor entero, no una columna que en la vista por defecto ni siquiera participa del cálculo).
- **Qué se sacrifica:** En mobile, con el sidebar expandido a mano (w-60/240px), el contenido del panel dispone de menos ancho visible de entrada que con el riel angosto de TR-023 — aceptado, es exactamente la contrapartida que el cliente eligió (control manual del sidebar sobre "ahorro automático de espacio"). La vista Día del calendario en mobile ahora requiere scroll horizontal para ver toda la ficha de un turno más ancho que el viewport, incluso siendo una sola columna — antes (con el bug) no hacía falta scrollear porque todo se aplastaba a la pantalla; ahora se ve más grande pero exige el gesto de deslizar, que es exactamente lo pedido.
- **Reversibilidad:** Alta — mismo mecanismo que TR-024 (una clase + variable CSS + un par de constantes en JS), sin cambios de modelo de datos. Verificado: pipeline completo (`typecheck`/`lint`/`test:coverage`/`build`) limpio, 307 tests → 92.73% cobertura (sin tests nuevos — `panel-sidebar.test.tsx` ya cubría el comportamiento restaurado tal cual, y los cambios de `calendar-grid.tsx` son solo constantes/estilo inline sin ramas nuevas).

## TR-026: Gestión de clínica en mobile — estructura fija (header/sidebar/página) + una sola área de scroll por página + tamaños fluidos con `clamp()`/`vw`

- **Fecha:** 2026-08-24
- **Fase:** ejecución (tercera vuelta sobre TR-024/TR-025, mismo día, rama `fix/mobile` — pedido explícito y muy detallado del cliente: header/sidebar fijos, "la página en sí NO debe scrollear (el layout raíz con altura 100vh y overflow: hidden)", "únicamente el área de contenido... se puede desplazar horizontal y verticalmente", "el contenido debe adaptarse al tamaño de la pantalla... ni gigante ni diminuto... clamp() usando vw", "en vez de un ancho fijo enorme, usá min-width... para que se estire y llene la pantalla, y que solo desborde... lo que realmente no entra", "no modifiques el meta viewport global")
- **Decisión:**
  - **Estructura fija, un solo scroll por página** (`app/panel/layout.tsx`, mobile-only vía `max-md:`): la raíz de gestión de clínica pasa a medir exactamente `100dvh` (no `100vh` — en mobile Safari `dvh` descuenta la barra de direcciones, más preciso que lo que pidió el cliente literalmente pero sin cambiar la intención) menos el header, con `overflow-hidden` — así el documento (`html`/`body`, compartido con el resto del sitio, **no tocado**) nunca llega a necesitar scroll propio, sin que haga falta editar `app/layout.tsx`. `PanelSidebar` queda como hermano de `<main>`, fuera del área que scrollea — al no moverse nunca, queda visualmente "fijo" (además de su `sticky` ya existente, que sigue sin romper nada, solo se vuelve redundante en mobile). `<main>` pasa a ser el ÚNICO elemento que scrollea verticalmente (`overflow-y-auto`, `overflow-x-hidden`, `min-h-0` para el gotcha clásico de flexbox) — cada página adentro fluye con su alto natural (título + filtros + tabla/calendario juntos, como cualquier página), en vez de que cada widget interno tuviera su propio recorte vertical (que hubiera significado *dos* scrolls anidados: uno en `<main>` y otro dentro de la tabla).
  - **Scroll horizontal solo donde hace falta, no en toda la pantalla**: el calendario (`calendar-view.tsx`) y las tres tablas (`TurnosTable`, Pacientes, `PacienteTurnosTable`) pierden su recorte/scroll VERTICAL propio en mobile (`max-md:overflow-y-visible`, y en las tablas también `max-md:max-h-none`) — ese scroll ahora lo da `<main>` — pero conservan su `overflow-x-auto` sin cambios, en las dos direcciones de viewport: es el único mecanismo de scroll horizontal, acotado a ese widget puntual.
  - **Ancho mínimo "que llena y solo desborda lo que no entra", no "un ancho fijo enorme" (tercera vuelta sobre `calendar-grid.tsx`)**: TR-024 (primera vuelta) ya había puesto un piso de ancho *por columna* (`minmax(150px, 1fr)`) — funcionaba para la vista Semana, pero no hacía nada en la vista Día (una sola columna: `1fr` siempre gana el 100% del ancho sin importar el piso), así que esa vista seguía "apretada". TR-025 (segunda vuelta) sobrecorrigió al revés: forzó un ancho ENORME fijo sobre TODO el contenedor (720px para Día, hasta 1400px para Semana) — resolvía lo de la vista Día, pero es exactamente lo que el cliente ahora pide evitar explícitamente ("en vez de un ancho fijo enorme..."). Esta vuelta reinstala el piso *por columna* de TR-024, con dos cambios: (a) el valor es `clamp(6.5rem, 30vw, 10.5rem)` (~104px–~168px) en vez de un px fijo, escalando con el viewport como pidió el cliente; (b) la vista Día deja de necesitar ningún piso especial — con el nuevo entendimiento del pedido, que una sola columna llene el 100% del ancho vía `1fr` sin desbordar nada **es exactamente lo correcto** ("que se estire y llene la pantalla"), no un bug a corregir. El piso por columna en `.panel-calendar-dias` (definido en `globals.css`, `@media (max-width: 767px)`) solo se activa cuando de verdad no entra (Semana, 7 columnas) — ahí sí desborda a propósito y el `overflow-x-auto` del contenedor lo hace navegable. `CalendarMonthGrid` recibe el mismo criterio: su `min-w-[490px]` incondicional pasa a `max-md:min-w-[clamp(280px,90vw,420px)]` — en escritorio ya no tiene ningún min-width propio (nunca hacía falta, el `grid-cols-7` se reparte solo).
  - **Tamaños fluidos con `clamp()`/`vw`**: cada `h1` de las cinco pantallas de `/panel` (General/Calendario/Turnos/Pacientes/detalle de paciente) pasa de `text-3xl` fijo a sumar `max-md:text-[clamp(1.25rem,6vw,1.875rem)]` (o `6.5vw` según el ancho de página); el padding raíz de cada página pasa de `p-8` fijo a sumar `max-md:p-[clamp(1rem,4vw,2rem)]`. El techo de cada `clamp()` coincide con el valor de escritorio (`1.875rem`≈`text-3xl`, `2rem`=`p-8`), así que el propio `clamp()` converge al mismo número que ya usaba escritorio a medida que el viewport crece — no hace falta un breakpoint aparte para "volver" al tamaño de escritorio.
  - **Sidebar** (`panel-sidebar.tsx`): sin cambios respecto de TR-025 (ya había vuelto a su comportamiento único, sin variante mobile) — la única novedad acá es el ajuste de `100vh`→`max-md:100dvh` en su propia altura, por el mismo motivo que la raíz del layout.
  - **Meta viewport**: no tocado — sigue siendo el default de Next.js (`width=device-width, initial-scale=1`), nunca se editó `app/layout.tsx` ni se agregó un `<meta>` propio.
- **Alternativas consideradas:** (a) Aislar el scroll vertical DENTRO de cada widget (tabla/calendario) en vez de en `<main>`, fijando el título/filtros de cada página con `flex-shrink-0` y solo el widget con `flex-1 overflow-y-auto` — descartada: requiere una cadena de `min-h-0` en cada nivel (layout → main → página → widget) mucho más frágil de mantener y más difícil de verificar sin poder correr un browser real en este entorno; y hubiera dejado DOS scrolls verticales anidados (uno en el widget, uno potencial en la página si algo no encaja bien), justo lo que "un solo scroll" busca evitar. La opción elegida (un solo `overflow-y-auto` en `<main>`) es más simple y con menos superficie de bugs de flexbox. (b) Mantener el ancho fijo enorme de TR-025 pero "bajarlo" a algo más moderado — descartada, el cliente no pidió un número más chico, pidió el mecanismo contrario (`min-width` que se adapta y solo desborda lo necesario, no un valor fijo). (c) Usar `100vh` en vez de `100dvh` para seguir la letra del pedido ("altura 100vh") — descartada a favor de `dvh`: es la unidad correcta para lo que el cliente describe (que la página no scrollee en mobile), `100vh` en Safari mobile incluye el espacio de la barra de direcciones y de hecho *reintroduce* un scroll fantasma cuando esa barra está visible; documentado acá para que quede claro que es una mejora técnica sobre el pedido literal, no una desviación de la intención.
- **Por qué:** El pedido de esta ronda es mucho más específico y prescriptivo que las dos anteriores — describe el mecanismo exacto (contenedor raíz 100vh+overflow:hidden, un área de contenido con su propio overflow:auto, min-width en vez de ancho fijo, clamp()/vw) en vez de solo el síntoma. Seguirlo al pie de la letra (con el único ajuste técnico de `dvh` sobre `vh`, justificado arriba) es lo que finalmente separa con claridad "estructura de la app" (header/sidebar, que no deberían moverse nunca) de "contenido de la sección" (calendario/tablas, que sí necesitan moverse para mostrar más de lo que entra) — una distinción que las dos rondas anteriores no habían modelado explícitamente a nivel de layout, solo a nivel de cada widget por separado.
- **Qué se sacrifica:** Nada de fondo — es una reestructuración de layout puramente en CSS/Tailwind (`max-md:`), sin tocar el modelo de datos, sin tocar `app/layout.tsx` ni el meta viewport, sin tocar ningún componente fuera de `/panel/**`. La complejidad de mantener una cadena `min-h-0`/`overflow` correcta a través de `panel/layout.tsx` → `<main>` queda documentada acá para quien la toque después: si se agrega un nuevo nivel de anidamiento flex dentro de `/panel/**` en el futuro, hay que revisar si necesita su propio `min-h-0` para no romper el `overflow-y-auto` de `<main>`.
- **Reversibilidad:** Alta — todo son clases `max-md:`/`clamp()` y una regla de `globals.css`, reversible sin tocar modelo de datos ni backend. Verificado: pipeline completo (`typecheck`/`lint`/`test:coverage`/`build`) limpio, 307 tests → 92.7% cobertura (sin tests nuevos — cambios puros de CSS/estilo, sin ramas de lógica nuevas que cubrir); además se inspeccionó el CSS compilado de producción (`.next/static/chunks/*.css`) para confirmar que Tailwind generó correctamente el bloque `@media not all and (min-width:48rem)` (el `max-md:` de Tailwind v4) con todas las clases esperadas adentro (`h-[100dvh]`, `overflow-hidden`, `min-h-0`, `max-h-none`, `overflow-y-visible`, los `clamp()` de padding/tipografía) — no se puede probar en un browser real dentro de este entorno, así que esta inspección del CSS generado fue la verificación más cercana disponible antes de pedirle al cliente que lo pruebe en su celular real.
